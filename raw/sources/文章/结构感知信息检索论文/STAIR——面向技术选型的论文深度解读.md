# STAIR：把“目录”变成检索入口，而不只是文档装饰

## 先用一句话理解

STAIR 的核心主张是：面对一本书、产品文档或制度手册这类**层级稳定的长文档**，不要只把文本切成固定长度的 chunk 再做相似度搜索；应当把目录（Table of Contents，ToC）作为全局地图，让模型先根据“问题 + 完整目录”选出最可能包含答案的**叶子章节**，再由这个章节地址取得正文。

它不是一个直接产出最终答案的 RAG 系统，也不是传统的向量库。更准确地说，它是一个把“用户问题 → 规范章节地址”学进模型参数、同时又用目录约束模型输出的**结构化路由器 / 参数化检索器**。

---

## 1. 这篇论文想解决什么真实问题

传统 RAG 的常见做法是：把一份长文档按字数或 token 数切块，为每个块建立 BM25 或向量索引，查询时从所有块中找相似文本。

这种做法有一个很实际的问题：切块保住了局部句子，却丢掉了文档本来就有的“知识地图”。例如一本医学教材中，“慢性病”“老年人”“日常活动”这几个词可能散落在不同段落；但读者其实会先从目录判断它大概率属于“老年人护理”下的某节，再阅读该节。固定长度 chunk 很难表达这种章节归属与上下位语义。

另一个被论文针对的问题来自参数化检索（如 DSI）：模型可以把语料知识压进参数，并直接生成文档 ID，但 ID 往往是没有语义的符号。模型不仅要记住“问题对应什么内容”，还要从训练样本中间接推断整个文档的组织方式；训练覆盖不足时，容易输出不存在的 ID，或把相近主题路由到错误章节。

STAIR 的判断是：很多企业知识库、技术文档、产品帮助中心、教材和报告，本来就带有高质量目录。与其丢掉它，不如把目录视为一个显式、可用的检索索引。

---

## 2. 最核心的技术思想

STAIR 把检索目标从“找一段最相似的文本”改成“在一个已知的目录树中，选择能回答问题的叶子节点”。

这有三个连在一起的变化：

1. **用章节标题代替无语义文档 ID。** 叶子标题既是可执行地址，也带有主题信息，例如“31.3 老年人护理的应用流程”比 `doc_1842` 更容易和问题建立语义对应。
2. **每次判断时都给模型完整目录。** 模型不必完全靠参数记住全部可选章节；目录把全局结构重新放回当前上下文，帮助它区分相邻主题、父子章节和同名概念。
3. **只允许生成有效的叶子节点。** 推理时采用受约束生成：候选输出只能来自当前目录的叶子节点，而不是让模型自由拼一个章节名。这样把“模型编造不存在的检索地址”变成系统层面可避免的错误。

所以它的价值不只是“目录标题带来了更多文本”。更本质的是：目录同时承担了**全局语义提示、候选集合、合法输出约束**三种角色。

## 3. 系统由哪些部分组成

| 部分 | 职责 | 为什么重要 |
| --- | --- | --- |
| 文档与目录解析 | 从 PDF / 文本提取目录树，并将每个叶子节点绑定到对应正文 | 建立稳定的“章节地址 → 内容”映射；目录质量决定上限。 |
| 问题生成与数据准备 | 从各章节正文生成多个可回答的问题，并为问题标注正确叶子节点 | 将“正文知识”转化为可监督的“问题 → 章节”训练信号。 |
| 参数化知识摄入 | 用问题和完整目录微调 LLM，让它在参数中学到正文内容与章节的关联 | 模型不是读到正文后即时搜索，而是在离线训练阶段学会这种关联。 |
| 目录条件化分类器 | 输入“问题 + 完整目录”，输出正确叶子节点 | 这是 STAIR 的核心检索器；目录是实时可见的候选空间。 |
| 受约束解码器 | 将输出限制为当前目录中存在的叶子标题 | 防止无效章节名，降低检索地址层面的幻觉。 |
| 正文获取与下游回答层 | 依据预测叶子节点取回该节内容，再交给 RAG 回答器或 Agent | 论文重点评测的是路由准确性；生产系统仍需要这一层完成证据阅读与最终回答。 |

一个容易误解的点：论文把模型称为“检索器”，但它的直接输出不是正文 chunk，而是**章节地址**。要构建可追溯的问答系统，仍应把地址解析回原文，并让最终回答基于原文生成。

## 4. 从输入到结果，完整如何运行

### 离线阶段：把一本有目录的文档变成可检索对象

1. **解析文档。** 从书籍或长文档提取目录，并将每个叶子目录节点与其正文内容对齐。这里的“叶子”指没有更细分子章节的最小可检索单元。
2. **为正文生成训练问题。** 论文用 LLM 为各段正文生成覆盖主要主题的多个问题；每个问题天然知道自己来自哪个叶子章节。
3. **构造训练样本。** 输入固定为“任务提示 + 用户问题 + 这本书的完整目录”；目标固定为正确的叶子标题。正文不会在这一步塞进模型上下文，而是通过大量问题-章节配对被灌入模型参数。
4. **微调 LLM。** 论文使用 Mistral Instruct，通过 LoRA 做监督微调；验证集用于选择停止点。这样训练出的模型同时学会两个事情：该书讲了什么，以及目录中的哪一项最适合回答某类问题。

### 在线阶段：先选结构地址，再取内容

1. 用户提出问题，系统拿到该知识库的完整目录。
2. 系统把“问题 + 目录”拼成提示，送入已针对该语料微调的模型。
3. 解码器只允许输出目录中合法的叶子标题；模型选出一个章节地址。
4. 系统以该地址取回对应章节正文。若用于问答或 Agent，还应在这一节内部继续做细粒度段落检索、阅读和回答生成。

可以把它放进实际 RAG 流程中理解：

```text
用户问题
  → STAIR：从目录树选出最相关叶子章节
  → 在该章节 / 子树内进行 chunk 或向量检索
  → 取回原文证据
  → 回答模型或 Agent 生成可追溯结果
```

论文展示的是前两步中的“结构路由”；最后两步是工程落地时应补齐的部分。

## 5. 最关键的实现细节与设计取舍

### 目录不是附带元数据，而是每次推理的输入

STAIR 在训练和推理时都把完整 ToC 放进提示。这使模型不用靠训练样本猜测候选章节集合，也让标题的父子关系、主题相邻关系保持可见。代价是目录会占用上下文：论文的 STAIR 输入上限约为 14k token。对于目录极深、目录随查询动态变化或拥有百万级页面的知识库，直接塞完整目录未必可行。

### 训练目标选“叶子章节”，而不是任意文本块

叶子节点在这里是一种人为定义的检索粒度：它比整本书小，又保留清晰的主题边界。好处是地址稳定、可解释，且可直接映射回正文；风险是章节太大时仍需要二次检索，章节太细时目录和候选集合会过长。因此生产系统需要根据文档结构决定叶子是否足够细，而不能机械沿用 PDF 的原始标题层级。

### 受约束生成是可靠性机制，不只是解码技巧

论文把“生成了不存在的叶子节点”定义为一种检索幻觉。受约束生成把输出空间锁定为合法章节，因此能显著减少这一类错误。这里要区分两件事：

- 它能防止模型给出**不存在的章节地址**；
- 它不能保证模型选中的合法章节一定真的能回答问题，更不能保证下游回答模型不会编造内容。

也就是说，约束解码解决的是“路由输出格式与候选合法性”，不是事实正确性的全部问题。

### 参数化摄入换取了在线速度，也带来更新成本

STAIR 的问题-章节对应关系来自微调，不是每次查询都在原始全文中做开放式搜索。适合内容较稳定、可批量训练、问题分布可预期的知识库；但源文档修改、目录重排或新增章节后，需要重新生成训练样本并增量或重新微调。论文没有证明它能在频繁更新的大型企业语料上保持低维护成本。

### 合成问题的质量决定知识摄入质量

论文用 LLM 从段落生成训练问题，这能快速覆盖 18 本跨领域教材，却也让训练与测试都依赖同一类合成问题分布。真实用户可能表述更短、更含混、跨章节，或使用与教材不同的业务词汇。部署前应使用真实查询日志做独立评测，并把人工标注的困难问题加入训练和回归集。

## 6. 相比已有方案新在哪里

| 方案 | 它主要依赖什么 | STAIR 的差异 |
| --- | --- | --- |
| BM25 | 关键词在 chunk / 文档中的词面匹配 | STAIR 先利用章节语义和层级定位，不让关键词直接在全部 chunk 中竞争。 |
| 向量检索 / DPR | 查询与文本块的向量相似度 | STAIR 的第一跳不是相似度最近的文本，而是目录树中的结构节点；两者可以串联，而非只能二选一。 |
| DSI | 把语料编码进模型参数，再生成一个文档 ID | 两者都属于参数化索引；STAIR 把无语义 ID 换成目录叶子标题，并把完整目录提供给模型作为显式候选空间。 |
| RAPTOR 一类层次检索 | 从文本聚类、摘要后构造层次，并以密集检索访问 | STAIR 利用已有的人工目录，并通过模型生成节点地址做检索；它不解决“从零自动构树”的问题。 |

真正的新意在于：把人类已写好的信息架构直接引入模型的输入和输出约束中，而不是把文档结构压扁为无关系的 chunks，也不是要求模型在参数里暗中记住这个结构。

## 7. 实际效果用文字怎么理解

论文在 SearchTome 上评测：这是一个由 6 个领域、18 本开放教材构成的结构化检索基准，问题的正确答案被标注为某个目录叶子节点。

结果显示，STAIR 在“第一名是否命中正确叶子章节”这项指标上优于 BM25、通用向量检索和同样经过微调但不输入目录的 DSI；平均首选命中率约为八成，而 DSI 约为七成多。对工程决策更有意义的现象是：当某个章节的训练问题较少时，STAIR 的优势更明显。原因不是它凭空学到更多知识，而是目录把稀有章节的名称和位置直接暴露给了模型，减少了模型仅靠少量样本记住结构的负担。

论文还显示，STAIR 输出不存在章节名的比例接近于零，而不带目录的 DSI 更容易在低样本叶子上编造或混合章节名。这验证了“候选集合 + 受约束生成”对路由可靠性有用。

但不要把这些结果读成“STAIR 已经解决 RAG 幻觉”。该评测的正确性是“是否选对目录叶子”，不是最终答案是否忠实于正文；数据集以有清晰 ToC 的教材和合成问题为主。因此它证明了结构路由的潜力，而非所有文档问答场景的通用胜利。

## 8. 局限与不适用场景

1. **依赖高质量、稳定的全局结构。** 论文自己也限定在已有目录的语料。会议纪要、聊天记录、杂乱 Wiki、网页碎片或跨库混合检索没有天然 ToC，不能直接照搬。
2. **每个语料库都需要知识摄入。** 模型需针对书籍 / 文档库微调；这与“接入新文件即可马上检索”的通用向量库体验不同。
3. **整份目录的上下文成本会增长。** 文档库越大、目录越深，输入越长；超出上下文窗口时必须改为分层路由或候选子树召回，论文尚未完成该规模验证。
4. **合成 QA 可能高估效果。** 生成式问题有覆盖优势，但不能替代真实用户的歧义问法、跨章节推理和口语化表达。
5. **单一叶子输出不处理多跳与组合问题。** “比较两章政策差异”“先找定义再找例外”这类任务通常要返回多个节点并安排后续推理，论文把这部分留给未来工作。
6. **目录本身可能不等于最佳检索粒度。** 标题含糊、章节过大、内容跨节重复时，结构路由仍可能稳定地把问题送到一个不够精确的合法节点。

## 9. 对 Agent / Harness 技术选型的启发

### 适合放在哪里

最适合把 STAIR 思路放在 Agent 的**检索规划层**：它不替代最终阅读器，而是为“去哪里找”提供可解释的第一跳。

```text
任务理解 / Query Rewrite
  → 结构路由（目录、产品树、策略树、代码模块树）
  → 受限到命中的子树
  → 子树内混合检索（关键词 + 向量 + 重排序）
  → 原文阅读、工具调用与答案生成
```

这种分层比“全库向量 Top-K 后直接回答”更适合结构明确的知识：产品帮助中心、工程 Runbook、合规制度、SDK 文档、课程资料、代码仓库的模块树等。对 Agent 而言，目录节点还可以成为可审计的执行状态：先选领域，再缩小到页面或段落，最后调用专用工具。

### 值得直接借鉴的设计

- **为内容保留规范、语义化的稳定地址。** 不要只存随机 chunk ID；让章节路径、产品模块、页面层级成为可被模型引用的实体。
- **把结构作为检索输入而非离线标签。** 当前候选树显式给模型，比期待模型从历史样本中记住系统结构更稳。
- **限制关键动作的合法输出空间。** 对章节选择、工具选择、工作流节点选择都可采用 schema / grammar / 枚举约束，先防止无效动作，再处理正确性。
- **把稀有节点单独测出来。** 平均准确率会掩盖长尾章节的路由失败；应按节点样本数、深度和业务风险建立回归集。

### 必须按本地系统改造的部分

- 目录很大时，先用廉价召回器或父节点分类缩小候选子树，再进行叶子选择；不要把百万级目录直接塞给模型。
- 内容更新时，将“目录版本、章节内容版本、训练数据版本、模型版本”绑定，避免模型按旧目录返回已失效地址。
- 用真实查询日志、人工标注和在线反馈替换或补强合成 QA；高风险领域还应加入权限过滤与证据校验。
- 将结构路由与细粒度检索结合：先选章节，再在章节内检索段落，最终回答必须附着原文证据。

### 暂时不应照搬的情况

- 文档持续高速变化、必须实时生效，或不能接受微调流水线维护成本；此时优先采用可增量更新的混合检索。
- 语料没有可信层级，或层级是人为拼凑且标题与正文语义弱相关；先解决信息架构，再谈结构感知检索。
- 任务要直接给出可核查结论、引用和长链推理；STAIR 的单叶子路由只能是前置步骤，不能独立承担回答责任。

## 10. 一页式结论

| 问题 | 结论 |
| --- | --- |
| 这篇论文最值得记住的思想 | 把文档目录变成“模型可见、可选择、可约束”的检索空间，而不是把结构压扁后只搜索 chunk。 |
| 它真正解决了什么 | 在结构稳定的长文档中，更可靠地把问题路由到正确主题单元，尤其改善低样本章节和无效地址生成。 |
| 最值得借鉴什么 | 层级化检索、语义化地址、约束输出、结构路由与正文检索分离。 |
| 暂时不用照搬什么 | 为每个频繁变化的知识库训练一个参数化索引；把章节选择当成最终答案。 |
| 采用前先验证什么 | 目录是否可信且稳定、真实用户问题能否映射到单一节点、更新频率能否承受训练成本、子树内检索是否能找回真正证据。 |

如果把 STAIR 的思想压缩成一个工程原则，就是：**先利用人类已经建立的结构缩小“该去哪里找”，再在局部做精确检索和可信回答。**
