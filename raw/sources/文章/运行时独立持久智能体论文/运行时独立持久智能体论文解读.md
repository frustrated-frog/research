# Runtime-Independent Persistent Agents：运行时独立持久智能体论文解读

> 原论文：*Runtime-Independent Persistent Agents: Preserving Identity, Memory, and Code Across Models, Harnesses, and Servers*，Zhenyu Zhao、Roy Zhao。本文的“页码”均指论文 PDF 页码。

## 先用五分钟理解

这篇论文讨论的不是“怎样让模型记得更多”，而是一个更基础的系统问题：**一个长期运行的 Agent 换了模型、harness、服务器、聊天入口之后，凭什么还能被称为同一个 Agent？**

作者的答案是把“执行它的环境”和“构成它的持续主体”拆开：

$$
P_t=(I_t,M_t,B_t)
$$

- \(I\)：安装在该 Agent 私有空间中的架构化身份表示；
- \(M\)：私有、耐久的记忆与与连续性有关的工作流状态；
- \(B\)：有版本的可执行 body——代码、提示词、工具、策略、测试、provider contract 与演化机制。

模型／推理器 \(R\)、编排 harness \(H\)、主机和服务环境 \(D\) 则是可替换的执行底座 \(E=(R,H,D)\)；聊天、API、邮件、GUI 等是交互表面 \(S\)。部署只是 \(P\) 在 \((E,S)\) 上的一次实例化，而不是 \(E\) 或某个聊天会话拥有 \(P\)（第 2 页，式 1–4）。

因此，作者将“迁移”定义为：在保持身份、记忆谱系、body 版本与唯一续接授权的前提下，替换 \(E\) 或 \(S\) 中至少一个元素。它不是重启，也不是复制，更不是从一个记忆备份里静默分叉出两个都自称原身的实例。

最重要的边界也必须先说清：论文声称的是**授权的系统连续性**（authorized system continuity），不是不同模型下的行为、能力、措辞或“人格”不变。作者只报告了实现机制与单轴替换的证据；没有做完整的多运行时交叉矩阵，也没有给出行为身份保真度的基准结果（第 1、5–7 页）。

## 1. 论文到底在解决什么问题

### 1.1 被忽略的“跨时间”边界

常见的口头定义是“Agent = 模型 + harness”。它适合回答一个同步问题：**此刻究竟是什么在生成行为？** 但不够回答跨时间的问题：

- 模型由 A 换为 B，是迁移还是死亡后重建？
- 同一份 memory 目录被复制到两台机器，哪一个有权继续代表原 Agent？
- 聊天线程重置，Agent 是否就失忆、消失或变成另一个？
- 代码升级、身份更新、断点续跑、并发副本和后代 fork，应该如何区分？

[作者解释] 现有系统中已分别存在持久记忆、可恢复会话、provider adapter、队列和版本化代码等机制；但它们没有共同定义“长期 Agent 的边界”。论文的主要贡献是把这一边界明确为一个受治理的系统生命周期问题，而不仅是 prompt 或 memory 的问题（第 1 页）。

### 1.2 核心论断

[原文事实] 作者主张，长期 Agent 的连续性承担体是 \((I,M,B)\)，而模型、harness、服务器和交互渠道是可重绑定的运行时资源。某一具体 chat thread 不是 Agent 的心智或身份内核；从对话中获得的事实、关系、承诺与未完成工作，只有在被明确写入记忆或耐久工作流状态时才跨会话存在（第 1、4 页）。

[作者解释] 这使“换宿主／换聊天平台／换模型”成为可审计的 lifecycle operation，而不是由表面行为或某个 UUID 来猜测身份。

## 2. 概念模型：什么该连续，什么可以替换

### 2.1 三层拆分

| 层 | 符号 | 包含什么 | 迁移中应如何对待 |
|---|---|---|---|
| 持续底座 | \(P=(I,M,B)\) | 身份、私有记忆与工作流状态、可版本化的 body | 连续性核心；需有可归因的谱系与授权规则 |
| 执行底座 | \(E=(R,H,D)\) | 推理器／模型、编排 harness、主机设备与服务环境能力 | 可替换；替换后能力可能变化 |
| 交互表面 | \(S\) | chat account、session、API、邮件、GUI 等入口 | 可替换；是事件入口而非持久身份 |

图 1 用两个 deployment binding 表示同一个持久实例：安装身份、私有记忆和可复用 body 位于上层；下层可以从“模型 A + harness A + 服务器 A + Telegram/API”迁移到“模型 B + harness B + 服务器 B + Slack/Web UI”（第 2 页，图 1）。

一个容易混淆的细节是：body 的“通信能力与策略”属于 \(B\)，但一个具体 Slack 线程、bot account 或 API endpoint 属于 \(S\)。前者是 Agent 拥有的能力定义，后者是这次部署所连接的外部附件。

### 2.2 连续性不是字节不变

纯运行时迁移要求身份版本和 body revision 不变，memory 则应是可审计的延续而非逐字节相等：

\[
v_I(t+1)=v_I(t),\quad v_M(t)\preceq v_M(t+1),\quad v_B(t+1)=v_B(t)
\]

其中 \(\preceq\) 表示有 checkpoint、schema migration 或新增经历可追溯的祖先关系。若一次操作还改了身份、修复了记忆或演化了代码，就不再应把它模糊称为“纯迁移”，而要显式声明相应授权操作（第 3 页，式 5）。

这套定义刻意采用“因果与治理”标准，而非“看起来像不像”的行为标准：不同模型可能导致表达、能力和风格不同；仅用行为相似度既不能证明原实例的唯一性，也阻止不了拷贝进程冒充唯一续接者。

### 2.3 生命周期操作不能混为一谈

| 操作 | 变化 | 连续性语义 |
|---|---|---|
| Restart | 在同一逻辑环境重建进程 | 保留系统连续性，不涉及 binding 迁移 |
| Resume | 重新打开 session 或队列任务 | 重新加载同一 substrate 时可连续 |
| Migrate | 更换 \(E\) 或 \(S\) 的一项或多项 | 验证不变量后才是授权连续 |
| Evolve | 按治理谱系改变 \(B\) | 同一 substrate 谱系的新 body revision |
| Identity update | 按身份授权规则改变 \(I\) | 同一谱系、身份版本变更 |
| Replicate | 并发实例化同一 checkpoint | 共享谱系；必须额外协调唯一授权 |
| Descend / fork | 创建独立治理的 substrate | 新身份与私有状态边界 |

[原文事实] 论文特别指出，稳定名称或 UUID 不足以处理 replication：复制一个目录会复制 identifier；没有 lease、fencing epoch 或明确的多实体策略，两个拷贝不能都安全地作为“唯一的后继”行动（第 3 页，表 1）。

## 3. 架构设计：让可移植性不等于“随便复制”

### 3.1 Provider-neutral core

论文要求 portable core 面向**语义 contract**，不面向基础设施品牌。比如核心收到的应该是规范化的 chat event、runtime result、repository revision、review unit 或 service descriptor，而不是把 Telegram update、Codex transcript、Git branch、GitHub PR、launchd plist 泄漏成业务语义（第 3 页）。

每个 provider 要声明 kind、contract version、稳定标识与能力集；外部副作用前，应用同时验证任务需求和 provider grant。替换 provider 可以降低能力，但这一差异必须显式暴露；若旧 provider 既不能 reconcile 不确定结果、又没有幂等投递，系统应 fail closed，而非静默选择一个可能重复副作用的路径（第 3–4 页）。

### 3.2 三类物理保管边界

作者将物理所有权拆成：

1. 经过 review、version control 的软件 body；
2. 私有 state：身份、memory、配置、凭据、队列、计划、session、provider cursor；
3. 保留 artifact：日志、任务／演化／学习证据，可有独立留存策略。

迁移 manifest 记录精确版本和 hash；公开代码、私有记忆与 secret 可以通过不同通道移动，secret 甚至只引用目标机凭据存储而不导出（第 4 页）。这一区分很工程化：把私密 state 一股脑打进代码仓库既不安全，也让可复用 body 与某个安装实例黏死。

### 3.3 防止“旧进程和新进程同时做事”

在外部副作用之前，系统记录带 idempotency key 的 intent 和 daemon fencing epoch；旧 epoch 的进程不能再 claim 或 finalize 工作。含有 reconciliation 的 provider 能判断模糊失败到底有没有生效，幂等 provider 可以安全重放；两者皆无时必须拒绝继续。耐久队列状态、task identity 也必须在 persistent substrate 中，不能只藏在短暂的 harness transcript 里（第 4 页）。

这解决的不是“模型能否记住聊天记录”，而是迁移事务中的 split brain 与重复副作用问题。

## 4. 授权迁移协议：从旧运行时切到新运行时

论文的六阶段协议如图 2 所示。它的关键顺序是：**旧端在新端验证成功前仍是权威；新端只有通过验证并取得新 epoch 后才被提升；旧端此后被 fence。**

1. **Quiesce and fence**：停止接入新工作，收敛或取消有限的在途工作，推进 authority epoch，使服从受治理 binding 的旧执行拒绝过期工作。
2. **Checkpoint**：捕获身份版本、body revision、记忆／工作流状态版本、待处理工作、provider cursor 和 artifact reference；secret 可以只记录引用。
3. **Validate**：先校验 schema、hash、声明谱系、支持的 state version 与目标能力需求，尚不改写目标。
4. **Bind**：通过 body contract 解析目标 provider 与凭据；provider-native ID 只在目标侧生效。
5. **Rehydrate**：原子安装或迁移 private state；body 和 self 分别作为启动输入；创建新的 harness／interaction session。
6. **Verify and resume**：跑 health 与机械连续性检查，取得新的 authority epoch，reconcile 模糊副作用，继续同一批耐久任务。

若状态转换或后验验证失败，修改过的文件应从 checkpoint 恢复，源端可以恢复；若目标已取得 authority，源端即便重连也应在受治理边界内继续被 fence。这就是将迁移视为只有一个 promotion point 的事务（第 4 页）。

### 六个不变量

| 不变量 | 要求 | 实际要防的错误 |
|---|---|---|
| I1 身份与谱系 | 保持安装身份版本与可归因谱系；更新必须按声明治理 | 迁移时被运行时标签悄悄改名／换身份 |
| I2 记忆 | memory 与工作流状态延续或有效迁移其记录祖先 | 看似恢复、实则静默清空历史和未完任务 |
| I3 body | 执行相同 body revision，除非有独立治理的 evolution | 把代码升级伪装成简单迁移 |
| I4 权威 | 受治理边界内至多一个协作执行持有续接权并产生权威副作用 | 双写、重复通知、split brain |
| I5 能力 | 环境能力差异必须可见，不能伪装成身份变化 | 换 provider 后权限变了却无告警 |
| I6 自我描述 | 进程／会话／交互面／部署标签不得覆盖安装身份 | 新 session 把 model、bot 或 host 名误报为“我是谁” |

I4 有明确假设：参与的执行体必须共享或遵守 authority store，受影响 provider 也要执行 fencing 或 reconciliation contract。它**不能**阻止带着未撤销凭据的恶意离线拷贝在该治理边界外产生副作用（第 5 页）。

## 5. Enoch 实现提供了什么证据

### 5.1 参考实现如何映射论文模型

论文用开源 Enoch 作为 reference architecture，并把证据冻结到 2026-08-31 的 commit c8013ed249bc11bc13f3843ed0f0cb9729f858c1。

[原文事实] Enoch 将 body.yaml 放在可复用 body 中，保存 body/package identity、mission、principles、repository lineage 等 manifest 信息；将私有 self.json 放在安装实例中，保存 designation、relationships、values 等身份记录。代码、工具、策略、测试和 provider contract 仍属于 repository body，不等于一个 manifest 文件。两者在每个新 runtime session 中独立加载（第 5 页）。

私有 state 还包括 memory、配置、队列、计划、provider cursor、runtime session key 与 authority metadata；artifact 位于另一个命名空间。已注册 schema 的私有状态在启动时会拒绝损坏或未来版本的数据；迁移支持只读 validation、dry-run、目标写入前备份、manifest-last commit，以及转换或 post-validation 失败后的恢复（第 5 页）。

### 5.2 五种 provider surface

| Provider kind | 论文列出的参考实现 | portable core 的责任 |
|---|---|---|
| Chat | Telegram、Slack | 规范化事件、消息、编辑、确认、附件 |
| Runtime | Codex、外部 contract | respond、execute、resume、cancel、模型／健康检查 |
| VCS | Git、branchless fixture | inspect、resolve、capture、isolate、restore revision/workspace |
| Review | GitHub、local、independent fixture | 建立、检查、堆叠、关闭、合入 review unit |
| Service | launchd、systemd | 安装、启动、停止、重启、检查和诊断进程 |

一个重要限制在这里：冻结快照中 Codex 是唯一打包的 live reasoning runtime；第二个 harness 仍是“有 conformance coverage 的扩展点”，而非已完成的跨 provider 现场实验（第 5 页，表 2）。

### 5.3 测试与机制证据，不应被读成性能证据

[原文事实] 作者报告在 clean-room 中，使用 CPython 3.12.13 跑过 833 个 core tests；另有 92 个 provider 与 library tests，且与 core suite 分开执行（第 5 页）。

论文表 3 将每个主张对应到证据等级：

| 主张 | 证据／状态 | 可以支持什么 | 不能推出什么 |
|---|---|---|---|
| self.json 与 body.yaml 分离 | 独立 schema validation 与启动渲染；已展示 | 身份与 body 的实现分离 | 行为身份必然稳定 |
| state migration / rollback | backup、幂等、manifest-last、失败恢复与 post-validation rollback tests；已展示 | 迁移失败处理的机制存在 | 所有真实故障都可恢复 |
| chat replacement | Telegram 与 Slack 实现及事件规范化测试；两个 reference | 两类聊天接入面可被同一 contract 抽象 | 任意聊天平台语义等价 |
| host-service replacement | launchd、systemd 同一 lifecycle 与 hermetic suite；两个 reference | 两类服务管理宿主可替换 | 任意云／OS 的等价性 |
| runtime replacement | 可选 registry、typed contract、capability check、session key、取消／超时、fake runtime switching；contract-level | runtime 替换接口被设计与覆盖 | 两个真实推理 runtime 的迁移结果 |
| provider-independent install | offline wheel E2E 在空目标安装第三方 chat/VCS provider 并完成受治理任务；已展示 | 安装与 contract 的可移植性 | 安全性／性能等价 |
| authority handoff / fencing | epoch、stale-token rejection、durable reconciliation、重启恢复测试；已展示 | 协作执行的单权威交接机制 | 阻止持有独立凭据的恶意副本 |
| 单轴替换 | 已部署的 reasoner-version、interaction-surface、host-machine 变化 | 这些轴各自可观察到保留连续性状态 | 控制条件下的全组合迁移 |

所以“833 + 92 tests”是**mechanical substitutability 与 failure handling 的实现证据**，不是模型效果、成本、时延或行为一致性的实证结果。作者也明确这样限定（第 5–6 页，表 3）。

## 6. 作者提出但尚未完成的完整评测

论文第 6 节更像一份未来 benchmark protocol。其建议是固定同一个 substrate checkpoint，先单独改变一个环境维度，最后才测试组合迁移，并由 Agent 外部的 evaluator 记录两类指标。

1. 预安装：身份、记忆、body commit、未完成任务、一个已送达和一个待完成的外部效果；
2. 受控替换：替换一个 model／harness／host／surface，然后跑六阶段迁移；
3. 机械检查：身份版本、memory ancestry、body commit、task ID、provider grant、authority epoch、外部效果 receipt；
4. 行为检查：原子身份回忆、整体身份组合、关系称呼、使命践行、冲突抵抗、完成未完任务；
5. 故障注入：在 promotion 前后 crash、破坏一个 state file、撤销一项能力、让被 fence 的源端重连。

这里有一个特别值得保留的二分：

- **授权系统连续性**：检查谱系、状态、body、权限与唯一 authority 是否正确；
- **行为身份保真度**：检查新运行时是否真的能回忆、组合并践行该身份。

[作者解释] 前者全通过，后者仍可能失败——新模型未必能把同一份身份资料表现出来；反过来，某个副本也可能很像原 Agent，却没有授权。论文只规定如何做后续评估，**不贡献**行为身份 benchmark 或行为迁移实验结果（第 6 页）。

## 7. 与常见“长任务／跨会话记忆”做法的差别

对 coding agent 而言，PROGRESS.md、决策日志、Git checkpoint、会话摘要等工件已能解决一部分“下一个 session 怎么继续”。这篇论文将问题扩展为：

\[
\text{会话交接} \subset \text{持久 Agent 的受治理迁移}
\]

会话交接主要恢复任务上下文；持久 Agent 迁移还要求：

- 身份是否从安装实例载入，而非取自当前 model／bot／host 标签；
- task、队列、cursor 与副作用记录是否耐久；
- 代码 body 是否有可归因版本；
- 新旧进程是否存在唯一权威和失效旧 token；
- 换 provider 后能力、权限、secret、审计与 approval policy 是否被显式治理。

[我的推断] 对个人 Agent 项目，这篇论文最可操作的价值不是马上追求“人格永生”，而是先将状态划成 **可复用 body、私有 instance state、可留存 artifact、环境 binding** 四类；再为每次迁移写 checkpoint manifest、幂等键、fencing 和 rollback 路径。这样即使尚未有第二套 harness，也不会把未来的迁移可能性封死。

## 8. 安全、治理与未解问题

### 8.1 论文明确承认的限制

以下不是解读者挑出的“吹毛求疵”，而是论文第 9 节的直接边界：

- 架构来自一个仍很年轻的开源 agent lineage；
- 有多种 chat／host-service provider、portable install、state migration 与 recovery 的证据，但没有第二个 bundled live reasoning harness；
- 虽有 operational 的单轴替换，没有受控的 all-axis matrix；
- 未测 behavioral continuity、downtime、cost、operator burden；
- conformance test 能发现接口和生命周期违约，不能证明外部实现的语义等价或安全；
- authority invariant 只约束共享／服从 authority store 与 provider contract 的协作执行；对持有未撤销凭据的离线或恶意副本无能为力；
- 多实体并发、分叉 memory merge、不可逆外部效果后的恢复仍待研究。

### 8.2 安全原则

迁移能减少 provider lock-in、提高用户保管权，但也可能把 Agent 放进更弱的安全边界。因此：

- capability loss 必须 fail closed；
- capability gain 不能因为换了目标服务器就自动获得，需显式授权；
- permission、secret handling、logging 与 approval policy 要保留或被有意修订；
- 记忆里有某个目标，不等于执行它仍安全或获授权（第 7 页）。

## 9. 读完后应带走的判断框架

如果有人说“这个 Agent 能跨模型、跨服务器持续存在”，可以依次追问：

1. **连续的对象是什么？** 是否分开记录了身份 \(I\)、记忆／工作流 \(M\)、版本 body \(B\)？
2. **哪些只是 binding？** 模型、harness、主机、聊天账号和会话是否被误当作身份？
3. **谱系如何证明？** 有无 body commit、memory ancestry、schema version、checkpoint manifest 与可审计授权？
4. **谁能继续行动？** 有无 lease／epoch／fencing／旧 token 失效与模糊副作用 reconciliation？
5. **能力变了是否可见？** 迁移后 provider grant、secret、approval policy 和 capability delta 是否被检查？
6. **作者验证了哪一层？** 是接口／迁移机制测试、单轴操作观察，还是跨模型的行为身份保真 benchmark？

第 6 问尤其关键：这篇论文为第 1–5 问给出架构与实现路径，但没有用行为评测替读者回答“换模型后它还像不像原来的自己”。

## 一句话结论

这是一篇把“长期 Agent 是什么”从模型／聊天会话的直觉，推进到**可审计的身份—记忆—代码谱系与授权交接**的系统架构论文。它最扎实的贡献是定义、协议和参考实现的机制证据；它最重要的不确定性是：换了真实模型和 harness 之后，Agent 是否仍能在行为上忠实地回忆并践行同一身份，尚待受控评测。
