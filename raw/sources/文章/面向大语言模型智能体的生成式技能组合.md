## 摘要

近期的大语言模型（LLM）智能体正受益于解决复杂任务的技能。

技能封装了程序性知识的模块化包以及执行专门任务的指令，例如建立沙盒环境、运行测试套件或跨多个文件重构函数。

随着技能库的增长并在不同任务和领域之间变得可重用，选择合适的技能组合已成为核心瓶颈。

现有的方法分为两类。

一种是将智能体的推理暴露给整个技能集合；另一种是通过嵌入或基于大语言模型的重排器进行技能检索。

这两种方法都提供了有用的见解；然而，它们忽略了技能组合的结构特性，即关于使用哪些技能、使用多少以及以什么顺序执行的联合决策——这三个维度是无法解耦延展的。

我们将此正式定义为结构化技能组合：给定一个任务和一个技能库，预测一个联合指定了激活子集、计数和执行顺序的可执行技能计划。

我们提出了 SkillComposer，它将结构化技能组合实例化为任务条件下的技能序列预测。

SkillComposer 在技能标识符上使用了一个受约束的自回归解码器，因此子集选择、计数和顺序可以从单次解码过程中共同产生，并且自然地捕获了连续技能之间的依赖关系。

我们从一个真实的、人工策划的技能库中构建了一个由“任务-组合”对组成的训练集。

然后，我们从两个轴线评估了 SkillComposer：在预留测试集上的组合质量，以及在 SkillsBench 上跨两个生产级编码智能体的下游任务成功率。

在 {GPT-5.2-Codex, Gemini-3-Pro-Preview} 上，SkillComposer 比无技能的基线分别提高了 {+23.1, +18.2} 百分点的通过率，超越了 Top-3 检索，并以更低的提示词 Token 成本达到了金标准技能检索的上限。

## 1 引言

技能库允许 LLM 智能体将程序性知识应用于复杂的任务，例如结构化文档生成、软件开发和计算机使用自动化 (Jimenez et al., 2024; Yang et al., 2024; Xie et al., 2024; Zhou et al., 2024; Trivedi et al., 2024)。

技能是程序性知识的模块化、可重用单元，例如捆绑了自然语言指令、脚本和支持资源，智能体动态地将其加载到工作上下文中以执行专门的子任务，例如协调代码审查和测试执行、生成工件或生成结构化文档 (Anthropic, 2025; Xu & Yan, 2026; Jiang et al., 2026)。

研究界在为各种任务整理技能方面取得了实质性进展 (Wang et al., 2023; 2026; Xia et al., 2026; Li et al., 2025; Jiao et al., 2026; Yue et al., 2025; Liu et al., 2026a)，推动了技能库规模的快速增长。

这使得推理时间的瓶颈从获取技能转移到了组合正确的技能集合上：为了提高任务性能，智能体必须决定加载哪些技能、加载多少以及应该以什么顺序使用它们。

当前选择性使用技能的方法主要属于两种范式。

检索方法使用大语言模型作为裁判（LLM-as-a-judge）或任务-技能嵌入相似度来独立对技能进行排序 (Zheng et al., 2026; Su et al., 2026; Li et al., 2025)，而端到端规划方法则将整个技能库暴露给智能体，智能体需要在处理输入任务的同时进行推理以触发适当的技能 (Wang et al., 2023; Yao et al., 2023; Schick et al., 2023; Xia et al., 2026)。

当任务能够清晰地映射到单个主导技能时，这些接口是足够的，但在组合任务中，它们让重要的结构性要素保持在隐式状态。

例如，考虑一个请求：“定位一个已弃用的 API 调用，在整个代码库中重构它，并运行回归测试套件。”

一个有用的计划应该首先识别相关的调用位置，然后应用重构，最后运行测试来验证更改。

检索可以表面上提供用于搜索、编辑和测试的单独相关技能，但仅凭排序列表无法指定应该使用多少个技能，或者它们应该以什么顺序执行。

我们将结构化技能组合表述为任务条件下的技能序列预测。

给定一个任务描述 $x\in\mathcal{X}$、一个环境上下文 $c\in\mathcal{C}$ 和一个技能库 $\mathcal{S}=\{s_{1},...,s_{K}\}$，模型预测一个以停止符号（STOP）结尾的有序技能标识符序列。

我们提出了 SkillComposer，这是一个生成式框架，它在现有库技能上使用受约束的自回归解码器，其中子集选择、技能计数预测和技能排序从单次解码过程中共同产生。

因为每个预测都以任务、技能库和先前选择的技能为条件，所以 SkillComposer 可以捕获连续技能之间的依赖关系，而无需在推理时指定显式的执行顺序。

此外，输出词表是有效的技能标识符，预测的计划是可检查的，并且可以直接加载到下游智能体中。

为了构建 SkillComposer，我们建立了一个基于真实、人工策划的技能库的任务-技能组合对数据集。

从 SkillsBench (Li et al., 2026) 的真实任务-技能组合种子出发，我们利用技能元数据和观察到的工作流共现构建了一个技能依赖图。

然后，我们使用分层合成和过滤来获得单技能落地和多技能组合的监督信号。

这种构建旨在覆盖长尾的单个技能和感知依赖的技能链，同时将输出空间绑定到库中的可执行技能。

我们从两个互补的轴线评估了 SkillComposer。

首先，我们在来自合成数据和预留真实数据的评估集上测量组合质量，测试预测的计划是否与目标技能子集、计数和顺序相匹配。

其次，我们测量了 SkillsBench 上跨两个生产级编码智能体（GPT-5.2-Codex，Gemini-3-Pro-Preview）的下游任务成功率，以测试更好的技能计划是否能转化为更好的智能体执行效果。

我们的主要贡献是：

* 我们将大语言模型智能体在推理时的技能使用正式定义为固定技能库上的结构化预测问题，其中输出计划共同决定了激活哪些技能、需要多少个技能以及它们应该以什么顺序执行。
* 我们构建了一个基于真实、人工策划的技能库的数据集。从真实的“任务-组合”种子出发，我们构建了一个技能依赖图，并使用带有质量过滤的分层合成来获取单技能和多技能依赖感知组合的监督信号。
* 我们提出了 SkillComposer，这是一个任务条件下的技能序列预测器，具有在技能标识符上受约束的自回归解码器。SkillComposer 将子集选择、基数预测和排序统一到单个解码过程中，同时确保生成的每个元素都对应于一个可执行的库技能。
* 我们我们在组合质量和下游任务成功率上跨两个生产级编码智能体评估了 SkillComposer。在 {Codex, Gemini} 上，SkillComposer 比无技能基线分别提高了 {+23.1, +18.2} 百分点的 SkillsBench 通过率，超越了检索方法，并以更低的提示词 Token 成本达到了金标准技能检索的上限。

## 2 相关工作

**技能库与发现**：越来越多的一系列工作为 LLM 智能体配备了可在部署时检索的可重用技能或工具 (Wang et al., 2023; Yuan et al., 2023; Qian et al., 2023; Ma et al., 2025)。

虽然 these 方法展示了维护技能库存的明显好处，但它们在选择时都采用了扁平检索，通过嵌入相似度独立对技能进行排序，而没有考虑需要多少个技能或者它们之间如何相互依赖。

相比之下，我们的工作将精心整理的技能库视为给定条件，并解决结构化组合的互补问题：联合预测技能子集、技能数量和执行顺序。

近期的工作进一步验证了基于技能的智能体设计在检索与重排路由、检索增强的技能使用、基准测试、生命周期分类法、基于强化学习的技能构建以及现实检索条件下的分析中日益增长的重要性 (Zheng et al., 2026; Li et al., 2025; Liu et al., 2026a; Su et al., 2026; Li et al., 2026; Jiang et al., 2026; Xia et al., 2026; Liu et al., 2026b)。

这些努力中没有一个将技能选择建模为具有显式基数和排序决策的闭词表序列生成。

**工具级规划与组合**：一条平行的研究主线在原子函数调用级别上对工具或 API 动作空间进行规划，将选择和排序视为分解、搜索、图评估、词表嵌入或图结构规划 (Shen et al., 2023; Zhuang et al., 2023; Shen et al., 2024; Hao et al., 2023; Wu et al., 2024)。

尽管这些系统也推导了步骤间的依赖关系，但它们在 API 调用级别运行，其中类型签名和返回值提供了用于选择和排序的强结构化信号。

我们的工作在更粗粒度的技能级别上运行，其中每个技能封装了一个跨越多个 API 调用的可重用多步程序（例如，“模式落地”或“查询重构”），这种转变带来了 API 级别方法未曾面临的挑战：技能缺乏类型签名，因此依赖关系是潜在的、任务逻辑驱动的，而非类型引导的；同时，目录虽小但高度互动，甚至调换或重新排序两个技能都会颠覆任务结果。

扁平相似度检索和原子动作搜索均不适用，从而促使将技能组合视为联合预测。

## 3 预备知识

遵循开放的智能体技能（Agent Skills）标准和 (Jiang et al., 2026)，智能体技能是一个可重用的程序化模块，它通过将程序化知识注入到提示词上下文中来增强智能体在推理时的行为，而无需修改模型权重。

形式上定义如下：

**定义 3.1（技能）**：我们将每个技能定义为 $s_{i}=(m_{i},C_{i},\pi_{i},T_{i},R_{i})$，其中 $m_{i}$ 是元数据（名称 + 单行描述，例如 `flood-detection` - 将水级与阈值进行比较；计算洪涝天数），$C_{i}$ 是适用条件（例如“输入包含按时间索引的水级序列和站点阈值”），$\pi_{i}$ 是程序化策略（例如“将瞬时值聚合为每日极端值，然后与行动/轻度/中度/重度级别带进行比较”），$T_{i}$ 是终止条件（例如“每个站点的 `flood_days` 计数已被写入请求的输出路径”），$R_{i}$ 是一个可选的可调用接口或支持资源（例如“一个 Python 助手、一个 REST 端点如 USGS 数据检索 API，或一个捆绑的查找表”）。

与工具（原子 API 调用）、计划（短暂的任务特定推理）和提示词模板（没有适用性门慢的静态文本）不同，技能编码了跨任务和会话持久存在的、可重用的程序化知识。

我们进一步定义技能库如下：

**定义 3.2（技能库）**：令 $\mathcal{S}=(s_{1},...,s_{K})$ 表示一个包含 K 个可重用技能的技能库。每个技能 $s_{i}$ 都会暴露元数据 $m_{i}$，以便在运行时通过渐进式披露进行发现：智能体在启动时加载紧凑的元数据，并根据需要激活完整的指令。

我们在训练时将 $\mathcal{S}$ 视为固定的，因为现实中的智能体部署附带的是精心整理的技能包，而不是开放式的技能生成 (Li et al., 2026), 从而将组合问题与正交的技能创建问题隔离开来。

基于这些，我们可以表述我们的问题：

**定义 3.3（任务条件下的技能序列预测）**：给定一个任务描述 $x\in\mathcal{X}$、一个环境上下文 $c\in\mathcal{C}$ 和一个技能库 $\mathcal{S}=\{s_{1},...,s_{K}\}$，我们将技能组合表述为任务条件下的技能序列预测。

一个参数化模型 $f_{\theta}$ 预测一个可变长度的技能索引序列：
$$\hat{z}=(\hat{z}_{1},\hat{z}_{2},...,\hat{z}_{\hat{n}},STOP)=f_{\theta}(x,c,\mathcal{S})$$

其中 $\theta$ 是可学习的参数，每个 $\hat{z}_{t}\in\{1,...,K\}$ 索引 $\mathcal{S}$ 中的一个技能，而 STOP 是一个特殊的序列结束符号，表示终止。

预测的技能数量 $\hat{n}$ 由 STOP 的位置决定。

然后通过索引查找恢复预测的技能序列：$\hat{s}=(s_{\hat{z}_{1}},s_{\hat{z}_{2}},...,s_{\hat{z}_{n}})$。

该预测联合解决了三个耦合的维度：（1）子集选择 —— 哪些技能是相关的；（2）技能计数 —— 需要多少个技能（取决于任务，不是固定或预定义的）；以及（3）排序 —— 应以何种序列组合所选技能。

在推理时，解析后的技能 s 按照预测的顺序加载到智能体的上下文中，为下游执行提供程序化指导。

## 4 SkillComposer: Generative Composition of Skill Sequences
## 4 SkillComposer：技能序列的生成式组合

### 4.1 概述

受到近期将检索和工具选择构建为在闭合词表上生成的启发 (Rajput et al., 2023; Hao et al., 2023)，我们将每个库索引 $i\in\{1,...,K\}$ 视为一个小型任务条件解码器的原始输出 Token，并用 STOP 标记序列终止。

这个单一的序列模型联合解决了第 3 节中确定的三个耦合维度：哪些技能（子集选择）、多少个（技能计数）以及以什么顺序（程序化排序）。

以图 2 中的洪涝分析任务为例，技能组合模型读取任务 x、环境 c（密歇根州站点文件）和紧凑的元数据 $\{m_{i}\}_{i=1}^{K}$，并发出索引序列 (104, 184, 55, STOP)。

索引查找恢复了有序的计划 $\hat{s}=(s_{104},s_{184},s_{55})=$ (nws-flood-thresholds, usgs-data-download, flood-detection)。

SkillComposer 包含三个组件，如图 3 所示：（i）一个冻结的文本编码器，将序列化的提示词 $P(x,c,\mathcal{S})$ 映射为稠密的任务表示；（ii）一个带有辅助基数和集合成员资格头的受约束自回归解码器；以及（iii）一个将词法相似度先验融合到技能 Logits 中的检索增强解码步骤。

我们接下来依次描述这三个组件。

### 4.2 任务条件组合器

**技能 Token 化**：我们首先通过其整数索引 $i\in\{1,...,K\}$ 对每个库技能 $s_{i}$ 进行 Token化，产生输出词表 $\mathcal{V}=\{1,...,K\}\cup\{STOP\}$。

在预测过程中仅消耗紧凑的元数据 $m_{i}$；完整的程序化策略 $\pi_{i}$ 和资源 $R_{i}$ 只有在 s 被解析后才会被激活，这镜像了技能库中的渐进式披露。

**任务编码器**：一个冻结的预训练文本编码器 $E_{\phi}$ 将序列化的提示词 $P(x,c,\mathcal{S})$ 映射为一个聚合的任务向量 $h=W_{proj}h_{x}\in\mathbb{R}^{d}$。

我们将 $E_{\phi}$ 实例化为 Qwen3-Embedding-0.6B（最后一词聚合，输出维度 1024）并投影到 $d=256$。

编码器参数是冻结的。

投影矩阵 $W_{proj}$、解码器参数 $\theta$ 以及辅助头参数 $\psi$, $\xi$ 参与训练。

**自回归解码器**：一个轻量级的 Transformer 解码器 $D_{\theta}$ 预测每个 Token，其条件为投影后的任务向量和所有先前生成的 Token $\hat{z}_{<t}:=(\hat{z}_{1},...,\hat{z}_{t-1})$：
$$p_{\theta}(z|x,c,\mathcal{S})=\prod_{t=1}^{n+1}p_{\theta}(z_{t}|h,z_{<t})$$

我们将 $D_{\theta}$ 实例化为一个 3 层、256 维的 Transformer，带有 4 个注意力头。

技能 $s_{i}$ 通过对投影元数据嵌入的交叉注意力呈现给解码器，以便解码器通过其自然语言描述而不是仅凭其索引来区分 K 个候选技能。

**通过辅助头进行因式分解监督**：自回归（AR）头对第 4.1 节中确定的技能组合三个维度的联合分布进行建模：使用哪些技能、使用多少以及以什么顺序。

这种联合表述对于排序是可取的，因为以 $\hat{z}_{<t}$ 为条件至关重要，打散了其余两个维度可用的监督信号：整个长度信号仅由单个 STOP 位置承载，并且对相关技能的正向监督仅出现在其真实位置。

模型无法接收到与位置无关的、表明该技能相关的顺序无关信号。

因此，我们为其余的两个维度分别配备了一个任务条件的辅助头，每个头连接到任务向量 $h_{x}$，并与序列损失联合训练。

AR 头保持对排序的责任，而基数和集合成员资格拥有专用的监督通道，并且在推理时也可以重用作解码先验。

**基数头（预测多少个）**：$h_{x}$ 上的一个线性分类器直接预测技能计数 $\hat{n}\in\{1,...,N_{max}\}$（我们设置 $N_{max}=8$）：
$$p_{\psi}(\hat{n}|x,c)=softmax(W_{n}h)$$

从而产生一个独立于 AR 头发出 STOP 的长度信号，可用于软性偏置或硬性截断解码。

**集合头（预测哪些技能）**：一个成对匹配器 $g_{\xi}$ 独立地为每个库技能 $s_{i}$ 针对任务向量进行打分：
$$\sigma_{i}=g_{\xi}(h,e_{i})=MLP_{\xi}([h;e_{i};h\odot e_{i};|h-e_{i}|])$$

其中 $e_{i}=W_{m}E_{\phi}(m_{i})\in\mathbb{R}^{d}$ 是 $s_{i}$ 的投影元数据嵌入，四个拼接项捕获了任务与技能之间的恒等性、相互作用和距离。

$MLP_{\xi}$ 是一个 2 层 MLP，隐藏层宽度为 256，输出单个 Logit。

监督信号是针对真实成员资格指示函数 $\mathbb{I}[s_{i}\in\hat{s}]$ 的二元交叉熵，因此每个相关技能都会收到一个直接的梯度，与其在 z 中的位置无关。

### 4.3 检索增强解码

自回归解码器产生一个上下文预测，该预测将每一步都以先前解码的输出为条件，通过稠密向量 $h_{x}$ 和学习到的技能嵌入路由所有任务信息。

除了这个上下文通道之外，技能的两个结构特性促使引入额外的推理时先验。

首先，技能库是重尾分布的：许多技能仅出现在一两个训练任务中（第 5.1 节）。

学习到的表示在区分它们方面的信号较弱，而检索分数则利用了整个技能库语料库，并且不需要针对每个技能的训练数据。

其次，技能词表结构使得这种推理时先验几乎是免费的：每个输出索引对应于一个固定的元数据文档，因此任何“任务-技能”相关性打分器都可以为每个任务预先计算一次，并在所有解码步骤中重用，而无需修改解码器。

因此，我们用第二个独立于位置的通道来补充上下文通道，该通道对每个库技能与任务的独立语义相关性进行打分：即技能 $s_{i}$ 凭其自身价值与 (x, c) 的匹配程度。

结合起来，解码器捕获上下文排序，而检索先验贡献了上下文通道不擅长表达的“任务-技能”语义证据。

**任务-技能相关性先验**：对于每个库技能 $s_{i}$，令 $r(x,s_{i})\in\mathbb{R}$ 表示由现成检索器 r 生成的“任务-技能”相关性分数，该检索器以任务文本为查询，以技能元数据为文档。

我们将 r 实例化为在从库构建的一元词-二元词词表上的 TF-IDF 余弦相似度；第 5.5 节报告了将此选择与 BM25 和稠密 Qwen3-Embedding 余弦相似度进行对比的消融实验。

分数 $\{r(x,s_{i})\}_{i=1}^{K}$ 为每个任务预先计算一次，并在每个解码步骤以微不足道的成本重用，因为每个输出索引对应固定的技能元数据。

**解码时的 Logit 融合**：在每个解码步骤 t，技能索引 $i\in\{1,...,K\}$ 的原始解码器 logit $l_{t}(i)$ 被替换为融合后的 logit，其中 $\overline{r}_{i}$ 是归一化或校准后的检索分数。
$$l_{\text{fused logit}}(i) = l_{t}(i) + \alpha \overline{r}_{i} + \beta \sigma_{i}, \quad i \in \{1, ..., K\}$$

带有在验证集 F1 上调整的固定标量 $\alpha, \beta\ge0$（我们使用 $\alpha=1.0$, $\beta=0.5$）；第 5.5 节报告了对这些权重的敏感性分析，其中表面在工作点周围是平滑且呈碗状的。

我们不直接在 STOP Logit 上添加检索或成员资格先验。

因此，终止主要由 AR 的 stop logit 控制，并且在起作用时也受到基数先验的控制。

融合后的 Logits $\tilde{l}_{t}$ 随后照常传递给 Softmax 和束搜索。

总而言之，SkillComposer 在每个解码步骤产生三个可解释的信号：取决于前缀 $\tilde{z}_{<t}$ 的上下文项 $l_{t}(i)$、独立于位置的语义相关性分数 $r(x,c,s_{i})$，以及学习到的、与顺序无关的技能感知成员资格先验 $\sigma_{i}$。

## 5 实验

### 5.1 实现细节

**数据整理**：我们在随 SkillsBench (Li et al., 2026) 发布的精心整理的技能库上收集了 9,872 条“任务-技能序列”训练记录，并根据排序依据将其组织为三组。

真实锚点是来自 SkillsBench 的 65 个由人类编写的软件工程任务，并配有金标准技能标注；每个任务的顺序尽可能从智能体轨迹日志中恢复，否则通过 Gemini 2.5 Pro 备用方案恢复。

单技能合成任务（2,880条记录，由 Gemini 2.5 Flash 合成）均匀覆盖所有 196 个技能，并校准组合器在面对简单查询时在单个技能后终止。

多技能合成任务（6,927条记录，由 Gemini 2.5 Pro 合成）覆盖 2-5 个技能的组合，具有两个互补的排序依据：依赖边（上游技能的输出类型与下游技能的输入类型重叠，编码硬性数据流排序）和工作流边（从真实锚点轨迹中的技能共现中挖掘，在不存在共享输入/输出类型时编码经验排序）。

两种边类型均从一个 196 节点的技能依赖图中采样。

完整语料库按 90% 划分为训练集，验证集和测试集各占 5%。

合成提示词、技能依赖图以及去重和有效性检查流水线参见附录 B。

**Model implementation.** 如第 4 节所述，SkillComposer 将一个冻结的编码器与一个轻量级的任务条件解码器配对。

我们对比了两种编码器骨干：因果语言模型（Qwen3-0.6B-Base，平均聚合）和经过检索微调的稠密嵌入模型（Qwen3-Embedding-0.6B，最后一词聚合）。

解码器是一个 3 层的 Pre-Norm Transformer，隐藏层宽度为 256，有 4 个注意力头，Dropout 为 0.1，并带有对 196 行技能内存的交叉注意力；输出词表是闭合的库加上 STOP、START 和 PAD。

在序列损失上共同训练两个 Logit 融合先验，权重分别为 $\alpha=0.5$ 和 $\beta=0.25$。

训练使用 AdamW（学习率 $1\times10^{-4}$，权重衰减 0.01，Batch 大小 64），最多进行 100 个 Epoch，并在验证集 Set F1 上使用 Patience-15 的早停机制。

在推理时，我们运行一个宽度为 4、长度惩罚为 0.7 且带有重复技能约束的束搜索，将 TF-IDF 检索先验和集合头分数融合到每一步的解码器 Logits 中（仅针对库索引）。

词法和集合融合权重，以及吸收了合成与真实基数偏差的每个划分停止偏置，都是通过在验证划分上进行坐标上升来选择的。

### 5.2 实验设置

**技能组合评估**：我们在两个共享数据组合幕后但预留子集不同的方案下评估 SkillComposer，以隔离同分布上限与真实任务迁移效果。

SkillsBench 提供了包含 196 个技能的技能库，配有 65 个真实任务以及基于图的合成语料库，所有这些都与基于 Harbor 评估框架构建的确定性验证器配对 (Harbor Framework Team, 2026)。

**同分布测试** $(n=494)$：当训练集和测试集来自同一个生成器时测量上限。

**真实任务预留** $(n=65)$：从训练和验证中删除每个真实任务，仅在合成数据上训练 SkillComposer 和基线方法，并在 65 个预留的真实任务上进行测试。

**基线方法**：我们将 SkillComposer 与三类基线进行对比，所有基线都从相同的闭合库中预测一个包含 $\le8$ 个技能名称的有序列表。

检索基线包括 BM25、TF-IDF 余弦相似度和 Qwen3-Embedding-0.6B；对于每种方法，我们报告了验证集调整的 k 变体（best-k）和给定金标准列表长度的 oracle-k 变体，从而将选择质量与基数预测隔离开来。

大模型裁判 (Gemini-2.5-flash) 是一个前沿 API 基线，它在填满了技能名称和元数据系统的单个提示词中对所有 196 个技能进行打分，直接返回有序的候选短表；模型同时选择使用哪些技能以及使用多少。

SFT Qwen3-0.6B-Base 微调了完整的 600M 骨干，以文本形式生成有序的技能序列，将 196 个技能名称作为特殊 Token 添加到分词器中，且贪婪解码在训练好的 EOS 类别处停止。

**评估指标**：我们报告了 5 个用于衡量技能预测质量的指标，涵盖选择和排序，并在图 4 中单独报告基数校准。

Set F1 是预测和金标准技能集之间与顺序无关的 F1 值，在单个数字中同时捕获了选择质量和基数校准。

Recall@5 衡量前 5 个预测中金标准技能的覆盖率，将选择与基数解耦。

MRR 是第一个命中金标准技能的预测的倒数排名。

nDCG@5 通过带对数折扣的二元相关性对前 5 的排序进行分级。

Set EM 是与顺序无关的精确匹配率。

对于下游任务性能，我们报告通过率、归一化收益和 Codex 输入提示词 Token 数（第 5 节）。

**任务性能评估**：为了验证更好的技能预测能转化为智能体执行收益，我们在 88 个 SkillsBench 任务中的 75 个上评估了下游任务性能 (Li et al., 2026)，排除了 13 个由办公和文档处理组成的任务，这些任务主要由 Anthropic 捆绑的格式技能（pdf, xlsx, pptx, docx）主导，任何检索器都可以通过文件扩展名微不足道地对其进行路由，因此无法区分技能加载方法。

我们使用两个生产级编码智能体进行评估：GPT-5.2-Codex（通过 Azure OpenAI）和 Gemini-3-Pro-Preview（通过 Gemini CLI）。

每个智能体都在 Harbor 评估框架内运行 (Harbor Framework Team, 2026)，带有确定性的 pytest 验证器 and a 1200 秒的超时；我们在 Temperature 为 0 下每个任务运行 3 次尝试（每个智能体条件 225 次试验），并按照 SkillsBench 协议报告二元通过率。

我们还报告了每个未出错试验的平均输入提示词 Token 数，以此作为上下文开销的衡量标准。

我们将 SkillComposer 与四种技能条件进行了比较：无技能（没有程序化上下文）、全部技能（将整个 196 个技能的库注入提示词）、检索 (top-3)（来自 Qwen3-Embedding）和检索 (oracle)（检索限制在金标准技能集中），并以金标准技能（策划的任务特定 oracle）作为上限。

### 5.3 技能预测质量

**SkillComposer 以极少的参数成本在同分布测试中胜出**：在合成测试中（表 1 左侧），SkillComposer 领先 SFT $+2.8$ 百分点的 Set F1 和 LLM-judge $+12.9$ 百分点，同时训练的参数量减少了约 154 倍（3.9M 对比 600M）。

相同的排名也体现在 MRR 和 nDCG@5 上，即使当 SFT 可以直接将金标准序列作为文本记忆时，AR 头也能产生更清晰的列表顶部排序，而 SFT 仅在 Set EM 上保持微弱优势。

基数切片（图 4）进一步表明，SkillComposer 的优势集中在 $k=1$ 的桶中，在此处过度发出技能受到的惩罚最重，从而获得了最高的宏观平均 Set F1 值。

两种训练模型都占据了检索方法和 LLM 裁判（包括 oracle-k 检索上限）的主导地位，因为它们能够联合预测“使用哪些技能”和“使用多少”，而检索方法需要金标准计数，且 LLM 裁判在其上下文预算内无法读取完整的技能主体。

**在分布偏移下，SFT 急剧退化，而 SkillComposer 优雅降级**：在真实任务预留测试中（表 1 右侧），SFT 从合成任务到真实任务新闻丢失了 27.5 百分点，而 SkillComposer 仅丢失了 11 百分点，在完全相同的训练数据和技能库上产生了 $+19.3$ 百分点的 Set F1 差距。

在预测 k 的方法中，只有 SkillComposer 在未被告知金标准计数的情况下接近了 oracle-k 上限，并且即使面对前沿 LLM 裁判，它在 Set F1 上依然是最强的。

检索基线实际上从合成任务到真实任务有所改善，因为真实任务的措辞更接近技能描述，而 SFT 记忆了合成模板的分布，没有强健的先验可供依靠。

冻结的、经过检索微调的编码器与一个轻量级的专家解码器配对，正是反向赋予 SkillComposer 这种迁移偏差的原因。

### 5.4 下游任务性能

**技能预测质量转化为智能体执行收益**：两个智能体在不同基线上都遵循相同的模式：通过率从“无技能”爬升到“金标准技能”上限，留下了大约 $+25$ 百分点的空间供任何技能加载机制去填补。

加载整个库（All Skills）仅恢复了该空间的一小部分，同时将 Codex 提示词膨胀到了 1.27M 输入 Token，这证实了淹没上下文是远远不够的。

Retrieval (top-3) 以更小的提示词预算闭合了更大的份额，甚至连 Retrieval (oracle) 也只能与之持平，这表明剩余的提升空间是由每个任务的选择质量驱动的，而不是检索召回率。

SkillComposer 在不使用 oracle 技能标签的情况下预测了一个校准后的有序短表，在 {Codex, Gemini} 上达到了 45.3 / 44.0 的通过率，击败了两种检索基线，并达到或超过了 Retrieval (oracle)，同时在加载技能的条件下使用了最小的提示词预算（1.03M Codex tokens）。

这在两个智能体上都弥合了大约 80% 的提升空间，从而证实了组合预测（表 1）中的上游收益能转化为真正的智能体执行效果。

### 5.5 消融实验

所有消融实验均在同分布划分上进行训练和评估；进一步的消融实验和每层细分见附录 D。

**超参数敏感性与计算-准确率前沿面**：图 5(a) 在 $6\times6$ 网格上对解码权重 $(\alpha,\beta)$ 进行扫描；表面是平滑且呈碗状的，验证集选择的工作点与其每个邻居的差距都在 2 百分点以内，表明没有脆弱的人工微调。

计算-准确率前沿面（图 5b）显示，SkillComposer 在训练参数减少约 154 倍、使用计算量减少约 25 倍的同时，达到或击败了 SFT，并以明显优势主导了检索方法和 LLM 裁判。

推理延迟（图 5c）与 SFT 处于同一量级，并且比基于 API 的裁判快两个数量级。

这些视角共同将 SkillComposer 定位为该基准测试中预测 k 的方法中的帕累托最优（Pareto-optimal）。

**每个组件都起到了承重作用**：表 3 消融了 SkillComposer 中的各个组件。

从单独的 AR 头开始，在训练期间添加集合成员资格头使 Set F1 提升了 $+2.5$ 百分点，每个金标准技能上与顺序无关的梯度对 AR 目标形成了补充。

在解码时，两种融合先验都是必不可少的：将集合融合偏置归零会损失 7.1 百分点，将词法检索先验归零会损失 4.6 百分点。

在推理时重用辅助头以细化 AR Logits，移除任何一个信号都会降低预测短表的质量。

**在解码先验上，稀疏检索击败了稠密检索**：表 4 对输入到每步解码器 Logits 中的检索先验进行了扫描。

TF-IDF 在 Set F1 上比稠密 Qwen3-Embedding 余弦相似度高出 $+2.5$ 百分点，比无先验高出 $+3.8$ 百分点。

闭合库暴露了 196 个简短、语法特异的技能名称；Token 级别的重叠在区分它们时具有高精准度，而稠密嵌入则在更广泛的语义上下文中进行平均，导致了过度泛化。

对于任务表示，稠密编码器仍然是正确的选择：SkillComposer 使用 Qwen3-Embedding 获得 $h_{x}$ 和 TF-IDF 作为解码时先验，结合了两者的优势。

## 6 结论

我们将技能组合正式定义为在闭合库上任务条件下的有序技能序列预测，联合解决了加载哪些技能、加载多少以及以什么顺序的问题。

SkillComposer 由一个冻结的检索微调编码器和一个轻量级的自回归解码器组成，其 Logits 在推理时融合了 TF-IDF 检索先验和集合成员资格信号。

With only ~3.9M trainable parameters, SkillComposer 在同分布测试划分上与 SFT 相当，并在预留的真实软件工程任务集上比其高出 $+19.3$ 百分点的 Set F1，同时依然是对抗检索和前沿 API 裁判中最强健的预测 k 的方法。

结果表明，对于闭合的智能体技能库，一个利用了库结构的小型专家模型比扩大通用语言模型规模是更可靠的组合器。
