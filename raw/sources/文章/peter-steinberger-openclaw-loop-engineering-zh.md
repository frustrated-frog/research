## 第一部分：旧方法与新方法

过去两年，我们一直是在一次只给代理一个任务。

你输入一个 prompt。
代理给出回应。
你来审查。
你修正错误。
你再写下一次 prompt。

你自己，就是那个循环。

但这件事正在改变。

以前你会让代理去做一个落地页，然后每一步都自己盯着推进。

现在你会搭建一个循环，让它自己完成发现问题、规划、执行、检查和迭代，直到目标达成。

区别在这里：

旧方式（prompting）：

你 → Prompt → 代理 → 输出 → 你来审查 → 你来修正 → 重复

新方式（looping）：

你设定目标 → 循环运行 → 代理发现问题 → 规划 → 执行 → 验证 → 迭代 → 完成

你不再为每一步亲自写 prompt。

代理会替你反复完成整个循环。

Prompt 给代理的是指令。
Loop 给代理的是工作。

## 第二部分：Loop Engineering 到底是什么

Loop Engineering（循环工程）本质上是在设计一种可重复的反馈循环，让 AI 代理能够从“尝试”走到“经过验证的结果”，而不需要人类持续不断地介入。

循环是一种你搭建出来的机制。

几乎任何代理框架都可以运行它。

区别只在于你怎么把它连起来。

最简单的情况下，一个代理可以对自己的工作不断迭代：

→ 研究  
→ 起草  
→ 对照目标检查草稿  
→ 修补薄弱环节  
→ 再次运行这个循环，直到结果满足要求

每一个循环，不管简单还是复杂，都会经过相同的 5 个阶段：

DISCOVER → PLAN → EXECUTE → VERIFY → ITERATE

验证通过 → 交付。  
验证失败 → 再循环一轮。

这就是全部核心思想。

这篇文章后面讲的所有东西，本质上都只是“如何把这个循环搭对”。

## 第三部分：单代理循环 vs 代理集群循环

循环有两种规模。

### 单代理循环

一个代理独自跑完整个循环。

你可以把它想成一个人自己反复修改自己的草稿。

它会自己发现需求、规划工作、执行、验证质量，如果发现问题就继续迭代。

适合：

→ 聚焦型任务  
→ 简单目标  
→ 范围有限的问题

一个脑子。一个循环。自我改进。

━━━

### 代理集群循环

更大的版本，是由一组代理组成的循环。

你把目标交给一个总控代理（orchestrator）。

它把目标拆成若干部分。

再把每一部分交给对应的专家代理。

这些专家代理还会继续把更小的任务派给自己的子代理。

整棵代理树会不断在“发现、规划、执行、验证”之间循环，直到目标达成。

你可以把它想成一整个团队在端到端地推进一个项目。

结构通常是这样：

→ 总控代理负责总目标  
→ 专家代理负责各个步骤  
→ 子代理负责更窄、更具体的工作  
→ 评估闸门（eval gates）负责防止输出变成一堆粗糙垃圾

例子：“做一个效率工具 App”

Orchestrator（负责总体任务）  
    ↓                             ↓                      ↓  
Research       Engineering           QA  
Specialist        Specialist         Specialist  
  ↓                                ↓                       ↓  
Web                  Code Writer      Test Writer  
Researcher   + Debugger    + Bug Tracker

这棵树里的每个代理，跑的其实都是同一个 5 阶段循环：

Discover → Plan → Execute → Verify → Iterate

最重要的区别是：

单代理循环，像是一个人自己反复修改自己的草稿。  
代理集群循环，像是一整个团队端到端地推动项目。

## 第四部分：开放循环 vs 封闭循环

这是 2026 年最重要、也最实用的区分：

并不是所有循环都一样。

循环有两种。

### 开放循环

探索性强，行动空间大。

你给代理一个目标，然后让它自己到处探索。

它可以尝试不同路径、发现新信息，甚至做出你一开始根本没完全定义出来的东西。

这是最令人兴奋的一端。
也是 Peter Steinberger 和 OpenAI 其他人正在做的方向。

但问题是：

它会烧掉惊人的 token。

对于没有无限 API 预算的那 90% 人来说，开放循环现在还不现实。

如果你把它对准那些标准模糊的项目，它很容易变成一个“粗糙产物制造机”。

快、乱、贵。

### 封闭循环

边界明确。
由人先把端到端路径设计好。

→ 目标清晰  
→ 步骤明确  
→ 每一步都有评估  
→ 知道何时停止，或何时交还给你

代理仍然会循环，但它是在你搭好的框架里循环。

每一轮的结果都会喂给下一轮，所以每次运行都会更好。

因为路径足够收敛，它可以在普通预算下运行。

标准明确，也能防止它跑偏。

没有质量闸门：AI 会漂。  
有了质量闸门：AI 才会进步。

对于今天的大多数真实工作来说，真正值得投入的是封闭循环。

那你该选哪一种？

先从封闭循环开始。

先搭出一个可靠、收敛、能稳定运行的系统。

等你有了质量闸门，再逐步把它放开。

## 第五部分：一个好循环必备的 6 个构件

任何一个真正能运转起来的循环，都离不开下面这 6 样东西。

现在进入最实操的部分。

从概念上说，循环有 5 个阶段。

但在工程上，你到底要搭哪些东西，它才能真的跑起来？

答案是 6 个。

Claude Code 和 Codex 现在都已经把这些能力配齐了。

下面就是它们，以及它们在循环里真正扮演的角色。

### 1. Automations（自动化）

这是触发 DISCOVER、把整个循环启动起来的东西。

它是循环的心跳。

自动化之所以重要，是因为它让循环变成真正的“循环”，而不只是你手动跑过一次的东西。

你定义一个 prompt、一个节奏、一个目标。

循环就会按计划运行。
发现的结果会主动回到你这里。
你不需要自己反复去盯。

→ `/loop` 会按固定节奏重复运行  
→ `/goal` 会一直跑，直到你定义的条件真的成立

比如你给它：

“`test/auth` 里的所有测试都通过，而且 lint 全部干净。”

然后你就可以离开了。

### 2. Worktrees（工作树）

这是让多个 EXECUTE 阶段可以并行运行、而又互不破坏的关键。

并行代理，但不制造混乱。

你一旦同时跑多个代理，文件冲突马上就来了。

两个代理同时改同一个文件，本质上和两个工程师没打招呼就同时改同一段代码是一样的问题。

Git worktree 会给每个代理一个独立的工作目录和分支。

仓库历史相同，但完全隔离，零冲突。

一个代理的修改，物理上就碰不到另一个代理的 checkout。

### 3. Skills（技能）

这是让 DISCOVER 更快的关键。

代理在开始之前，就已经了解你的项目。

不要每次都从零开始向代理解释你的项目。

一个 skill 就是一个目录，里面有一个 `SKILL.md` 文件。

它记录项目约定、构建步骤，以及那些“我们不这么做，因为以前出过事”的经验。

写一次，每一轮循环都能读。

没有 skill：
循环每一轮都得从零重新推导你的整个项目。

有了 skill：
能力会不断积累。
代理在开始前就已经懂你的项目。

例如：

→ `VISION.md`：成功应该长什么样  
→ `ARCHITECTURE.md`：技术栈和目录结构  
→ `RULES.md`：代理绝对不允许做什么

### 4. Plugins and Connectors（插件与连接器）

这是让 EXECUTE 变得“真实”的东西。

有了它，循环作用的不是只有你的文件系统，而是你真实的工作环境。

一个只能看文件系统的循环，其实是个很小的循环。

连接器（通常构建在 MCP 之上）让代理能够读取 issue tracker、查询数据库、调用预发 API、往 Slack 发消息。

这就是两种代理之间的区别：

一种代理会说：“这是修复方案。”  
另一种循环会自己开 PR、挂上 Linear 工单、等 CI 绿了以后自动去频道里通知。

而且这一切都不需要你手动介入。

### 5. Subagents（子代理）

这是让 VERIFY 变得诚实的关键。

检查的人，绝不能和生产的人是同一个代理。

让“做事的人”和“验收的人”分开。

写代码的模型，在给自己的作业打分时通常会太宽容。

第二个代理，配上不同的指令，甚至换一个模型，才能抓住第一个代理自己把自己说服过去的问题。

一个有效的分工方式通常是：

→ 一个代理负责探索  
→ 一个代理负责实现  
→ 一个代理负责对照规格进行验证

`/goal` 本质上也是这么工作的。

最后判定“循环是否完成”的，是一个全新的模型，
而不是那个实际干活的模型。

### 6. Memory（记忆）

这是让循环具备持续性的东西。

第 47 次运行里的 DISCOVER，需要知道第 1 到 46 次已经试过什么。

它是整个循环的脊柱。

可以是一份 Markdown 文件。
也可以是一块 Linear 看板。
任何存在于单次对话之外的东西都行。

模型在两次运行之间会忘记一切。

但仓库不会。

记忆文件会保存：
哪些尝试做过了，哪些通过了，哪些还没解决。

第二天早上，循环就能从今天停下来的地方继续。

听起来好像简单得不值一提。

但所有长时间运行的循环，最终都依赖它。

## 第六部分：真实的循环例子

循环在实践里长什么样？

### 编码循环

```plaintext
读取 VISION.md + ARCHITECTURE.md
↓
规划下一次变更
↓
修改代码
↓
自动运行测试
↓
如果测试失败 → 读取错误 → 修复 → 重新测试
↓
如果测试通过 → 总结改动
↓
停止
```

中间没有人参与。

代理自己写、自己测、自己修、自己验证。

━━━

### 研究循环

```plaintext
定义研究问题
↓
搜索资料来源
↓
总结发现
↓
对照来源验证说法
↓
比较互相冲突的信息
↓
综合出最终答案
↓
当置信度达到阈值时停止
```

━━━

### 内容循环

```plaintext
定义主题 + 受众 + 目标
↓
生成初稿
↓
由批评代理审阅草稿
↓
根据批评重写
↓
对照成功标准评分
↓
如果评分通过 → 发布
↓
如果评分不通过 → 继续重写
```

━━━

### 销售外联循环

```plaintext
定义 ICP（理想客户画像）
↓
找到符合画像的潜在客户
↓
补充公司信息
↓
按标准进行筛选
↓
个性化消息
↓
质量审查
↓
发送，或升级给人工处理
```

每一个循环，骨架其实都一样：

目标 → 行动 → 检查 → 修复 → 重复，直到完成。

## 第七部分：Prompt Engineer vs Loop Engineer

2026 年正在拉开的技能差距，是这个：

### Prompt Engineer

→ 追求更好的指令  
→ 核心是语言能力  
→ 更好的 prompt  
→ 带来更好的单次输出  
→ 每次运行结束后仍然需要人工审查  
→ 你自己就是反馈循环

### Loop Engineer

→ 设计更好的反馈循环  
→ 核心是软件工程能力  
→ 更好的循环  
→ 带来可靠、经过验证的结果  
→ 系统会自己运行、自己检查、自己纠错  
→ 系统本身就是反馈循环

Prompt Engineer：

“帮我写一个函数。”

Loop Engineer：

“写 → 测 → 修，直到全部变绿。”

写更好的 prompt。  
写 `VISION.md`。  
手工审查输出。  
自动化测试和审查。  
代理只跑一次。  
搭一个可重复运行的系统。  
按单次输出付费。  
按“经过验证的结果”付费。

工具还是同一批工具。

但思维方式已经完全不同。

Prompt Engineer 是向 AI 要输出。
Loop Engineer 是设计一个系统，让它自己产生“经过验证的结果”。

2026 年收入最高的 AI 工程师，不是那些能写出更漂亮英文句子的人。

而是那些能写出“控制代理如何发现问题、如何规划、如何检查自己的工作、如何判断完成”的逻辑的人。

## 结尾

这就是 Loop Engineering。

我把核心再快速总结一遍：

发生了什么变化：

→ 过去两年，我们是一项任务一项任务地给代理写 prompt  
→ 现在，我们开始设计能跑完整个循环的系统

你真正要搭的 6 样东西：

→ Automations：心跳，负责触发 discovery  
→ Worktrees：并行代理不互相撞车  
→ Skills：项目知识会在每轮运行中不断积累  
→ Plugins and connectors：循环可以操作你的真实工具  
→ Subagents：执行者和检查者绝不能是同一个代理  
→ Memory：循环不会在两次运行之间失忆

两种规模：

→ 单代理：一个脑子，自我改进  
→ 代理集群：总控 + 专家 + 子代理，而且每个代理都跑同一个循环

两种类型：

→ 开放循环：探索性强、能力大、成本高，需要无限预算  
→ 封闭循环：边界明确、稳定可靠、可负担，是今天更值得投入的方向

每个好循环的 5 个组成部分：

→ Goal：精确定义“完成”到底是什么意思  
→ Context：`VISION.md`、`ARCHITECTURE.md`、`RULES.md`  
→ Action：只给代理真正需要的行动空间  
→ Feedback：测试、类型检查、lint、结构化错误  
→ Stop condition：让循环知道自己什么时候应该结束

成本问题：

→ 循环会非常快地消耗 token  
→ 在 DeepSeek 上花 20 美元，能跑出的东西比大多数前沿模型多得多  
→ 这就移除了最后一个真正的阻碍

最大的转变：

→ Prompt Engineer 是向 AI 要输出  
→ Loop Engineer 是设计系统，让系统产出经过验证的结果

Peter Steinberger 说得很对：

别再只是给代理写 prompt。
开始设计循环。

因为一个可靠的循环，价值胜过一千个完美的 prompt。

还有一件几乎没人明说的事。

两个人可以搭出一模一样的循环，却得到完全相反的结果。

一个人用它来加速自己已经深刻理解的工作。

另一个人用它来逃避真正理解工作本身。

循环并不知道这两者的区别。

你知道。

这也是为什么循环设计并不比 prompt engineering 更简单，反而更难。

Boris Cherny 想表达的，并不是“工作变简单了”。

而是杠杆点变了。

去搭循环。
