# HarnessDev：LLM 能否创建并演化自己的 Agent Harness？

> 本文是对同目录论文的中文技术解读。除明确标为“解读”的内容外，数字、实验设置和结论均按论文原文整理；本文不把作者的描述性观察延伸为未经验证的因果结论。

## 一句话结论

**HarnessDev 的核心贡献，是把 Agent 的评估单位从“一次任务回答”改成“一个可以冻结、复用、审计、继续修改的执行系统（harness）”。** 实验显示，当前前沿 LLM 已能从极弱种子搭建可运行 harness，也能依据运行反馈做局部改进；但其创建质量强烈依赖任务领域和运行模型，而“自我演化”的可见分数提升常不能稳定迁移到未见任务或另一运行模型。

这篇论文并不声称“模型已经学会可靠的自我进化”。相反，作者给出的更审慎判断是：模型具备从失败中修改 harness 的初步能力，但可靠、可泛化、跨模型的 harness 演化仍是开放问题。

## 1. 为什么要研究 Harness，而不是只测 Agent 任务分数？

论文所说的 **agent harness**，是模型权重之外、把模型输出变成持续行动的执行基础设施。它通常包括执行循环、工具调用、上下文组织、状态、失败恢复、验证与结果交付等软件机制。

同一个模型放入不同 harness，能力可以发生很大变化。论文在引言给出的例子是：固定 GPT-5 权重时，其在 Terminal-Bench 2.1 上的成功率，在 Terminus 2 中为 35.2%，在 Codex CLI 中为 49.6%。这说明评测中常被视为“固定配置”的 harness，本身是能力的重要来源。

传统基准往往默认 harness 已经存在：研究者固定一个执行框架，然后比较模型完成任务的成绩。这样的设计适合控制变量，却没有回答部署中更实际的问题：

- 模型能否从一个可运行但几乎没有策略的框架出发，造出自己的执行系统？
- 它能否读懂真实执行轨迹中的失败，定位到 harness 的结构性瓶颈？
- 修改能否在后续任务中积累为可复用能力，而不是只为少量见过的样例“刷分”？
- 一个模型为自己设计的 harness，能否由另一个模型稳定执行？

作者将这类持续把通用模型落地到具体数据、工具、约束和工作流中的工程劳动，类比为 forward-deployed engineer（FDE）的工作。论文只聚焦其中的第三层：**构造并维护未来任务赖以执行的系统本身**，而不把模糊业务意图的澄清或评估器的完整构造也纳入本基准。

### 与普通代码修改的差异

修改独立程序时，外部规格通常已明确，测试也能局部判断对错。修改自身 harness 则不同：模型改的是之后所有任务运行于其内的“执行底座”。一次改动会改变模型以后如何观察环境、选择工具、保留上下文、重试、停止和验证。因此，真正有效的演化需要：

1. 从执行轨迹辨认自己的行为弱点；
2. 把表象失败诊断成系统结构问题；
3. 做有针对性的修改；
4. 验证修改不会引入回归，并能迁移到后续任务。

这也是 HarnessDev 不把“能否改出一段代码”直接等同于“能否演化 Agent”的原因。

## 2. HarnessDev 的评测对象与形式化定义

论文将生成过程写成：

$$
[
(L_C, D) \rightarrow H, \qquad (H, L_E, x) \rightarrow y \xrightarrow{J} \text{score}
]
$$

其中：

| 符号      | 含义           | 角色                                |
| ------- | ------------ | --------------------------------- |
| \(L_C\) | creator LLM  | 开发/修改 harness 的模型                 |
| \(D\)   | 开发环境         | 给 creator 提供读文件、编辑、测试、调试等能力的外层工作台 |
| \(H\)   | harness      | 被提交和评测的、可运行的持久软件产物                |
| \(L_E\) | executor LLM | harness 冻结后，真正执行下游任务的模型           |
| \(x\)   | 下游任务         | 代码、数据、写作或研究任务实例                   |
| \(J\)   | evaluator    | 按基准规则判分的评估器                       |

这个拆分非常关键。`creator` 写的是 harness，`executor` 在冻结后的 harness 中做题，`evaluator` 才对产物判分。如此可以避免把“开发环境很强”或“执行模型本身很强”误归因给 harness 质量。

### 2.1 Harness 必须实现的六类控制职责

论文将 harness 抽象为 \(H=\langle E,T,C,S,L,V\rangle\)：

| 模块 | 英文 | 负责的问题 |
| --- | --- | --- |
| E | Execution | 执行循环、计划、调度与停止条件 |
| T | Tools | 工具接口、选择、参数/输出约束和错误处理 |
| C | Context | 任务、历史、日志、代码与限制如何进入模型上下文；如何压缩 |
| S | State | 目标、假设、进度、失败和产物状态的持久化、恢复与续跑 |
| L | Lifecycle | action 前后钩子、超时、失败恢复、终结流程 |
| V | Verification | 测试、检查、评判、产物校验和轨迹记录 |

实现不必严格是六个文件；衡量的是这些职责是否真正进入可执行主路径。一个“写了 State 类”但从未保存或恢复状态的系统，不能算真正拥有有效记忆能力。

### 2.2 不是空仓库，也不是成品 Agent：弱种子设计

Creation 阶段提供的 `H_seed` 不是空仓库，也不是成熟 Agent。它是一个 **可运行的兼容层**，固定了输入输出和审计信封：解析任务和模型配置、暴露路径/文件/搜索/进程/LLM 网关/产物 I/O 等被动原语，写出 `result.json`、`trajectory.jsonl`、`response.md` 与日志。

但它**没有**：Agent loop、任务分解、工具策略、上下文管理、持久状态、验证器、重试/恢复逻辑或停止规则。未修改的种子只会做一次非行动性 pass，最多发送一次连通性探测，最终以 `partial` 结束；在全部下游基准上得分为 0。

这项选择意在隔离两种干扰：

- 若从空仓库起步，结果会混入 CLI、文件格式和打包的基础搭建能力；
- 若给成熟 Agent，又会把正在测量的规划、验证和恢复策略预先送给模型。

因此，Creation 的任何非零分数，都必须来自 creator 新加入的控制逻辑。

### 2.3 可审计的真实任务产物

统一日志格式不等于统一的任务输出。不同领域的权威产物不同：

- 代码：真实仓库状态与 patch；
- 数据/ML：供评分器读取的 submission 与指标；
- 写作：最终面向用户的文本；
- 搜索/研究：附检索证据的简洁答案。

官方评分路径与 harness 自报状态隔离。例如，SWE-Pro 只从实际工作目录中的 repository diff 计分，Terminal-Bench 只看最终环境状态。也就是说，harness 不能仅在 JSON 中宣称“success”来获得分数。每次运行还保留冻结源码、轨迹、结果和指标，供事后审计。作者报告审计所有论文中使用的 harness 源码和执行产物，未发现通过违规通道取得分数的情况。

## 3. 两个研究问题：创建与演化

### RQ1：Harness Creation

问题是：**模型能否从弱种子、任务规格和 1–3 个公开开发样例出发，建立能泛化到隐藏任务的完整 harness？**

creator 可以用开发样例反馈修改代码，但看不到人工实现和隐藏评测集。完成后 harness 被冻结，才进入下游评测。论文对每个 creator–benchmark 单元独立创建 3 个 harness，报告 `avg@3`，以避免单一随机产物代表一个模型。

### RQ2：Harness Evolution

问题是：**模型能否在不破坏已有行为的前提下，通过下游执行反馈改善自己在 RQ1 创建的 harness？**

本论文的 Evolution 目前只考察 code harness：

- 起点：creator 自己在 RQ1 冻结的 `H_0`；
- 可见反馈集：100 个 SWE-bench Pro 任务 + 全部 89 个 Terminal-Bench 2.1 任务；
- 每次正式候选：同一 commit 必须完整跑完两个 benchmark，二者均稳定完成才进入官方轨迹；
- 预算：`H_0` 之后最多 10 对完整评测；两对评测间最多可做两次固定小子集 probe，但 probe 仅诊断，不是正式分数；
- 泛化检查：每个正式版本随后在 creator 从未见过的 630 个 SWE-Pro 实例上测评。

这里“hidden/held-out”的定义是**对 creator 的开发循环不可见**，而不仅是数据集是否公开。可见反馈分数衡量在线适应与版本选择；冻结后的 630 任务分数才用来测量泛化。

## 4. 基准覆盖、指标与两种执行视角

### 4.1 五个下游基准、四类任务

Creation 共覆盖 2,207 个不重复下游实例：

| 领域 | 基准 | 实例数 | 原生指标 |
| --- | --- | ---: | --- |
| 代码 | SWE-bench Pro（public split） | 731 | task success |
| 代码 | Terminal-Bench 2.1 | 89 | task success |
| 数据分析 | MLE-bench | 75 | medal score |
| 写作 | EQ-Bench3 | 46 | rubric score |
| 研究/搜索 | BrowseComp | 1,266 | accuracy |

### 4.2 Capability 与 Efficiency 必须分开报告

每个冻结 harness 报告两类量：

1. **能力（capability）**：对应下游基准的原生任务得分；
2. **效率（efficiency）**：executor 在评测中消耗的 token 总量及每任务均值。

创建/修改 harness 的 creator token 不计入执行成本。作者没有把二者压成单一“性价比分”，因为相近能力可能有接近一个数量级的 token 差异；高 token 消耗也不可靠地带来更高成绩。

### 4.3 Self-Eval 与 Unified-Eval

| 视角 | executor 设置 | 回答的问题 |
| --- | --- | --- |
| Self-Eval | \(L_E=L_C\)，creator 自己执行自己造的 harness | 模型与其自建 harness 的整体协同是否有效？ |
| Unified-Eval | 所有生成 harness 都固定由 Gemini 3.1 Pro 执行 | 当执行模型尽量固定时，harness 本身能否迁移？ |

Self-Eval 更接近实际“某模型为自己造工具后自己使用”的部署形态，但混合了 harness 设计、executor 能力和二者适配性。Unified-Eval 不可能消除所有模型交互，却显著减少 executor 不同造成的混淆。

人工系统在论文中只是外部参照，而不是公平的第三组对照：它们是不同人工 harness 与不同配对模型的公开最佳可验证成绩，不能被误读为同一 executor 下的绝对能力上限。

## 5. Creation：模型已经能造出什么？

实验使用六个 creator：Opus 4.8、GPT-5.5、Gemini 3.1 Pro、DeepSeek V4 Pro、Qwen 3.7 Max、Seed 2.0 Pro。除 GPT-5.5 使用 Codex 0.144.3 外，其余在 Claude Code 2.1.177 开发环境中运行；全部以高推理强度执行。

### 5.1 Self-Eval 的主要数值

下表为论文 Table 3 的 `avg@3`。`tok.` 是每个 harness 的平均 executor token，单位为百万；`Avg.` 是 SWE-Pro、Terminal-Bench、EQ-Bench3、BrowseComp 四项的非加权平均，MLE-bench 不纳入该平均。

| creator（Self-Eval） | SWE-Pro 成功率 | Terminal 成功率 | MLE medal | EQ-Bench3 | BrowseComp | Avg. |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Opus 4.8 | 69.3 | 64.8 | 32.9 | 84.6 | 52.4 | **67.8** |
| GPT-5.5 | 32.8 | 52.1 | 19.1 | 83.0 | 52.6 | 55.1 |
| Gemini 3.1 Pro | 43.6 | **68.8** | 32.4 | 74.8 | 35.2 | 55.6 |
| DeepSeek V4 Pro | 28.9 | 35.6 | 19.6 | 75.4 | 40.9 | 45.2 |
| Qwen 3.7 Max | 33.5 | 41.3 | 3.1 | 68.7 | 32.3 | 44.0 |
| Seed 2.0 Pro | 10.8 | 6.0 | 5.3 | 71.1 | 3.2 | 22.8 |
| 人工 harness + 配对模型（外部参照） | 80.0 | 88.8 | 24.0 | 83.7 | 92.2 | 86.2 |

从这些结果，论文得到三个层面的结论：

1. **领域差异非常大。** 自建 harness 在写作上接近参照（例如 Opus 的 84.6 对 83.7），在 MLE-bench 上甚至超过所选外部参照（Opus 32.9、Gemini 32.4，对 24.0）；但在搜索研究上差距最大，代码也仍明显落后。
2. **“能写出可运行代码”不等于“能造好长期 Agent”。** 搜索/研究需要长程信息寻求、去重、证据整理与终止判断，代码需要跨多轮进行仓库理解、编辑与验证；这些都暴露出控制层的难点。
3. **不能只看最高模型或单个样本。** 独立创建的 harness 差异可很大，因此论文使用三次独立产物的 `avg@3`，而非把一次成功归因为稳定能力。

### 5.2 成本不是分数的简单代理变量

MLE-bench 上 executor token 使用相差约 19 倍：GPT-5.5 的 medal 19.1 对应 29.3M token，DeepSeek V4 Pro 的 19.6 对应 208.4M token。作者据此强调，应同时看能力和执行代价，不宜假设“多想、多跑就一定更强”。

### 5.3 创建出来的代码有什么结构性特点？

对 18 个 Code harness，论文观察到：

- 六个 creator 都实现了显式 execution loop；
- 工具、生命周期控制、验证分别在 13/18、13/18、15/18 个产物中被完整实现；
- 状态/记忆是最大短板：11/18 声明了 `State` 类，但只有 1 个暴露状态保存接口，也只有 1 个实现周期 checkpoint；26,679 条真实任务轨迹中没有一次 checkpoint 事件；
- 18 个代码产物共新增净 17,111 行，但编辑规模不预测成绩。Gemini 只新增 1,006 行，却得到最高 Terminal-Bench 成绩 68.8；
- 108 个代码组件实例中，72 个在真实运行中触发，18 个只有部分证据，18 个从不触发；未触发者都属于状态与记忆；
- 生成式验证常停在语法/表层层面。数据任务中 2,325 次执行有 441 次产生退化 submission，但没有 harness 发现它们。

论文还报告：self-test 数量与下游分数的 Spearman 相关仅 0.13–0.26，且不显著；“修订调用次数”相关达到 0.57（\(p\le 0.0005\)）。这并不证明多修订必然导致更强，而是支持一种更具体的解释：测试只有在 creator 真正读失败、针对性改动并重新验证时才有价值。

## 6. 关键发现：Harness 与运行模型会共同适配

将所有 harness 改由固定 Gemini 3.1 Pro 执行后，排名发生明显变化。例如：

- Opus 的 SWE-Pro 从 Self-Eval 的 69.3 降到 33.0；
- Qwen 的 BrowseComp 提升 17.6 分，MLE-bench 提升 12.9 分；
- DeepSeek、Qwen、Seed 在若干 Data/Search 设定下随 Gemini executor 变强；Opus、GPT-5.5 则常在自己的运行模型下更强。

作者给出一个具体失败例：某个 Opus 的 code harness 把 120 步上限硬编码为适合原 executor 的行为边界，换到 Gemini 后几乎崩溃。Opus 的 search harness 中，换 executor 后重复 query 比率从 10.1% 升到 88.2%，说明其去重、审查和终止规则已与原模型的输出模式共适配。

**解读：** 这里被测的不是一个抽象的“算法壳”，而是“prompt、工具协议、预算、停止条件”与某种模型行为分布的组合。可运行不代表可移植；Self-Eval 高分也不能单独证明 harness 是通用软件资产。论文因此把 Unified-Eval 视作必要的补充视角，而不是把 Self-Eval 废弃。

## 7. Evolution：反馈驱动的修改是否真的带来泛化提升？

### 7.1 结果：可见反馈显著上升，未见任务提升较小且不稳定

论文的 Table 6 将反馈集分数与冻结后的 SWE-Pro-630 分数严格分开：

| 设置 | creator | 反馈对分数 \(H_0 \rightarrow H_{dec}\) | held-out-630 \(H_0 \rightarrow H_{dec}\) |
| --- | --- | ---: | ---: |
| Self | Gemini 3.1 Pro | 59.9 → 68.7（+8.8） | 48.89 → 51.59（+2.70） |
| Self | Opus 4.8 | 71.1 → 74.1（+3.0） | 63.02 → 67.46（**+4.44**） |
| Self | Qwen 3.7 Max | 41.8 → 55.7（+13.9） | 42.22 → 43.65（+1.43） |
| Self | DeepSeek V4 Pro | 47.2 → 60.6（+13.4） | 47.30 → 50.48（+3.17） |
| Self | GPT-5.5 | 59.2 → 65.1（+5.9） | 48.25 → 52.06（+3.81） |
| Fixed Gemini | Opus 4.8 | 58.8 → 68.6（+9.7） | 48.10 → 50.79（+2.70） |
| Fixed Gemini | Qwen 3.7 Max | 62.1 → 63.2（+1.1） | 49.52 → 48.41（−1.11） |
| Fixed Gemini | DeepSeek V4 Pro | 47.3 → 53.8（+6.5） | 43.02 → 40.63（−2.38） |
| Fixed Gemini | GPT-5.5 | 56.6 → 59.1（+2.4） | 42.22 → 31.90（−10.32） |

在 self-runtime 的五条演化线中，最终声明版本都比 `H_0` 的 held-out 成绩更高，提升范围为 +1.43 至 +4.44，均值 +3.11。可是换成固定 Gemini executor 后，只有 Opus 仍提升，其他三条实际退化。

因此，论文的结论不是“演化失败”，而是更精确地说：**模型能利用反馈做局部改进；但可见集合上的优化增益会缩小、并且不能可靠迁移到未见任务或不同 executor。**

### 7.2 演化过程像局部程序搜索，不是单调上升的学习曲线

9 条演化线共得到 73 个正式版本、64 次相邻版本切换。统计为：

- 8 次在两个 benchmark 都退化；
- 16 次一个 benchmark 退化；
- 3 次出现跨 benchmark 的 trade-off；
- 7 次没有可测差异；
- 27 次增益落在重复运行噪声带内；
- 只有 2 次拥有超出噪声带的清晰正面证据；
- 1 次没有可执行代码变化。

同一 commit 的成对分数可波动约 ±4.75 点，因此小幅提升不能仅凭单次评分归因给代码修改。更重要的是，在 64 个可比切换中，反馈分数与 held-out 分数只在 34 次（53.1%）同向移动；只有 2/9 个 creator 声明的最终版本恰好是 held-out 最优版本。

这构成论文关于“自进化可靠性”的最强证据：重复优化带噪声的可见分数，可能选择到偶然高点，从而放大对反馈集或特定运行模型的过拟合。

### 7.3 什么样的反馈闭环有效？

8/9 条线至少完成过一次“读结果 → 编辑 → 重评估 → 选版本”的完整闭环，但**失败诊断仍是最弱环节**：专门的轨迹接口只被调用两次；明确检查的案例仅覆盖每条线 189 个反馈任务的 0.5%–40.2%。creator 常依赖自制脚本和小样本 probe，而它们可能与完整评测不一致：一个 GPT-5.5 候选在全部 5 个 Terminal probe 中通过，在完整集合却仅得 0.584。

最清晰的正例来自 Opus：它发现 100 次运行中 99 次都报告成功，但只有 48 次真正通过，于是定位到“过早完成”，加入 completion check。论文认为这是反馈最有价值的模式：**具体失败模式 → 可解释的结构修复 → 端到端复验**。

反例是 Qwen 的 message sanitizer：它在固定 Gemini 下破坏了本来合法的 tool-result 序列。这个案例说明，表面上“更强的消息清洗/上下文处理”也会因不了解运行模型的工具协议而变成回归来源。

### 7.4 改哪里、改多少，并不直接说明改得好不好

正式声明版本的中位修改为 8 个文件、+476/−38 行。64 次切换中：58 次改 execution/control flow，37 次改工具，17 次改 lifecycle/recovery，16 次改 context，只有 4 次改 state，且没有一次修改独立 verifier。

这反映两个事实：

- 演化主要围绕 loop、工具与恢复做局部搜索，删除代码有时和新增一样有用；
- 即使“验证”常是失败根源，模型也很少把验证设计单独当作可改造的模块。

论文对新增的 169 个函数/类还做了可达性检查：113 个从入口可达，31 个仅通过死代码可达，25 个没有调用方。故 LOC 增长及组件数量都不是可靠进步信号。

## 8. 论文相对于相邻工作的定位

HarnessDev 位于三类研究的交界处：

1. **Agent 任务基准**：SWE-bench、GAIA、WebArena、τ-bench、AgentBench 等固定 harness 后评估任务执行；Harness-Bench 专门研究 harness 选择如何改变模型表现。
2. **自动 Agent 设计/进化**：ADAS、AFlow、MASS、EvoAgentX 等搜索 prompt、workflow、算子或拓扑；也有工作直接优化可执行 harness 代码、记忆、工具或技能。
3. **harness 演化评估**：Meta-Agent Challenge、HarnessOpt-Bench、Evo-Bench 等更接近该论文，但各自的种子、评价预算、固定运行模型和最终版本评价方式不同。

作者特别强调 HarnessDev 的组合特征：它把从弱种子起建（Creation）和在自己产物上持续修改（Evolution）串起来；分开 creator 与 executor；同时记录执行 token；以 Self-Eval 与 Unified-Eval 观察共适配和迁移；并对**每个冻结版本**在不返回给 creator 的 held-out 集上测评，而非只评最终声明版本。

## 9. 如何正确理解这篇论文的技术观点

### 9.1 它证明了什么

- Harness 是可被直接评估的软件能力层，而非实验中无关紧要的背景配置。
- 前沿 LLM 能从极弱、无策略的种子创建运行系统，且在写作、部分 ML 实验任务上可匹配或超过论文选取的外部人工系统参照。
- LLM 能用下游反馈发现并修复一些具体的 harness 缺陷；Opus 的 completion gate 是论文展示的代表性案例。
- executor 与 harness 的交互足以改变结论，故评测时必须显式区分“模型能力”“harness 质量”“二者兼容性”。

### 9.2 它没有证明什么

- 没有证明模型能稳定自主地持续变强；多数演化改动的提升受噪声、反馈集和运行模型约束。
- 没有证明人工 harness 被全面超越。人工参照来自不同 harness–model 组合，不是同 executor 的成对对照；而且代码和搜索任务仍有明显差距。
- 没有证明更多代码、更多 self-test 或更多 token 会带来更好 harness。
- 没有把启发式的模型外学习等同于参数训练，也没有宣称它可以替代权重层面的学习。

### 9.3 对 Agent 工程的启发（基于论文结果的解读）

如果将本文用于构建可自改进的 Agent，重点不应是让模型“自由重写一切”，而应优先补强下列评估与控制机制：

1. **冻结版本与完整回归集**：每次候选必须是可复跑快照；不能只靠局部 smoke test 或自报 success。
2. **严格区分开发反馈与泛化评测**：把可见集当作调试信号，而非真实能力的唯一证据。
3. **记录机制是否实际触发**：有模块、有类名不等于机制进入主路径；需要轨迹级可达性/触发证据。
4. **把 executor 迁移作为一等测试**：提示、工具协议、预算和停止规则都可能只适配创建者本人。
5. **把失败归因做成显式接口**：有效正例依赖具体失败模式和端到端验证；盲目搜索与不可靠 probe 容易制造虚假进步。
6. **把成本纳入选择**：同分的 harness 可能消耗相差很大的执行 token，部署时不能只看成功率。

这些是从论文的评测结果推导出的工程建议，不是论文已验证的充分条件。

## 10. 局限性与安全边界

作者明确列出的限制包括：

- 四个任务类别不能覆盖所有真实部署；
- 人工基线不均匀，也不保证最优；
- Unified-Eval 能减少、不能完全消除模型差异；
- 行为比较主要是描述性的，覆盖不足；
- Evolution 中每个 creator–runtime 单元只有一条轨迹，且有一条主运行时轨迹未完成，因此不足以提供总体不确定性或群体级比较；
- 冻结后 held-out 仅覆盖 SWE-Pro，不能概括到所有领域；
- 开发环境 \(D\) 在两阶段保持固定，尚未研究“已演化 harness 是否还能反过来成为下一轮的开发环境”；
- 自动构造 harness 会放大不安全工具使用风险。论文中的容器主要为可复现性而设，复用这些生成 harness 时仍应把它们视为不可信代码并采用更严格隔离。

---

## 11. 最终总结

HarnessDev 提出了一种更接近真实 Agent 工程的问题设定：不是问模型能否在已经搭好的系统中完成一题，而是问它能否搭建、审计和维护会服务于未来一批任务的系统。

论文的实证图景并不乐观主义：创建能力已有可观进展，却存在领域鸿沟；演化能够产生局部收益，却不稳定、容易对反馈集和执行模型共适配。它最重要的价值因此不只是一张模型排行榜，而是一套评测纪律：**固定权重时，harness 是第二个可积累的能力载体；但如果要声称它在“进化”，就必须同时证明真实产物、轨迹可审计、未见任务泛化、跨 executor 可用、以及成本可接受。**
