循环工程，就是把“给智能体写提示词”的那个人换掉，也就是换掉你自己。你要设计一个系统，让这个系统来做这件事。这里的“循环”可以理解为一种递归目标：你定义一个目的，然后 AI 反复迭代，直到完成。它大致由五个构件组成，而 Claude Code 和 Codex 现在都已经具备了这五个构件。

我认为，这可能是我们未来与编程智能体协作的方式。不过，它仍然处在很早期。我对此保持怀疑，而且你绝对必须小心 token 成本（如果你的 token 很充裕或很紧张，使用模式可能会有巨大差异）。你也仍然需要某种方式来确保质量不会下降，关于“AI 垃圾产出”的担忧是合理的。话虽如此，我们还是来看看这到底是怎么回事。

@steipete 最近说：“你不应该再给编程智能体写提示词了。你应该设计那些会给你的智能体写提示词的循环。”类似地，Anthropic Claude Code 负责人 @bcherny 说：“我已经不再提示 Claude 了。我有一些循环在运行，它们会提示 Claude，并弄清楚接下来该做什么。我的工作就是写循环。”

好吧，那这些话到底是什么意思？

过去大概两年里，如果你想从一个编程智能体那里得到东西，方法就是写一个好的提示词，并提供足够的上下文。你输入一段话，阅读返回结果，再输入下一段话。智能体是一个工具，而你一直握着它，一轮接一轮地操作它。这个阶段差不多结束了，或者至少有些人认为它将要结束。

现在，你构建的是一个小系统：它会发现工作、分发工作、检查工作、记录已经完成的内容，然后决定下一步做什么。你让这个系统去推动智能体，而不是你亲自去推动它们。我之前写过与此类似的东西，叫做 agent harness engineering，也就是为单个智能体构建其运行环境；还有 factory model，也就是构建软件的系统。循环工程位于 harness 的上一层。它像一个 harness，但运行在定时器上，会生成小助手，并且会自我喂养。

让我意外的是，这其实已经不再是一个工具问题了。一年前，如果你想要一个循环，你得写一大堆 bash 脚本，并且永远维护那堆东西。那是你的东西，也只属于你。现在，这些组件已经直接内置在产品里了。Steinberger 列出的东西几乎完全对应到 Codex app 上，也几乎同样对应到 Claude Code 上。一旦你注意到它们的形状是一样的，你就不会再争论到底该用哪个工具，而是会去设计一个循环，让它无论你坐在哪个工具里都能工作。

## 五个构件，以及一些说明

一个循环需要五样东西，外加一个用来记住事情的地方。我先列出来，然后再做映射。

自动化：按照计划触发，并且自己完成发现和分诊。

Worktree：让两个并行工作的智能体不会互相踩到对方。

技能：把项目知识写下来，否则智能体只能靠猜。

插件和连接器：把智能体接入你已经在使用的工具。

子智能体：让一个智能体提出想法，让另一个智能体来检查。

然后是第六样东西：记忆。可以是一个 Markdown 文件，也可以是一个 Linear 看板，任何存在于单次对话之外、用来记录什么已经完成、下一步是什么的东西都可以。听起来蠢到不像什么重要东西。但这是每一个长时间运行的智能体都依赖的同一个技巧，我在 long-running agents 那篇里也讲过：模型会在两次运行之间忘记所有东西，所以记忆必须放在磁盘上，而不是放在上下文里。智能体会忘，代码仓库不会。

现在两个产品都已经具备这五样东西。

这些名称在不同地方略有不同，但能力其实是同一件事。让我一个一个讲，因为说实话，细节正是一个循环要么能稳住、要么悄悄到处漏水的地方。

## 自动化，这是心跳

自动化让一个循环真正成为循环，而不只是你曾经运行过的一次任务。在 Codex app 里，你可以在 Automations 标签页创建一个自动化，然后选择项目、它要运行的提示词、运行频率，以及它是在你的本地 checkout 上运行，还是在后台 worktree 上运行。那些发现了东西的运行会进入 Triage inbox；没有发现东西的运行会自动归档，这点挺好。OpenAI 内部会把它们用于一些无聊但必要的事情，比如每日 issue 分诊、总结 CI 失败、撰写 commit 简报、寻找上周某个人引入的 bug。自动化还可以调用一个 skill，所以你可以让重复发生的事情保持可维护：触发 `$skill-name`，而不是把一大堵没人会再更新的说明文字粘进一个定时任务里。

Claude Code 通过调度和 hooks 到达同样的位置。你可以用 `/loop` 按照间隔运行一个提示词或命令；你可以安排一个 cron 任务；你可以在智能体生命周期的某些节点用 hooks 触发 shell 命令；或者，如果你想让它在你合上电脑后继续运行，你可以把整套东西推到 GitHub Actions。想法完全一样：你定义一个自治任务，给它一个节奏，然后让发现结果来到你面前，这样你就不是那个到处检查的人了。

还有第二个值得了解的会话内原语，它更接近这整篇文章真正要谈的东西。`/loop` 会按照节奏重新运行。`/goal` 会持续运行，直到你写下的某个条件真正成立；而且在每一轮之后，一个独立的小模型会检查任务是否已经完成，所以写代码的那个智能体不是给它打分的那个。你给它类似“`test/auth` 里的所有测试通过，并且 lint 是干净的”这样的条件，然后就可以离开。Codex 也有同样的东西，也叫 `/goal`。它会跨轮次持续工作，直到一个可验证的停止条件成立，并且支持暂停、恢复和清除。同一个原语，两个工具都有，这基本就是整篇文章的模式。

所以，这是暴露工作的那一部分。循环的其余部分，则负责对这些工作采取行动。

## Worktree，让并行不变成混乱

只要你运行不止一个智能体，文件就会开始互相冲突，而这就会变成失败原因。两个智能体写同一个文件，和两个工程师在没人先沟通的情况下提交同几行代码，是完全一样的头疼事。一个 git worktree 可以解决它：它是在自己的分支上的一个独立工作目录，共享同一个仓库历史，所以一个智能体的编辑实际上不能碰到另一个智能体的 checkout。

Codex 把 worktree 支持直接内置进来，所以多个线程可以同时处理同一个仓库，而不会互相撞上。Claude Code 通过 `git worktree`、一个用来在独立 checkout 中打开会话的 `--worktree` 标志，以及你可以放在子智能体上的 `isolation: worktree` 设置，提供同样的隔离，让每个 helper 都拿到一个干净的 checkout，并在结束后自动清理。我在 orchestration tax 里写过这件事的人类侧面：worktree 消除了机械层面的冲突，但你仍然是天花板。你的 review 带宽决定了你实际能同时运行多少个智能体，而不是工具决定。

## 技能，让你不必每次都重新解释项目

Skill 是你停止像金鱼一样每个会话都重新解释同一个项目上下文的方法。两个工具都使用同样的格式：一个文件夹，里面有一个 `SKILL.md`，保存说明和元数据，然后还可以有可选的脚本、参考资料和资产。Codex 会在你用 `$` 或 `/skills` 调用 skill 时运行它，也会在你的任务匹配 skill 描述时自动运行它。这就是为什么一个紧凑、朴素的描述胜过一个 clever 描述。Claude Code 也是同样的做法，我在 agent skills 那篇里写过这个模式。

技能也是 intent 不再一次次消耗你的地方。我在 intent debt 中曾经说过，智能体每个会话一开始都是冷启动的，它会用自信的猜测填补你意图里的任何空洞。Skill 就是把意图写在外部：约定、构建步骤、“我们不这么做是因为那次事故”的经验，一次性写在智能体每次运行都会读取的地方。没有 skills，循环每一轮都要从零重新推导你的整个项目；有了 skills，它就有点像会复利增长。

有一点要分清：skill 是创作格式，而 plugin 是你分发它的方式。当你想跨仓库共享一个 skill，或者把几个 skill 打包在一起时，你会把它们打包成一个 plugin。Codex 是这样，Claude Code 也是这样。

## 插件和连接器，让循环触碰真实工具

一个只能看到文件系统的循环，是一个很小的循环。连接器基于 MCP 构建，它们让智能体可以读取你的 issue tracker、查询数据库、访问 staging API、在 Slack 里发消息。Codex 和 Claude Code 都支持 MCP，所以你为其中一个写的连接器通常也能在另一个里工作。插件会把连接器和 skills 打包在一起，所以你的队友可以一次性安装你的设置，而不是凭记忆重新搭建整套东西。

这就是“智能体说：这里是修复方案”和“循环自己打开 PR、关联 Linear ticket，并在 CI 变绿后 ping 频道”之间的区别。连接器让循环能够在你的真实环境里行动，而不是只告诉你“如果我能做的话，我会怎么做”。

## 子智能体，让制造者远离检查者

在一个循环里，最有用的结构性东西，毫无疑问，是把写东西的人和检查东西的人拆开。写了代码的模型在给自己的作业打分时太友善了。第二个带着不同说明、有时甚至是不同模型的智能体，会抓到第一个智能体说服自己接受的那些问题。

Codex 只有在你要求时才会生成子智能体；它们会同时运行，然后把结果折叠回一个回答中。你可以在 `.codex/agents/` 里用 TOML 文件定义自己的智能体，每个智能体都有名称、描述、说明，以及可选的模型和 reasoning effort。所以你的安全审查员可以是一个高 effort 的强模型，而你的探索者可以是某个快速的只读模型。Claude Code 也用 `.claude/agents/` 里的 subagents 和 agent teams 做同样的事，让工作在它们之间传递。两边常见的拆分都是：一个智能体探索，一个智能体实现，一个智能体根据 spec 验证。

我已经两次论证过这个观点，一次是在 code agent orchestra，另一次是在 adversarial code review。它在循环里尤其重要，是因为循环会在你没有盯着的时候运行，所以一个你真正信得过的 verifier，是你能离开的唯一理由。子智能体确实会消耗更多 token，因为每一个都会做自己的模型和工具工作，所以你应该把 token 花在第二意见值得付费的地方。这基本也是 Claude Code 的 `/goal` 在底层做的事情：一个新的模型来决定循环是否完成，而不是让完成工作的那个模型自己来决定。也就是把制造者和检查者的拆分应用到停止条件本身。

## 一个循环长什么样

把这些东西拼起来，一个单独的线程就会变成一个小控制台。下面是我一直在用的一种形状。

一个自动化每天早上在仓库上运行。它的提示词调用一个 triage skill，这个 skill 会读取昨天的 CI 失败、打开的 issues、最近的 commits，然后把发现结果写进一个 Markdown 文件或 Linear 看板。对于每一个值得做的发现，这个线程都会打开一个隔离的 worktree，并派一个子智能体起草修复方案，再派第二个子智能体根据项目 skills 和现有测试来审查这份草稿。

连接器让这个循环可以打开 PR 并更新 ticket。任何这个循环处理不了的东西，都会进入我的 triage inbox。状态文件是整套东西的脊柱：它记住试过什么、什么通过了、还有什么仍然打开，所以明天早上的运行会从今天停止的地方继续。

看看你实际上做了什么。你只设计了一次。你没有亲自提示其中任何一个步骤。这就是 Steinberger 的观点变成现实后的样子。而且无论是在 Codex 里还是在 Claude Code 里，都是同一个循环，因为这些组件就是同样的组件。

## 循环仍然不会替你做什么

循环改变了工作，但它不会把你从工作中删除。而且随着循环变得更好，有三个问题实际上会变得更尖锐，而不是更容易。

验证仍然在你身上。一个无人值守运行的循环，也是一个无人值守犯错的循环。你把 verifier 子智能体和 maker 拆开的全部原因，就是为了让循环说“完成了”这件事有点意义；即便如此，“完成了”仍然是一个声明，而不是证明。我一直在重复 code review in the age of AI 里那句话：你的工作是交付你已经确认能工作的代码。

如果你允许，你的理解仍然会腐烂。循环越快地交付你没有写过的代码，已经存在的东西与你实际理解的东西之间的缺口就越大。这就是 comprehension debt，而一个顺滑的循环只会让它增长得更快，除非你去读循环产出的东西。

而且，是的，舒服的姿势很可能也是危险的姿势。当循环自己运行时，你很容易停止拥有自己的判断，只是接受它返回给你的任何东西。我把这叫做 cognitive surrender。带着判断力设计循环时，设计循环是解药；为了避免思考而设计循环时，它就是加速剂。同一个动作，结果相反。

## 构建循环。继续做工程师。

我认为，这是我们工作方式将如何演化的一个预览。话虽如此，如果我不亲自 review 代码，或者如果我完全依赖自动循环来修复它，我的产品质量会受到损害。我很可能会陷入一个向下的螺旋，不断把自己挖进更深的坑里。

话虽如此，去设置你的循环吧，但别忘了，直接提示你的智能体仍然是有效的。关键在于找到正确的平衡。

循环也会因为你是谁而产生不同结果。两个人可以构建完全相同的循环，却得到完全相反的结果。一个人用它在自己深刻理解的工作上更快前进。另一个人用它来逃避理解工作本身。循环不知道这两者的区别。你知道。

这就是为什么循环设计比提示词工程更难，而不是更容易。Cherny 的观点并不是工作变简单了，而是杠杆点移动了。

构建循环。但要像一个打算继续做工程师的人那样构建它，而不只是像一个按下“开始”的人。
