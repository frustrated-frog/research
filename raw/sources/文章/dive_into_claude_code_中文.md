**Jiacheng Liu¹，Xiaohan Zhao¹，Xinyi Shang¹,²，Zhiqiang Shen¹,†**  
¹VILA Lab, Mohamed bin Zayed University of Artificial Intelligence，²University College London

Claude Code 是一种 agentic 编码工具，能够代表用户运行 shell 命令、编辑文件并调用外部服务。本研究通过分析公开可获得的 TypeScript 源代码ᵃ，并进一步将其与 OpenClaw 进行比较，描述了它的综合架构；OpenClaw 是一个独立的开源 AI agent 系统，它在不同的部署语境下回答了许多相同的设计问题。我们的分析识别出激励该架构的五种人类价值、理念与需求（人类决策权威、安全与安全性、可靠执行、能力放大以及上下文适应性），并将它们通过十三条设计原则追踪到具体的实现选择。系统的核心是一个简单的 while 循环，它调用模型、运行工具，然后重复。然而，大部分代码存在于围绕这个循环的系统之中：一个具有七种模式和一个基于 ML 的分类器的权限系统，一个用于上下文管理的五层压缩流水线，四种可扩展机制（MCP、插件、技能和钩子），一个子 agent 委派与编排机制，以及面向追加的会话存储。与 OpenClaw 这个多通道个人助理网关的比较表明，当部署语境发生变化时，相同的反复出现的设计问题会产生不同的架构答案：从逐动作安全评估到边界级访问控制，从单一 CLI 循环到嵌入网关控制平面的运行时，从上下文窗口扩展到网关范围的能力注册。最后，我们基于近期的经验性、架构性与政策性文献，识别出未来 agent 系统的六个开放设计方向。我们的 GitHub 位于：https://github.com/VILA-Lab/Dive-into-Claude-Code。

## 1 引言

AI 辅助软件开发已经从 GitHub Copilot（Chen et al., 2021）这类自动补全式工具，发展到 Cursor（Cursor, 2026）这类 IDE 集成助理，再发展到完全 agentic 的系统；这些系统能够自主规划多步骤修改、执行 shell 命令、读写文件，并对自己的输出进行迭代。Claude Code（Anthropic, 2026a）是 Anthropic 发布的一种 agentic 编码工具（Anthropic, 2026c）。其官方文档描述了一个“agentic loop”，该循环会规划并执行行动以完成目标，并且能够调用工具、评估结果，并持续进行直到任务完成¹。从建议到自主行动的这种转变，引入了基于补全的工具中没有对应物的架构需求。这些需求定义了一个设计空间，也就是每个编码 agent 都必须处理的一组反复出现的问题，涵盖安全、上下文管理、可扩展性以及委派等主题。本研究使用对 Claude Code 的源码级分析，展示一个生产系统如何回答这些问题。

尽管 Claude Code 的采用正在增长，Anthropic 发布的是面向用户的文档，而不是详细的架构描述。本研究使用源代码分析来描述架构设计决策。Anthropic 对 132 名工程师和研究人员的内部调查（Huang et al., 2025）报告称，大约 27% 的 Claude Code 辅助任务是如果没有该工具就不会尝试的工作，这表明该架构支持的是性质上新的工作流，而不仅仅是加速已有工作流。

在本文中，我们首先识别出激励该架构的五种人类价值/理念和十三条设计原则（第 2 节），然后将分析组织为三部分：

1. **设计空间分析。** 我们识别反复出现的设计问题（推理位于何处、迭代循环如何组织、采取什么安全姿态、扩展表面如何划分、上下文如何管理、工作如何跨子 agent 委派，以及会话如何持久化），并通过一个 7 组件的高层结构和一个 5 层子系统架构来分析 Claude Code 的答案，将每个选择追踪到具体的源文件（第 3 节）。该分析旨在深入理解系统机制，目标是为设计更好、更强大的 agent 系统提供参考。

2. **与 OpenClaw 的架构对比。** 除了分析 Claude Code 本身之外，我们还将其设计理念与开源 agent 系统 OpenClaw（Steinberger and OpenClaw Contributors, 2026）进行比较。OpenClaw 是一个多通道个人助理网关。我们从六个设计维度对比二者，以展示相同的反复出现的问题如何在不同部署语境下产生不同答案（第 10 节），从而突出商业软件与开源软件之间的共同原则与关键差异。该比较有助于揭示部署场景、产品目标、安全需求和用户假设如何以不同方式塑造架构选择。通过考察这些系统在哪里趋同、在哪里分化，我们的研究旨在为未来更有能力的 agent 系统设计提供有用指导和实践洞见。

3. **未来 agent 系统的开放方向。** 基于设计空间分析和 OpenClaw 对比，第 12 节识别了六个开放方向，涵盖可观测性-评估差距、跨会话持久化、harness 边界演进、视野扩展、治理以及评估性视角；每个方向都借鉴了经验性、架构性和政策性文献。作为一种评估性视角使用时，我们的研究也揭示出一个开放问题：虽然 Claude Code agent 系统显著增强了程序员和终端用户的短期能力，但它提供的显式支持长期人类提升、更深理解以及持续代码库一致性的机制有限。

核心 agent 循环是一个带有状态管理的 while-true 周期。围绕安全、可扩展性、上下文管理、委派和持久化的周边子系统构成了实现的大部分。源码级分析²使我们能够直接从系统本身识别设计选择、子系统边界和实现权衡，而不是仅仅从产品描述中推断。

## 2 设计理念、设计原则与架构动机

生产级编码 agent 是由人构建、为人服务的，它们所嵌入的架构决策反映了其创造者认为重要的东西。本节识别出激励 Claude Code 设计的人类价值，将它们追踪到反复出现的设计原则，并框定组织第 3 节到第 9 节分析的设计空间问题。

Anthropic 关于安全 agent 的框架指出了一个核心张力：“Agents 必须能够自主工作；它们的独立运行正是使其有价值的地方。但人类应当保留对其目标如何被追求的控制权”（Anthropic, 2025a）。Claude 的宪法不是通过僵硬的决策程序来解决这一点，而是通过培养“可以在上下文中应用的良好判断和健全价值观”（Anthropic, 2026b）来解决。这些承诺，再加上关于开发者实际上如何使用该工具的经验性发现（Huang et al., 2025; McCain et al., 2026），指向了塑造该架构的五种人类价值。

### 2.1 五种价值与理念

**人类决策权威。** 人类保留对系统所做之事的最终决策权威，这通过一种委托人层级组织起来（Anthropic，然后是运营者，然后是用户），该层级形式化了谁对什么拥有权威（Anthropic, 2026b）。系统被设计成让人类能够行使知情控制：他们可以实时观察行动，批准或拒绝拟议操作，中断兼容的进行中操作，并在事后审计。当 Anthropic 发现用户批准了 93% 的权限提示（Hughes, 2026）时，其回应不是增加更多警告，而是重构问题：定义边界（沙箱、自动模式分类器），让 agent 可以在其中自由工作，而不是依赖用户在习惯化之后会停止认真审查的逐动作批准（Dworken and Weller-Davies, 2025）。

**安全、安全性与隐私。** 系统保护人类、他们的代码、他们的数据和他们的基础设施免受伤害，即使人类疏忽或犯错也是如此。这不同于人类决策权威：权威关乎人类选择的权力，而安全关乎即使这种权力失效时系统仍有义务提供保护。Anthropic 的安全 agent 框架将保障 agent 交互安全和在扩展交互中保护隐私分别识别为核心承诺（Anthropic, 2025a）。自动模式威胁模型（Hughes, 2026）明确针对四类风险：过度积极行为、诚实错误、提示注入和模型错位。

**可靠执行。** agent 做人类实际想要它做的事，随着时间保持连贯，并支持在宣布成功之前验证其工作。这个价值跨越单轮正确性（它是否忠实解释了请求？）和长视野可靠性（它是否跨上下文窗口边界、会话恢复和多 agent 委派保持连贯？）。Anthropic 的产品文档（Anthropic, 2026d）描述了 agent 重复执行直到任务完成的三阶段循环：收集上下文、采取行动、验证结果。agent 设计指南（Schluntz and Zhang, 2024）进一步强调，每一步的“来自环境的真实依据”会评估进展。harness 设计指南（Rajasekaran, 2026）同样指出，“agents 倾向于通过自信地赞扬工作来回应”，即使质量一般，这推动了生成与评估的分离。

**能力放大。** 系统实质性地增加人类在单位努力和成本下能够完成的事情。第 1 节讨论的 Anthropic 内部调查（Huang et al., 2025）表明，该架构支持性质上新的工作流，而不仅仅是更快的已有工作流：大约 27% 的任务代表如果没有该工具就不会尝试的工作。其创造者将系统描述为“一个 Unix 实用工具，而不是传统产品”，由“有用、可理解且可扩展”的最小构件构成（Cherny and Wu, 2025）。该架构投资于确定性基础设施（上下文管理、工具路由、恢复），而不是决策脚手架（显式规划器或状态图），其前提是能力不断增强的模型从丰富的操作环境中获益，比从约束其选择的框架中获益更多。

**上下文适应性。** 系统适配用户的具体上下文（他们的项目、工具、约定和技能水平），且这种关系会随时间改善。扩展架构（CLAUDE.md、技能、MCP、钩子、插件）在多个上下文成本层级上提供可配置性（第 6 节和第 7 节）。纵向数据（McCain et al., 2026）显示，人类-agent 关系会演化：自动批准率从少于 50 个会话时约 20% 增加到 750 个会话时超过 40%。这种被描述为自主性“由模型、用户和产品共同建构”的模式意味着，系统是为信任轨迹而设计的，而不是为固定的信任状态而设计的。MCP 捐赠给 Linux Foundation 的 Agentic AI Foundation（The Linux Foundation, 2025）反映了这一价值的生态系统维度。

### 2.2 设计原则

这些价值通过十三条设计原则被操作化，每条原则都回答生产级编码 agent 必须解决的一个反复出现的问题。表 1 总结了这些原则；后续章节（第 3 节到第 9 节）将把每条原则追踪到具体实现选择。

这些原则可以与三类主要替代设计家族对照阅读。第一，基于规则的编排：LangGraph（LangChain, Inc., 2024）等框架将决策逻辑编码为带类型边的显式状态图，选择脚手架而非最小 harness。第二，容器隔离执行：SWE-Agent 和 OpenHands（Yang et al., 2024; Wang et al., 2024b）依赖 Docker 隔离，而不是分层策略执行。第三，将版本控制作为安全：Aider（Gauthier, 2024）等工具使用 Git 回滚作为主要安全机制，而不是拒绝优先评估。Claude Code 的原则集的独特之处在于，它结合了最小决策脚手架与分层策略执行、基于价值的判断与拒绝优先默认值，以及渐进式上下文管理与可组合可扩展性。

### 2.3 从价值到架构

每一种价值都通过其原则追踪到具体架构决策：

**图 1 Claude Code 的高层系统结构。** 系统分解为七个功能组件：用户、接口、agent 循环、权限系统、工具、状态与持久化，以及执行环境。所有入口表面都汇聚到同一个 agent 循环。

- **人类决策权威** 激励拒绝优先评估、分级信任谱、仅追加状态（可审计历史）、外部化可编程策略，以及价值高于规则（第 5 节到第 7 节和第 9 节）。
- **安全、安全性与隐私** 激励纵深防御、拒绝优先默认值、按可逆性加权的评估、外部化策略，以及隔离的子 agent 边界（第 5 节和第 8 节）。
- **可靠执行** 激励上下文作为稀缺资源、仅追加持久状态、优雅恢复、隔离的子 agent 边界，以及纵深防御（第 4 节和第 7 节到第 9 节）。
- **能力放大** 激励最小脚手架、可组合可扩展性、按可逆性加权的风险、上下文管理和优雅恢复（第 4 节到第 6 节）。
- **上下文适应性** 激励透明的基于文件的记忆、可组合可扩展性、分级信任谱，以及外部化可编程策略（第 5 节到第 7 节）。

这些映射也揭示了该架构没有做什么：它不把显式规划图强加给模型推理，不提供单一统一扩展机制，也不会在恢复时还原所有会话作用域的信任相关状态。这些缺席与上述原则集一致。

### 2.4 一种评估性视角：长期能力保存

上述五种价值描述了该架构被设计为服务什么。本文还应用第六个关切，即该架构是否保存长期人类能力，作为一种评估性视角。这个关切是真实的：Anthropic 对 132 名工程师和研究人员的研究（Huang et al., 2025）记录了一个“监督悖论”，其中过度依赖 AI 有可能使监督 AI 所需的技能萎缩；独立研究（Shen and Tamkin, 2026）发现，在 AI 辅助条件下的开发者在理解测试中的得分低 17%。然而，这个关切并没有作为设计驱动因素显著反映在该架构或 Anthropic 所陈述的设计价值中。因此，我们不把它视为同等价值，而是把它视为一个横切关切：第 11 节会把它作为一个应用于全部五种价值的问题，询问短期能力放大是否以长期人类理解、代码库一致性和开发者管道为代价。

## 3 架构概览

构建生产级编码 agent 需要回答几个反复出现的设计问题：推理应位于何处、需要多少个执行引擎、采取什么安全姿态，以及把什么资源视为绑定约束。Claude Code 的架构可以被理解为对这些问题的一组回答。在实现层面，系统具有七个由主数据流连接的组件：用户通过若干接口之一提交提示，该提示进入一个共享 agent 循环。agent 循环组装上下文，调用 Claude 模型，接收可能包含工具使用请求的响应，将这些请求通过权限系统路由，并把获批行动分派给与执行环境交互的具体工具。在整个过程中，状态与持久化机制记录对话转录，管理会话身份，并支持恢复、分叉和回退操作。

### 3.1 设计问题与运行示例

该描述围绕生产级编码 agent 中反复出现的四个设计问题组织，每个问题都支撑表 1 中识别的一条或多条设计原则。这里先引入每个问题及 Claude Code 的答案，说明可能的替代方案，然后在第 4 节到第 9 节中逐步演示。

**推理位于何处？** 在 Claude Code 中，模型推理该做什么；harness 负责执行行动。模型将 `tool_use` 块作为其响应的一部分发出，harness 解析这些块，检查权限，将其分派给工具实现，并收集结果（`query.ts`）。模型从不直接访问文件系统、运行 shell 命令或发起网络请求。这种分离具有安全后果：因为推理和执行占据不同代码路径，被攻陷或受到对抗性操纵的模型无法覆盖 harness 中实现的沙箱、权限检查或拒绝优先规则。模型通往外部世界的唯一接口是结构化的 `tool_use` 协议，harness 会在执行前验证它。社区对提取源代码的分析估计，Claude Code 代码库中只有约 1.6% 构成 AI 决策逻辑，其余 98.4% 是操作基础设施，这一比例展示了核心 agent 推理层有多薄。替代设计在脚手架侧推理上投入更多：Devin 维护显式规划和任务跟踪结构，而 LangGraph（LangChain, Inc., 2024）通过开发者定义的状态图路由控制流。

**有多少个执行引擎？** Claude Code 使用单个 `queryLoop()` 函数，无论用户是通过交互式终端、无头 CLI 调用、Agent SDK 还是 IDE 集成进行交互，它都会执行（`query.ts`）。只有渲染和用户交互层不同。其他系统使用特定模式的引擎：例如，一个 IDE 集成可能遵循与 CLI 工具不同的代码路径，以牺牲统一性换取表面特定优化。

**默认安全姿态是什么？** Claude Code 的默认安全姿态是带有人类升级的拒绝优先：拒绝规则覆盖询问规则，询问规则覆盖允许规则，未识别的行动会升级给用户，而不是静默允许（`permissions.ts`）。多个独立安全层（权限规则、`PreToolUse` 钩子、启用时的自动模式分类器，以及可选 shell 沙箱）并行应用，因此任一层都可以阻止行动（第 5 节）。这结合了表 1 中的带有人类升级的拒绝优先原则和带有分层机制的纵深防御原则。替代方法将信任边界转移到其他地方：SWE-Agent 和 OpenHands（Yang et al., 2024; Wang et al., 2024b）依赖基于容器的隔离来容纳任意执行，而 Aider（Gauthier, 2024）使用基于 git 的回滚作为其主要安全网。

**绑定资源约束是什么？** 在 Claude Code 中，上下文窗口（旧模型为 200K，Claude 4.6 系列为 1M）是绑定资源约束。每次模型调用前会执行五种不同的上下文削减策略（`query.ts`），并且若干其他子系统决策（指令懒加载、延迟工具 schema、子 agent 仅返回摘要）也用于限制上下文消耗（第 7 节）。五层流水线存在的原因是，没有单一压缩策略能够处理所有类型的上下文压力。预算削减针对溢出大小限制的单个工具输出。Snip 处理时间深度。Microcompact 响应缓存开销。Context collapse 管理非常长的历史。Auto-compact 作为最后手段执行语义压缩。每一层都在不同成本-收益权衡上运行，较早且更便宜的层在较昂贵的层之前运行。替代架构将其他资源视为主要瓶颈，例如计算预算（限制模型调用或工具调用次数）或工作记忆（维护显式 scratchpad，而不是依赖对话历史）。

**运行示例。** 为了支撑这些原则，我们在第 3 节到第 9 节中贯穿一个任务：“修复 auth.test.ts 中失败的测试”。在本节中，用户通过 Claude Code 的一个接口提交提示。后续章节将追踪该请求如何经过查询循环、权限门、工具池、上下文窗口、子 agent 委派和会话持久化。

**图 2 运行时 turn 流。** 该图展示一个 agentic turn 的端到端执行：用户提示通过上下文组装进入，模型被调用，工具请求通过权限门，工具结果反馈回循环，而压缩负责管理上下文压力。

### 3.2 高层系统结构

七组件模型（图 1）直接映射到源文件：

1. **用户：** 提交提示，批准权限，审查输出。
2. **接口：** 交互式 CLI、无头 CLI（`claude -p`）、Agent SDK，以及 IDE/Desktop/Browser。所有表面都进入同一个循环。

4. **权限系统：** 拒绝优先规则评估（`permissions.ts`）、自动模式 ML 分类器，以及基于钩子的拦截（`types/hooks.ts`）。

### 状态层（上下文组装、运行时状态、持久化、记忆、侧链）

## 3.4 QueryEngine：一个澄清

`QueryEngine.ts` 中的类文档写道：“QueryEngine 拥有一次对话的查询生命周期和会话状态。它把 `ask()` 的核心逻辑提取成一个独立类，使其可以被 headless/SDK 路径以及（在未来阶段）REPL 使用。”这个类是非交互式界面的对话包装器，而不是引擎本身。它的构造函数接受一个 `QueryEngineConfig`，其中包含初始消息、中止控制器、文件状态缓存以及其他每个对话独有的状态。它的 `submitMessage()` 方法是一个异步生成器，用于编排单个 turn。共享查询路径位于 `query()`（`query.ts`）中，后者包装了一个内部 `queryLoop()`；`QueryEngine` 委托给 `query()`。

这种区别在架构上很重要：交互式 CLI 也调用 `query()`，完全绕过 `QueryEngine`。共享代码路径是循环函数，而不是引擎类。

## 3.5 权限与安全层

默认安全原则通过七个独立层实现。一个请求必须通过所有适用层，任何单一层都可以阻止它：

1. 工具预过滤（`tools.ts`）：被整体拒绝的工具在任何调用发生前就会从模型视野中移除，防止模型尝试调用它们。
2. 拒绝优先规则评估（`permissions.ts`）：拒绝规则总是优先于允许规则，即使允许规则更具体也是如此。
3. 权限模式约束（`types/permissions.ts`）：当前活动模式决定没有匹配显式规则的请求的基线处理方式。
4. 自动模式分类器：一个基于机器学习的分类器评估工具安全性，可能会拒绝规则系统原本允许的请求。
5. Shell 沙箱（`shouldUseSandbox.ts`）：已获批准的 shell 命令仍然可能在限制文件系统和网络访问的沙箱中执行。
6. 恢复时不恢复权限（`conversationRecovery.ts`）：会话作用域权限不会在恢复或分叉时恢复。
7. 基于 Hook 的拦截（`types/hooks.ts`）：`PreToolUse` hook 可以修改权限决策；`PermissionRequest` hook 可以与用户对话框并行异步解析决策（或在协调器模式中先于用户对话框解析）。

这些层会在第 5 节中详细说明。

## 3.6 作为瓶颈的上下文：不只是压缩

除了五层压缩流水线（第 7 节详述）之外，还有几个子系统决策也反映了“上下文是瓶颈”的约束：

- `CLAUDE.md` 懒加载：基础 `CLAUDE.md` 层级在会话开始时加载，但额外的嵌套目录指令文件和条件规则只有在 Agent 读取这些目录中的文件时才加载，避免未使用指令消耗上下文。
- 延迟工具 schema：启用 `ToolSearch` 时，某些工具在初始上下文中只包含名称；完整 schema 按需加载。
- 子 Agent 仅返回摘要：子 Agent 只向父级返回摘要文本，而不是完整对话历史（第 8 节）。
- 每个工具结果预算：单个工具结果会被限制在可配置大小内，防止某个冗长输出不成比例地消耗上下文。

# 4 Turn 执行：Agentic 查询循环

当用户提交“修复 `auth.test.ts` 中失败的测试”时，输入会进入一个反应式循环，这是编码 Agent 可能采用的若干编排模式之一。本节考察 Claude Code 对简单 while 循环架构的选择，并端到端追踪一次 turn，展示表 1 中的三个设计原则：以最小脚手架配合最大操作性 harness、把上下文作为稀缺资源并逐步管理，以及优雅恢复和韧性。

## 4.1 查询流水线

每个 turn 都遵循固定顺序（图 2，`query.ts`）：

1. 设置解析。`queryLoop()` 函数解构不可变参数，包括系统提示词、用户上下文、权限回调和模型配置。
2. 可变状态初始化。单个 `State` 对象保存跨迭代的全部可变状态，包括消息、工具上下文、压缩跟踪和恢复计数器。循环中的七个继续点（“continue sites”）都会用一次整体对象赋值覆盖该对象，而不是逐个字段突变。
3. 上下文组装。`getMessagesAfterCompactBoundary()` 函数从最后一个压缩边界之后取回消息，确保被压缩的内容用其摘要表示，而不是使用原始消息。
4. 模型前上下文塑形器。五个塑形器顺序执行（第 4.3 节）。
5. 模型调用。一个遍历 `deps.callModel()` 的 `for await` 循环流式接收模型响应，传入已组装消息（前置用户上下文）、完整系统提示词、thinking 配置、可用工具集、中止信号、当前模型规格，以及包括快速模式设置、effort 值和备用模型在内的额外选项。
6. 工具使用分发。如果响应包含 `tool_use` 块，它们会流向工具编排层（第 4.2 节）。
7. 权限门。每个工具请求都会经过权限系统（第 5 节）。
8. 工具执行与结果收集。工具结果作为 `tool_result` 消息加入对话，然后循环继续。
9. 停止条件。如果响应不包含 `tool_use` 块（只有文本），则该 turn 完成。

`queryLoop()` 函数被定义为一个 `AsyncGenerator`，在推进过程中产生 `StreamEvent`、`RequestStartEvent`、`Message`、`TombstoneMessage` 和 `ToolUseSummaryMessage` 事件。基于生成器的设计使 UI 层能够流式输出，同时保持循环内部单一同步控制流。

Claude Code 的反应式循环遵循 ReAct 模式（Yao et al., 2022）：模型生成推理和工具调用，harness 执行动作，结果进入下一轮迭代。替代编排模式包括显式图路由（LangChain, Inc., 2024），其中控制流被定义为带类型边的状态机；以及树搜索方法（Zhou et al., 2023），它们在提交之前探索多个动作轨迹。Anthropic 自己的文档（Schluntz and Zhang, 2024）识别了五种可组合工作流模式（提示链、路由、并行化、编排器-工作者、评估器-优化器），Claude Code 主要在子 Agent 委派中使用编排器-工作者模式（第 8 节），同时让核心循环保持反应式。反应式设计以搜索完备性换取简单性和低延迟：每个 turn 都提交到一个动作序列，不进行回溯。

## 4.2 工具分发与流式执行

当模型响应包含 `tool_use` 块时，系统会在两条执行路径之间选择。主路径使用 `StreamingToolExecutor`，它在工具从模型响应中流式出现时就开始执行，从而降低多工具响应的延迟。回退路径使用 `toolOrchestration.ts` 中的 `runTools()`，后者遍历由 `partitionToolCalls()` 生成的分区。两条路径都会把工具分类为并发安全或互斥。只读操作可以并行执行，而像 shell 命令这样的状态修改操作会被串行化。

`StreamingToolExecutor`（`StreamingToolExecutor.ts`）通过两个协调机制管理并发执行：

- 兄弟中止控制器。当任意 Bash 工具出错时触发，立即终止其他正在运行的子进程，而不是让它们运行到完成。
- 进度可用信号。当有新输出可用时唤醒 `getRemainingResults()` 消费者。

结果会被缓冲，并按照工具接收顺序发出，因此即便工具并行运行，输出顺序也保持一致。这很重要，因为模型期望工具结果顺序与其工具使用请求顺序相同。这种“并发读、串行写”的执行模型处在完全串行分发与更激进的推测式方法之间，例如 PASTE（Sui et al., 2026）会在模型仍在生成时推测性预执行预测到的未来工具调用，用推测隐藏工具延迟。

工具结果收集阶段会遍历来自流式执行器或同步 `runTools()` 生成器的更新。每个更新都可能携带工具结果、附件或进度事件。一个特殊检查会检测 `hook_stopped_continuation` 附件：如果 `PostToolUse` hook 表示该 turn 不应继续，则设置 `shouldPreventContinuation` 标志。结果会通过 `normalizeMessagesForAPI()` 规范化以适配 Anthropic API，并过滤保留用户类型消息。

## 4.3 模型前上下文塑形器

在每次模型调用前，五个上下文塑形器会在 `query.ts` 中顺序执行，作用于 `messagesForQuery` 数组。它们依次运行，较早步骤先做较轻量的缩减，较晚步骤再做更广泛的压缩。

**预算缩减**（`applyToolResultBudget()`）。对工具结果执行每条消息大小限制，用内容引用替换超大输出。豁免工具（`maxResultSizeChars` 不是有限值的工具）保留完整输出。对 agent 和 session 查询源，内容替换会被持久化，以便恢复时重建。预算缩减在 microcompact 之前运行，因为 microcompact 只根据 `tool_use_id` 工作，从不检查内容；二者可以干净组合。

**Snip**（`snipCompactIfNeeded()`，由 `HISTORY_SNIP` 控制）。轻量裁剪，移除较旧历史片段，返回 `{messages, tokensFreed, boundaryMessage}`。`snipTokensFreed` 会传给 auto-compact，因为主 token 计数器从最近 assistant 消息的 `usage` 字段推导上下文大小，而该消息在 snip 后仍带着 snip 前的 `input_tokens`；如果不显式传入，snip 的节省量对计数器不可见。

**Microcompact**。细粒度压缩，总是运行基于时间的路径，并可选运行缓存感知路径（由 `CACHED_MICROCOMPACT` 控制）。启用缓存路径时，边界消息会延迟到 API 响应后，以便使用真实的 `cache_deleted_input_tokens` 而非估计值。返回 `{messages, compactionInfo}`，其中 `compactionInfo` 可能包括 `pendingCacheEdits`。

**上下文折叠**。由 `CONTEXT_COLLAPSE` 控制。这是对对话历史的读时投影。源代码注释解释道：“不会 yield 任何内容；折叠视图是 REPL 完整历史的读时投影。摘要消息存在于 collapse store 中，而不是 REPL 数组中。这就是 collapses 能跨 turn 持久存在的原因。”与其他塑形器不同，上下文折叠不会突变 REPL 存储的历史；它通过 `applyCollapsesIfNeeded()` 把 `messagesForQuery` 数组替换为投影视图，因此模型看到的是折叠版本，而完整历史仍可用于重建。

**Auto-compact**。第五个塑形器，通过 `compact.ts` 中的 `compactConversation()` 触发完整的模型生成摘要。该函数执行 `PreCompact` hook，使用 `getCompactPrompt()` 创建摘要请求，并调用模型生成压缩摘要。结果进入 `buildPostCompactMessages()`（`compact.ts`）。只有当前四个塑形器都运行后上下文仍超过压力阈值时，auto-compact 才会触发。

## 4.4 恢复机制

查询循环为边界情况实现了若干恢复机制：

- 最大输出 token 升级：当响应达到输出 token 上限时，系统可以在没有现有覆盖值或环境变量上限的情况下，受 GrowthBook 标志控制，用升级后的限制重试。每个 turn 最多允许三次恢复尝试（`MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3`）。
- 反应式压缩（由 `REACTIVE_COMPACT` 控制）：当上下文接近容量时，反应式压缩会只总结足够释放空间的部分。`hasAttemptedReactiveCompact` 标志确保每个 turn 最多触发一次。
- 提示过长处理：如果 API 返回 `prompt_too_long` 错误，循环首先尝试上下文折叠溢出恢复和反应式压缩。只有这些都失败后，它才以 `reason: 'prompt_too_long'` 终止。
- 流式回退：`onStreamingFallback` 回调处理流式 API 问题，使循环能用不同策略重试。
- 备用模型：`fallbackModel` 参数使主模型失败时能够切换到替代模型。

## 4.5 停止条件

多种条件可以终止循环：

1. 无工具使用：模型只生成文本内容（主要停止条件）。
2. 最大 turn 数：达到可配置的 `maxTurns` 限制。
3. 上下文溢出：API 返回 `prompt_too_long`。
4. Hook 干预：`PostToolUse` hook 设置 `hook_stopped_continuation`。
5. 显式中止：`abortController` 信号触发。

turn 流水线决定工具请求如何被编排与恢复。下一节考察决定每个请求是否允许执行的门控机制。

# 5 工具授权与控制边界

生产级编码 Agent 采用不同安全架构：分层策略执行、操作系统级沙箱，或基于版本控制的回滚。Claude Code 结合了前两者，实现了表 1 中的四个设计原则：拒绝优先并向人类升级、渐进信任光谱、分层机制的纵深防御，以及按可逆性加权的风险评估。

当 Claude 决定执行一个工具时（例如通过 `BashTool` 运行 `npm test` 来复现 auth 测试失败），该请求会进入图 4 所示的权限流水线。每个工具调用都经过权限系统，默认行为是拒绝或询问，而不是静默允许。这一默认值来自一个已记录的行为模式：Anthropic 的自动模式分析（Hughes, 2026）发现，用户大约批准 93% 的权限提示，这说明审批疲劳使交互式确认作为唯一安全机制在行为上不可靠。因为用户习惯性批准而不仔细审查，系统必须在不依赖人类警觉性的情况下维持安全。这促成了拒绝优先评估、整体拒绝预过滤和沙箱作为独立层的架构承诺。

## 5.1 权限模式与规则评估

类型定义中存在七种权限模式（`types/permissions.ts` 中 5 种外部模式；条件加入 `auto`；类型联合中有 `bubble`）：

1. `plan`：模型必须创建计划；只有用户批准后才执行。
2. `default`：标准交互式使用。大多数操作需要用户批准。
3. `acceptEdits`：工作目录内编辑以及某些文件系统 shell 命令（`mkdir`、`rmdir`、`touch`、`rm`、`mv`、`cp`、`sed`）会自动批准；其他 shell 命令需要批准。
4. `auto`：基于机器学习的分类器评估未通过快速路径检查的请求（由 `TRANSCRIPT_CLASSIFIER` 控制）。
5. `dontAsk`：不提示，但仍执行拒绝规则。
6. `bypassPermissions`：跳过大多数权限提示，但安全关键检查和绕过免疫规则仍然适用。
7. `bubble`：仅内部使用，用于子 Agent 权限向父终端升级。

五种外部可见模式（`acceptEdits`、`bypassPermissions`、`default`、`dontAsk`、`plan`）定义在 `EXTERNAL_PERMISSION_MODES` 数组中。只有在 `TRANSCRIPT_CLASSIFIER` 特性标志激活时，`auto` 模式才会被条件包含。`bubble` 模式存在于类型联合中，但不在任一模式数组中；它在内部用于子 Agent 权限升级（第 8 节）。

权限规则按拒绝优先顺序评估（`permissions.ts`）。`toolMatchesRule()` 函数首先检查拒绝规则：拒绝规则总是优先于允许规则，即使允许规则更具体也是如此。宽泛拒绝（“拒绝所有 shell 命令”）不能被窄允许（“允许 `npm test`”）覆盖。规则系统支持工具级匹配（按工具名）和内容级匹配（匹配具体工具输入模式，例如 `Bash(prefix:npm)`）。

七种模式构成一个渐进自治光谱，从 `plan`（用户在执行前批准所有计划）经由 `default` 和 `acceptEdits` 到 `bypassPermissions`（最少提示）。这种梯度反映了一个反复出现的设计张力：随着自治增加，系统必须从交互式批准转向自动安全检查。其他 Agent 系统以不同方式解决这种张力。SWE-Agent 和 OpenHands（Yang et al., 2024；Wang et al., 2024b）使用 Docker 容器隔离，把 Agent 的整个执行环境沙箱化，而不是评估单个工具调用。Aider（Gauthier, 2024）依赖 Git 作为安全网，通过版本控制使所有更改可逆。Claude Code 的方法是在可选容器沙箱之上叠加多种策略执行机制，以简单性换取对单个动作的细粒度控制。

## 5.2 授权流水线

完整授权流水线包含若干阶段：

**预过滤。** 在任何工具请求到达运行时评估前，`filterToolsByDenyRules()`（`tools.ts`）会在工具池组装时把整体拒绝工具从模型视野中剥离。文档写道：“使用与运行时权限检查相同的 matcher，因此像 `mcp__server` 这样的 MCP 服务器前缀规则会在模型看到之前剥离该服务器的所有工具。”这防止模型尝试调用禁用工具，也避免把调用浪费在这些工具上。

**PreToolUse hook。** 注册的 hook 会作为权限流水线的一部分触发。`PreToolUse` hook 可以返回 `permissionDecision` 来拒绝或询问，或返回 `updatedInput` 修改工具输入参数（`types/hooks.ts`）。hook 的 allow 不会绕过后续基于规则的拒绝或安全检查。在交互式路径中，用户对话框会先排队，hook 异步运行；协调器和类似后台 Agent 路径会在显示对话框前等待自动检查。

**规则评估。** 拒绝优先规则引擎评估请求。MCP 工具通过完全限定名 `mcp__server__tool` 匹配，服务器级规则匹配来自该服务器的所有工具。

**权限处理器。** `useCanUseTool.tsx` 中的处理器根据运行时上下文分支到四条路径之一：

1. 协调器：用于多 Agent 协调模式。在回退到用户交互前尝试自动解析（分类器、hook、规则）。
2. Swarm worker：处理多 Agent swarm 中的 worker Agent，拥有自己的解析逻辑。
3. 推测分类器：当 `BASH_CLASSIFIER` 启用且工具是 `BashTool` 时，推测分类器会让预先启动的分类结果与超时竞速。如果分类器高置信返回，工具会无需用户交互即刻批准。
4. 交互式：回退路径。通过终端 UI 呈现标准用户批准对话框。

在协调器和一些后台路径中，会先尝试自动解析再进行用户交互。在标准交互路径中，对话框可能先出现，而 hook 或分类器检查并行继续。当分类器或拒绝规则阻止动作时，系统把拒绝当作路由信号而不是硬停止：模型收到拒绝原因，修正方法，并在下一轮循环中尝试更安全的替代方案。`PermissionDenied` hook 事件（第 6 节）使外部代码能够以编程方式观察并响应这些拒绝。这种恢复导向设计意味着权限执行塑造 Agent 行为，而不是简单中止它。

## 5.3 自动模式分类器与 Hook 生命周期

启用时，自动模式分类器（`yoloClassifier.ts`）参与权限决策。当 `TRANSCRIPT_CLASSIFIER` 启用时，分类器加载三个提示资源：

- 基础系统提示词。
- 外部权限模板。
- 对 Anthropic 内部用户，单独的内部模板。

分类器会根据对话转录记录和权限模板评估拟议工具调用，产生允许、拒绝或请求人工批准。`isUsingExternalPermissions()` 函数检查 `USER_TYPE` 和 `forceExternalPermissions` 配置标志，以选择合适模板。

源代码（`coreTypes.ts`）定义的 27 个 hook 事件中，有五个直接参与权限流，每个都有特定的 Zod 校验输出 schema（`types/hooks.ts`）：

- `PreToolUse`：可以返回 `permissionDecision`（拒绝或询问，但允许不会绕过后续检查）、`permissionDecisionReason` 和 `updatedInput`（修改参数）。
- `PostToolUse`：可以注入 `additionalContext`，并且对 MCP 工具可以返回 `updatedMCPToolOutput`，在结果进入上下文前修改结果。
- `PostToolUseFailure`：可以为错误特定指导注入 `additionalContext`。
- `PermissionDenied`：可以在自动模式拒绝后提供重试指导。
- `PermissionRequest`：可以返回 allow 或 deny 决策。在协调器和类似路径中，它可以在用户对话框前解析；在标准交互路径中，它也可以与对话框并行运行。

对非 MCP 工具，`tool_result` 会在 `PostToolUse` hook 触发前发出。对 MCP 工具，结果会延迟到 post hook 运行后，以使 `updatedMCPToolOutput` 生效。

## 5.4 Shell 沙箱

Shell 沙箱为 Bash 和 PowerShell 命令提供额外保护层（`shouldUseSandbox.ts`）。`shouldUseSandbox()` 函数检查沙箱是否全局启用、调用是否选择退出，以及命令是否匹配任意排除模式。

启用时，沙箱提供独立于应用级权限模型的文件系统和网络隔离。一个命令可以获得权限批准但仍在沙箱中执行，也可以被权限拒绝而从不进入沙箱检查。两个系统作用在不同轴上：授权与隔离。

分层安全架构依赖一个独立性假设：如果一层失败，其他层会捕获违规。然而，若干层共享共同的性能约束。安全研究者（Adversa.ai, 2026）记录到，包含超过 50 个子命令的命令会回退到单个通用批准提示，而不是运行逐子命令拒绝规则检查，因为逐子命令解析会导致 UI 冻结。这个例子表明，当层之间共享失败模式时，纵深防御可能退化；第 11.3 节会进一步分析这种安全与性能之间的结构性张力。

权限流水线决定工具请求能否执行。下一节考察首先决定哪些工具存在的机制：组装模型动作表面的可扩展性架构。

# 6 可扩展性：MCP、插件、技能和 Hook

编码 Agent 的一个反复出现的设计问题是如何构造扩展表面：使用单一统一机制、少数专用机制，还是使用具有不同上下文成本的分层栈。这里的分析展示表 1 中两个设计原则：可组合的多机制可扩展性，以及外部化可编程策略。回到运行示例，一旦 Claude 正在尝试修复 `auth.test.ts`，并且先前的 `npm test` 请求已由权限系统调解（第 5 节），下一个问题就是可用于修复的扩展动作表面是什么。当 Claude Code 中的一个 turn 开始时，模型看到的不只是 `BashTool` 和 `FileReadTool` 这样的内置工具，还包括来自 MCP 服务器的数据库查询工具、`.claude/skills/` 中的自定义 lint 技能，以及已安装插件贡献的工具。这些通过四种在循环不同位置扩展 Agent 的机制进入：MCP 服务器提供外部工具集成，插件打包并分发组件包，技能注入领域特定指令，hook 拦截工具执行生命周期。Anthropic 文档（Anthropic, 2026d）给出了更广视图，其中还包括 `CLAUDE.md`（第 7 节）和子 Agent（第 8 节）。本文把 `CLAUDE.md` 和子 Agent 放在各自章节，因为它们运行在不同子系统（上下文构造和委派）中，但上下文成本排序具有架构意义：它揭示每个扩展点如何在表达力与有限上下文窗口之间做取舍。

## 6.1 四种扩展机制

这些机制在不同源目录中实现（图 5），服务于不同集成模式。

**MCP 服务器。** 模型上下文协议是主要外部工具集成路径。MCP 服务器从多个作用域配置：项目、用户、本地和企业，并且额外的插件服务器和 `claude.ai` 服务器会在运行时合并（`services/mcp/config.ts`）。MCP 客户端（`services/mcp/client.ts`）支持多种传输类型：`stdio`、SSE、HTTP、WebSocket、SDK，加上 IDE 特定变体（`sse-ide`、`ws-ide`）和内部 `claudeai-proxy`。每个连接服务器都会贡献作为 `MCPTool` 对象的工具定义。专用内置工具 `ListMcpResourcesTool` 和 `ReadMcpResourceTool` 提供对 MCP 资源的访问。

**插件。** 插件具有双重角色：既是打包格式，也是分发机制。`PluginManifestSchema`（`utils/plugins/schemas.ts`）接受十种组件类型：命令、Agent、技能、hook、MCP 服务器、LSP 服务器、输出风格、channels、settings 和用户配置。插件加载器（`utils/plugins/pluginLoader.ts`）校验 manifest，并把每个组件路由到相应注册表：命令和技能通过 `SkillTool` 元工具暴露，Agent 出现在被 `AgentTool` 消费的定义中，hook 合并到 hook 注册表，MCP 和 LSP 服务器折叠进标准配置，输出风格修改响应格式。因此，一个插件包可以同时跨多种组件类型扩展 Claude Code，使插件成为第三方扩展的主要分发载体。

**技能。** 每个技能由一个带 YAML frontmatter 的 `SKILL.md` 文件定义。`parseSkillFrontmatterFields()` 函数（`loadSkillsDir.ts`）解析 15 个以上字段，包括显示名称、描述、允许工具（授予技能访问额外工具的权限）、参数提示、模型覆盖、执行上下文（`fork` 表示隔离执行）、关联 Agent 定义、effort 等级和 shell 配置。技能可以定义自己的 hook，这些 hook 会在调用时动态注册。捆绑技能在启动时以内存方式注册。被调用时，`SkillTool` 元工具把技能指令注入上下文。

### Hooks

源代码定义了 27 个 hook 事件，覆盖工具授权（`PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`PermissionRequest`、`PermissionDenied`）、会话生命周期（`SessionStart`、`SessionEnd`、`Setup`、`Stop`、`StopFailure`）、用户交互（`UserPromptSubmit`、`Elicitation`、`ElicitationResult`）、子 Agent 协调（`SubagentStart`、`SubagentStop`、`SubagentStopFailure`、`SubagentSpawned`、`SubagentProgress`、`SubagentTerminate`）、文件和工作区事件（`FileChanged`、`WorktreeCreate`、`WorktreeRemove`）以及通知（`coreTypes.ts`、`coreSchemas.ts`）。其中只有一部分 hook 直接参与安全；其余多数 hook 服务于编排、生命周期管理、遥测、通知和上下文注入。

Hook 处理器的定义支持多种执行形态，包括 shell 命令 hook（`type: command`）、LLM 提示 hook（`type: prompt`）、HTTP hook（`type: http`）以及 Agentic verifier hook（`type: agent`）。这些 hook 构成了一种外部化可编程策略层：用户、插件或企业部署可以在不修改核心循环的情况下插入自定义检查、重写、通知和上下文补充逻辑。

## 6.2 工具池组装

`tools.ts` 中的 `assembleToolPool()` 函数被文档标注为“组合所有工具源的唯一真实来源”。它负责收集内置工具、MCP 工具、技能和插件贡献的工具，并根据特性标志、用户类型、权限规则、运行环境和工具可用性过滤最终暴露给模型的工具集。

工具池并不是一个静态列表。Claude Code 最多包含 54 个内置工具，其中 19 个无条件启用，35 个取决于特性标志和用户类型。MCP 工具会与内置工具合并成一个扁平工具池，因此模型在生成 `tool_use` 时不需要区分工具来自本地还是远程。工具池还会受到拒绝规则预过滤影响：如果某些工具被整体拒绝，它们会在模型看到之前就被移除。

`REPL.tsx` 通过 `useMergedTools` hook 使用该工具池，`AgentTool.tsx` 在构建 worker 工具集时也使用相同组装逻辑。Agent 型扩展（来自 `.claude/agents/*.md` 的自定义 Agent 定义以及插件贡献的 Agent）通过 `AgentTool` 间接暴露；技能通过 `SkillTool` 暴露；MCP 工具通过 MCP 客户端暴露；插件则把多个组件注册到各自子系统。

这种设计体现了“单一工具池、多种贡献源”的架构选择。模型面对的是统一动作表面，而系统内部保留来源信息，以便权限、hook、沙箱、插件生命周期和运行环境约束分别生效。

## 6.3 为什么需要四种机制？

既然每增加一种扩展机制都会增加开发者需要学习的表面积，一个自然问题是：为什么不只提供一种统一扩展 API？论文的回答是：四种机制分别服务于不同抽象层，具有不同上下文成本和插入点。

MCP 服务器提供运行时工具集成：模型获得新的可调用工具。代价是较高上下文成本，因为工具 schema 需要暴露给模型，并且外部服务连接需要配置和生命周期管理。

插件提供多组件打包和分发：一个插件可以同时贡献命令、技能、hook、MCP 服务器、LSP 服务器、输出风格和设置。它的上下文成本取决于组件类型，但它是面向分发和安装的机制，而不是单个工具调用机制。

技能提供领域特定指令和元工具调用：模型只需要在初始上下文中看到技能描述，真正的技能指令在调用时注入，因此上下文成本较低。技能适合把复杂领域流程封装为可调用知识包。

Hook 提供生命周期拦截和事件驱动自动化：默认情况下几乎没有上下文成本，因为 hook 不需要暴露给模型。它们在执行路径上运行，可以阻止、重写、注入上下文或触发外部副作用。

表 2 总结了这种差异：MCP 服务器插入模型可达工具池，插件横跨 assemble/model/execute 三个点，技能主要在 assemble 阶段通过上下文注入生效，hook 则在 execute 阶段的前后处理生效。

一些 Agent 框架提供单一扩展机制，通常是工具 API，把所有自定义都表达为工具。Claude Code 的多机制设计牺牲了概念简洁性，但换来了更低的上下文成本、更明确的部署语义和更细粒度的策略控制。扩展机制因此不是平行重复，而是分别回答“模型能调用什么”“如何分发能力”“什么时候加载领域知识”“执行前后如何拦截”这些不同问题。

# 7 上下文构造与记忆

Agent 如何管理上下文窗口、如何持久化用户指令，是一个核心设计选择，并直接连接表 1 中“上下文作为稀缺资源”和“透明文件化配置与记忆”的原则。

此时回到运行示例，修复 `auth.test.ts` 的任务已经积累了状态：原始请求、`npm test` 的失败输出、可能的文件读取结果、权限决策、hook 注入信息和先前模型响应。每次调用模型前，Agent 循环都需要从工具池（第 6 节）、`CLAUDE.md` 文件、自动记忆以及对话历史中组装上下文窗口。以下小节说明组装过程、`CLAUDE.md` 层级、自动记忆和压缩流水线。

## 7.1 上下文窗口组装

上下文窗口（图 6）由多个来源构成，其中一些在初始组装时加入，另一些在后期注入：

- 系统提示词和系统上下文：包括基础系统提示词、模型配置、git 状态、工作目录信息、当前环境以及其他会话级上下文。
- 用户上下文：包括 `CLAUDE.md` 层级、当前日期和其他用户可见指令。
- 工具 schema：可调用工具定义，可能完整加载，也可能在 `ToolSearch` 启用时延迟加载。
- 对话历史：来自当前 session 或恢复 transcript 的消息。
- Hook 注入内容：例如 `UserPromptSubmit` 或 `PostToolUse` hook 注入的额外上下文。
- 相关记忆预取：自动记忆或文件化记忆中与当前请求相关的内容。
- 压缩结果：来自 auto-compact、microcompact、context collapse 或 snip 的摘要与边界标记。

`query.ts` 中的系统提示组装使用 `asSystemPrompt(appendSystemContext(systemPrompt, systemContext))()` 把系统上下文与基础提示词结合。用户上下文（`CLAUDE.md` 和日期）则作为用户消息加入，而不是作为系统提示词内容加入。这个设计保留了系统提示词的高优先级，同时让用户可编辑指令处于较低权限层级。

若干上下文源会较晚注入。例如，相关记忆预取会在主窗口构造后加入；hook 注入可以发生在用户提交提示或工具执行之后；工具 schema 可能按需加载。这种分阶段组装避免在初始窗口中一次性塞入所有潜在信息。

## 7.2 `CLAUDE.md` 层级和自动记忆

记忆系统背后有一个设计原则：存储的上下文应该能被用户检查和编辑。`CLAUDE.md` 文件采用纯文本 Markdown，而不是结构化配置或不透明数据库条目。这种透明性选择以表达能力换取可审计性：用户可以读取、编辑、版本控制并审查这些文件。

`CLAUDE.md` 支持四层指令层级，从托管设置到目录特定文件。系统会从当前目录向上遍历到根目录，检查所有项目和本地记忆文件。文件按“优先级反序”加载：后加载的文件得到更多模型注意力。对于从根到当前工作目录的遍历，这意味着更接近当前工作目录的指令会更晚加载，从而更接近模型上下文末尾。

嵌入式记忆系统可以更有选择性地检索单条记忆，但代价是可检查性下降。Claude Code 选择文件化记忆，是为了让用户能够把项目规则、偏好、约定和长期说明放进版本控制。`CLAUDE.md` 的内容作为用户上下文消息提供，而不是系统提示词。这有重要含义：因为它是对话内容的一部分，模型会看到它，但它不具备系统级约束的同等优先级。

记忆文件还支持 `@include` 指令，用于模块化指令集（`claudemd.ts` 中的 `processMemoryFile()`）。语法变体包括 `@path`、`@./relative`、`@~/home` 和 `@/absolute`。该指令在叶子文本中生效，并允许用户把大型项目说明拆成多个可复用片段。

## 7.3 压缩流水线

五层压缩流水线（第 4.3 节）通过渐进策略实现“上下文是瓶颈”的原则。它不是单一总结器，而是多个针对不同压力类型的机制：

1. 工具结果预算：限制单个工具结果大小。
2. Snip：移除较旧历史片段。
3. Microcompact：对细粒度工具结果或缓存相关内容做压缩。
4. Context collapse：使用读时投影显示折叠视图。
5. Auto-compact：在前几层不够时触发模型生成摘要。

Auto-compact 会在 transcript 中产生可见摘要，microcompact 会发出边界标记，但 context collapse 的摘要存放在 collapse store 中，不直接突变 REPL 历史。`buildPostCompactMessages()`（`compact.ts`）返回压缩后的输出结构，通常包括摘要消息、边界标记以及必要的后续消息。设计目标是让压缩既能释放上下文，又能保留恢复和审计所需结构。

`compactConversation()`（`compact.ts`）包含若干设计选择。Pre-compact hook 可以在压缩前运行；摘要提示词由 `getCompactPrompt()` 构造；摘要模型调用生成压缩内容；之后 `buildPostCompactMessages()` 重新组装压缩后的消息列表。这使压缩成为显式事件，而不是不可见截断。

当系统把工作委派给子 Agent 时，上下文隔离更加关键，因为每个子 Agent 都运行在自己的上下文窗口中。

# 8 子 Agent 委派与编排

多 Agent 编排是编码 Agent 的关键设计维度，选择范围从父子委派到并行 worker、从共享上下文到隔离上下文、从共享权限到重新构造权限。

在运行示例中，当 Claude 判断修复 auth 测试之前需要先探索认证模块结构时，它可以调用 `AgentTool` 生成一个探索型子 Agent。该子 Agent 读取文件、理解模块结构，然后只把摘要返回给父 Agent。

## 8.1 Agent 工具与委派标准

`Agent` 工具输入 schema（图 7）使用特性门控字段，未启用特性时会省略可选参数。内置子 Agent 包括 Explore、Plan 和 general-purpose。除此之外，用户可以通过 `.claude/agents/*.md` 文件定义自定义子 Agent，插件也可以贡献 Agent 定义。

`SkillTool` 与 `AgentTool` 的差异在于：`SkillTool` 把指令注入当前上下文窗口，而 `AgentTool` 生成一个新的隔离上下文窗口。前者更轻量，适合在当前任务中增加专业知识；后者更昂贵，但适合把独立子任务委派出去，避免父上下文膨胀。

这种取舍意味着大多数子 Agent 调用需要一个自包含提示，因为默认路径不会把父上下文完整复制给子 Agent。父 Agent 必须把任务目标、相关文件、约束和期望输出明确写入子 Agent 提示。

## 8.2 隔离架构

子 Agent 隔离支持多种模式（`AgentTool.tsx`）：

- 普通隔离：子 Agent 运行在独立上下文中，使用重建后的权限上下文和工具集。
- Fork 模式：子 Agent 可以使用与父级相关但隔离的会话状态。
- 受限工具模式：通过 `allowedTools` 限制子 Agent 可用工具。
- 权限升级模式：内部 `bubble` 权限模式允许子 Agent 把无法自行解决的权限请求升级给父终端。

`runAgent.ts` 中的子 Agent 权限覆盖逻辑包含若干具体规则。当 `runAgent()` 显式提供 `allowedTools` 时，会建立两层权限作用域模型：子 Agent 先受自身工具白名单限制，再受父级和全局权限系统限制。这样子 Agent 不能因为隔离而获得更多权限。

这些隔离模式位于一个设计空间中的不同点。SWE-Agent 和 OpenHands 使用容器级隔离，把执行环境作为边界；Claude Code 则主要使用上下文、工具和权限隔离，把子 Agent 作为同一 harness 内的隔离运行单元。

每个子 Agent 都把自己的 transcript 写入单独 `.jsonl` 文件，并带有 `.meta.json` 元数据文件（`sessionStorage.ts`）。`runAgent()` 函数接受 21 个参数，覆盖 Agent 定义、提示、权限、工具、模型、上下文来源和运行时选项。

只返回摘要是一个有意的上下文保存选择：基于对话的框架常常让子任务完整历史进入父上下文，而 Claude Code 只把子 Agent 输出摘要返回给父级，避免父窗口被子任务细节填满。

在多实例 Agent 团队协调中，harness 使用文件锁，而不是消息代理或集中式调度器。这延续了系统偏好：用简单、文件化、可审计机制解决运行时协调问题。

# 9 会话持久化与恢复

编码 Agent 中的会话持久化涉及一个设计选择：使用追加式日志、结构化数据库、检查点快照，还是以版本控制为中心的历史记录。Claude Code 选择了以追加式 JSONL transcript 为核心的持久化模型，并把它与压缩边界、文件历史检查点、恢复、分叉和子 Agent 侧链 transcript 结合起来。

回到 auth 测试示例，执行到这一节时，会话已经包含原始提示、工具调用、工具结果、权限决策、可能的压缩边界以及若干文件读取或编辑。Claude Code 的持久化机制把对话（消息、工具结果和压缩边界）写入项目特定路径下的 transcript，并允许之后恢复、分叉或回滚文件历史。

## 9.1 Transcript 模型

会话 transcript 以基本追加式 JSONL 文件形式存储在项目特定路径下，同时存在显式分支与恢复机制。路径通常根据当前工作目录推导，例如通过 `getOriginalCwd()` 和相关函数生成项目目录。三个持久化通道独立运行：

1. 会话 transcript：保存当前会话中的消息、工具结果、压缩标记和其他事件。
2. 全局提示历史：保存在 `history.jsonl` 中，用于跨会话提示历史。
3. 子 Agent 侧链 transcript：每个子 Agent 拥有单独 `.jsonl` 和 `.meta.json` 文件。

会话 transcript 不只保存简单消息，还保存压缩标记、文件编辑历史、工具使用摘要、tombstone 消息、sidechain 关联和恢复所需元数据。图 8 把 live session state、context window、transcript persistence、compaction boundary 和 file checkpoints 区分开来，说明会话运行态和持久化日志之间并非一一等同。

会话身份系统把 `sessionId` 与 `sessionProjectDir` 成对使用，在恢复或分支时一起设置。transcript 路径必须使用写入消息时的同一项目目录，否则恢复会指向错误日志。这种设计让同一个 session 在不同目录下不会被误混。

## 9.2 Resume、Fork 与不恢复权限

`--resume` 标志通过重放 transcript 重建对话（`conversationRecovery.ts`）。Fork 操作从现有 transcript 派生新分支，使用户可以从某个历史点继续。恢复逻辑会重建消息、压缩边界和上下文，但不会恢复会话作用域权限。这是安全设计：用户先前批准的临时权限不会在新进程或新分支中静默延续。

`compact_boundary` 标记被精心设计以配合持久化。`annotateBoundaryWithPreservedSegment()`（`compact.ts`）在边界中记录 `headUuid`、`anchorUuid` 和 `tailUuid`，使系统能够知道压缩摘要对应原始历史中的哪个片段。这样恢复时既可以保留摘要，也可以理解被压缩内容的范围。

Claude Code 中的“checkpoints”是用于 `--rewind-files` 的文件历史检查点，存储在 `~/.claude/file-history/` 下。它们不是完整会话状态快照，而是文件系统变更的恢复机制。因此，系统同时拥有对话 transcript 和文件历史 checkpoint 两条线：前者恢复交互历史，后者支持文件回退。

前面各节记录了 Claude Code 对循环架构、安全、扩展、上下文、委派和持久化等设计问题的回答。下一节把这些回答与 OpenClaw 作比较。

# 10 比较分析：Claude Code 与 OpenClaw

前几节描述了 Claude Code 对一系列重复出现的设计问题的回答。为了说明这些问题并非 Claude Code 独有，本节将其与 OpenClaw 对比。OpenClaw 是一个开源的多通道个人助理网关。它回答了许多相同问题，但部署上下文不同：Claude Code 是本地 CLI/SDK/IDE 编码 Agent，强调代码库内自主执行；OpenClaw 是多渠道网关，强调接入多个入口、多个服务、多个个人助理能力以及边界级控制。

## 10.1 六个比较维度

论文从六个维度比较二者。

**1. 循环架构。** Claude Code 把所有入口面汇聚到一个共享 `queryLoop()`，模型驱动工具调用并迭代执行。OpenClaw 更像网关控制平面中的嵌入式运行时：请求来自多个通道，先进入网关层，再由路由、权限、工具和服务注册系统分发。Claude Code 的中心是“单个 CLI agent loop”，OpenClaw 的中心是“多通道入口 + 网关编排”。

**2. 安全边界。** Claude Code 采用逐动作安全评估：每个工具调用都会经过权限规则、hook、自动分类器和沙箱。OpenClaw 更偏向边界级访问控制，在网关层定义谁能访问哪些能力、哪些工具或哪些服务。前者适合用户在本地与 Agent 共同工作、逐步提升信任；后者适合在多入口系统中统一治理能力暴露。

**3. 扩展模型。** Claude Code 有 MCP、插件、技能、hook 四种机制。OpenClaw 更关注网关级能力注册：工具、知识源、通道和外部服务作为网关能力被注册、发现和调用。二者都需要可扩展性，但 Claude Code 的扩展围绕单次 agent loop 的上下文成本和工具表面组织；OpenClaw 的扩展围绕多服务、多通道和平台级治理组织。

**4. 上下文与记忆。** Claude Code 把上下文窗口作为主要稀缺资源，围绕 `CLAUDE.md`、工具 schema、对话历史和压缩流水线管理上下文。OpenClaw 则更强调跨通道、跨服务的个人助理记忆和能力路由。Claude Code 的主要问题是如何不让代码任务上下文溢出；OpenClaw 的主要问题是如何让网关在多个入口和服务之间共享足够相关的上下文。

**5. 委派与多 Agent。** Claude Code 的子 Agent 是父 Agent 内的隔离工作单元，通过 `AgentTool` 生成并摘要返回。OpenClaw 的多 Agent 更接近网关内多个能力或服务的协作，关注跨系统路由、能力发现和用户会话连续性。Claude Code 使用子 Agent 隔离来节省上下文并降低污染；OpenClaw 使用网关调度来组织多能力协同。

**6. 持久化与审计。** Claude Code 使用追加式 JSONL transcript、文件化 `CLAUDE.md` 和文件历史 checkpoint。OpenClaw 更可能使用服务注册、网关日志、用户配置和跨通道状态持久化。Claude Code 的持久化偏向本地、可检查、开发者可版本化；OpenClaw 的持久化偏向平台级可管理和多通道可恢复。

## 10.2 这种对比揭示了什么

Claude Code 与 OpenClaw 的对比说明，同样的设计问题会因为部署上下文而得到不同架构答案。

当 Agent 是本地编码工具时，主要风险来自具体动作：删除文件、运行命令、泄露代码、错误修改代码库。因此 Claude Code 把安全放在每个动作前，采用细粒度权限、hook 和沙箱。

当 Agent 是网关时，主要风险来自能力边界：哪个渠道、哪个用户、哪个服务能够访问哪些能力。因此 OpenClaw 更强调入口认证、能力注册、网关级策略和边界控制。

当 Agent 面向代码任务时，上下文窗口是核心瓶颈；当 Agent 面向多渠道助理时，能力发现和跨服务状态是核心瓶颈。

当 Agent 需要在本地代码库中执行时，append-only transcript、文件 checkpoint 和 `CLAUDE.md` 可见记忆有很强价值；当 Agent 需要跨平台服务时，网关日志、服务注册和通道抽象更重要。

这种对比并不是说明一种架构优于另一种，而是说明“Agent 系统设计空间”由部署环境、产品目标、安全要求和用户假设共同塑造。未来系统可能会融合二者：既具有 Claude Code 式的细粒度动作安全和上下文管理，也具有 OpenClaw 式的网关能力注册、跨通道治理和平台级协作。

# 11 讨论

## 11.1 设计哲学

Claude Code 的核心设计哲学可以概括为：让模型负责推理，让 harness 负责执行与约束。它不把推理逻辑编码成显式状态图，也不在系统侧维护复杂规划器，而是提供一个强操作环境：工具、权限、上下文压缩、hook、技能、MCP、子 Agent、持久化和恢复。

这种设计与“最小脚手架、最大操作性 harness”的原则一致。系统相信越来越强的模型可以在合适工具和上下文中自由推理，而固定流程图可能过早限制模型能力。与此相对，LangGraph 等框架更偏向开发者显式定义状态转换；SWE-Agent/OpenHands 更强调执行环境隔离；Aider 更强调 Git 安全网。

Claude Code 的选择带来一个张力：模型自由度高，但可预测性较弱；harness 强大，但系统复杂性主要转移到模型周围的基础设施。论文认为，这正是现代 Agent 系统的重要特征：agent loop 本身很小，真正的工程量在 loop 周围。

## 11.2 价值张力

五个价值之间存在张力。

人类决策权与能力放大之间存在张力：更多审批意味着更强人类控制，但也会降低效率并导致审批疲劳。Claude Code 通过渐进权限模式、自动分类器和沙箱尝试平衡。

安全与上下文适应性之间存在张力：允许用户和插件扩展系统能提高适配性，但也增加攻击面。Claude Code 用多层权限、hook 生命周期、MCP 前缀规则和沙箱降低风险。

可靠执行与上下文压缩之间存在张力：压缩可以延长任务 horizon，但可能丢失细节，导致模型误解历史。Claude Code 使用多层压缩和可见边界，但压缩仍然可能改变模型可用证据。

能力放大与长期人类能力保存之间也存在张力。AI 让开发者更快完成任务，但可能降低他们对代码库的理解。论文把长期人类能力保存作为评估透镜，而不是 Claude Code 明确设计驱动。

## 11.3 架构权衡

论文指出若干架构权衡。

第一，分层安全依赖层之间相互独立，但现实中它们可能共享失败模式。例如，为避免 UI 卡顿，复杂 shell 命令可能回退到通用批准提示，削弱细粒度拒绝规则。

第二，文件化记忆提高透明性，但不如向量数据库或结构化数据库灵活。用户可以审计 `CLAUDE.md`，但模型仍需要把大块文本作为上下文读取。

第三，子 Agent 隔离节省父上下文并降低污染，但摘要返回可能丢失重要中间证据。父 Agent 必须信任子 Agent 摘要。

第四，单一 query loop 简化了系统一致性，但不同界面可能有不同需求。一个统一循环让 CLI、SDK、IDE 共享行为，却牺牲了针对特定界面的优化空间。

第五，压缩流水线延长了任务可执行时间，但引入新故障模式：摘要错误、边界误设、缓存估算偏差和历史片段丢失。

## 11.4 经验预测与早期信号

基于源码和文档分析，论文提出若干经验预测。

如果上下文管理是核心瓶颈，那么更长上下文模型会减少压缩频率，但不会消除压缩需求，因为工具输出、历史噪声和长任务结构仍会制造上下文压力。

如果权限疲劳是真问题，那么单纯增加提示不会提高安全性，反而应通过自动分类器、沙箱和默认拒绝规则减少对用户注意力的依赖。

如果子 Agent 隔离有效，那么复杂任务中使用子 Agent 应该降低父上下文污染，但可能增加摘要错误导致的间接失败。

如果文件化记忆促进适应性，那么长期用户会逐步积累更丰富的 `CLAUDE.md` 和技能配置，并在项目层面形成可复用工作流。

早期信号包括用户 auto-approve 率随会话数量上升、Claude Code 任务中相当比例属于“没有工具就不会尝试的工作”，以及用户通过插件、MCP 和技能逐步扩展系统。

## 11.5 局限性

论文的方法主要是源代码分析，辅以官方文档和社区分析。这意味着结论反映可见实现，而不一定覆盖 Anthropic 内部不可见设计、实验或部署配置。源码版本也会变化，因此某些文件名、特性标志和工具数量可能随版本更新而改变。

此外，本文关注架构和设计空间，而不是大规模用户研究或定量性能评测。它解释系统如何组织，但不能单独证明某种设计在所有任务上更优。

## 11.6 新兴方向

论文从 Claude Code 的设计中抽象出若干正在出现的方向。第一，Agent harness 的边界正在扩展：早期编码助手只在 IDE 内补全文本，而 Claude Code 这样的系统已经能够运行命令、编辑文件、调用外部服务并委派子 Agent。第二，安全机制正从单点确认转向多层策略组合：权限规则、hook、自动分类器、沙箱和可恢复日志共同构成安全姿态。第三，上下文管理正在从简单截断转向分层压缩、懒加载和显式记忆层级。第四，扩展机制正在从单一工具 API 转向 MCP、插件、技能、hook、`CLAUDE.md` 和子 Agent 等多层扩展表面。第五，未来系统需要把观察、评估、治理和长期人类能力纳入架构一等公民。

这些方向说明，Agent 系统已经不再只是“调用模型的脚本”。它们更像小型操作系统或运行时：维护状态、组装上下文、仲裁权限、加载扩展、调度工具、记录历史，并把模型嵌入一个受控执行环境中。

## 11.7 反复出现的设计选择

论文总结出一组在多个 Agent 系统中反复出现的设计选择：

- 核心循环应当是简单反应式循环，还是显式状态图、搜索树或规划器？
- 安全边界应当在每个动作前评估，还是通过容器、网关或版本控制统一处理？
- 扩展机制应当统一为工具 API，还是拆分为工具、技能、hook、插件和协议？
- 上下文应当通过截断、摘要、折叠、检索还是外部记忆管理？
- 子任务应当共享父上下文，还是在隔离子 Agent 中执行？
- 状态持久化应当使用数据库、快照、追加日志还是 Git 式历史？
- 用户信任应当固定，还是随长期使用逐步演化？

Claude Code 的回答是：单一反应式循环、逐动作权限门、多机制扩展、渐进上下文管理、隔离子 Agent、追加式 transcript，以及渐进信任模式。OpenClaw 在许多问题上选择了不同答案，说明这些设计不是唯一最优，而是受部署场景塑造。

# 12 未来方向

基于 Claude Code 的设计空间分析和与 OpenClaw 的对比，论文提出六个开放方向。

## 12.1 静默失败与可观察性—评估鸿沟

Agent 系统的一个核心问题是：它们可能表面上成功，实际上失败。模型会生成自信解释、工具会返回部分结果、测试可能覆盖不足、用户可能没有仔细审查。Claude Code 提供 transcript、工具结果和 hook，但仍缺少系统级评估层来持续判断 Agent 的工作是否真正正确。

未来系统需要更强的可观察性和评估基础设施：记录为什么采取某动作、哪些证据支持结论、哪些工具结果被忽略、哪些测试真正验证了修改。还需要把评估器从普通提示词变成 Agent loop 的结构化组成部分，使系统在声明完成前能自动执行独立验证。

这种方向与“生成—执行—验证”分离有关。当前 Agent 往往由同一个模型生成方案并评价自身结果，容易产生自我确认偏差。未来可能需要独立 evaluator、外部测试 oracle、可执行规范和反事实检查。

## 12.2 持久性：记忆与纵向同事关系

随着 Agent 被长期使用，它不只是一次性工具，而会变成某种“纵向同事”。Claude Code 通过 `CLAUDE.md`、自动记忆、history 和 session resume 提供一些持续性，但这些机制仍主要面向项目上下文和会话恢复。

未来 Agent 需要更丰富的跨会话记忆：理解用户偏好、项目历史、团队约定、过去失败、长期目标和持续计划。同时，记忆必须可审计、可编辑、可删除，并且需要处理隐私与安全边界。

这种长期记忆不应只是向量检索或摘要数据库。Agent 需要知道哪些记忆可信、何时过期、是否来自用户明确授权、是否适用于当前项目，以及是否可能与新信息冲突。记忆系统因此会成为 Agent-native 的数据管理系统，而不只是 RAG 附件。

## 12.3 Harness 边界演化：Agent 在哪里、何时、做什么、与谁一起行动

Claude Code 的 harness 已经允许模型读写文件、运行 shell、调用 MCP、生成子 Agent。未来 harness 边界会继续扩展：Agent 可能跨越本地机器、云环境、远程仓库、CI/CD、浏览器、IDE、数据库、企业系统和多用户协作空间。

这会带来四个问题：

- Agent 在哪里行动？本地、容器、远程 VM、云服务还是浏览器？
- Agent 何时行动？只在用户请求时，还是后台持续运行？
- Agent 做什么？只是编辑代码，还是部署、迁移数据、修改配置、处理生产事件？
- Agent 与谁一起行动？单用户、团队、多个 Agent、外部服务还是组织治理系统？

边界扩展会放大安全和治理问题。逐动作权限可能不足以管理跨系统行为，纯容器隔离也不能覆盖外部服务副作用。未来需要将权限、身份、审计、资源限制、组织策略和人类审批工作流整合进 harness。

## 12.4 Horizon 扩展：从会话到科学项目

Claude Code 的设计支持多 turn 编码任务和一定的长期会话恢复，但未来 Agent 可能要处理更长 horizon：持续数天、数周甚至数月的软件项目、研究项目或科学计划。

长 horizon 带来不同问题：目标会变化，环境会变化，依赖会更新，先前决策会变成技术债。上下文压缩无法单独解决这个问题，因为问题不只是“记住更多”，而是“维护长期计划、假设、证据、实验结果和决策理由”。

未来系统需要项目级记忆、里程碑、任务图、假设跟踪、实验日志、失败复盘和可验证进展指标。Agent 需要知道不仅当前要做什么，还要知道为什么之前那样做、哪些约束仍有效、哪些结果已经被证伪。

## 12.5 大规模治理与监督

当 Agent 从个人工具进入组织环境，治理成为核心。谁可以启用哪些工具？哪些操作需要审批？哪些数据不能进入模型？哪些日志必须保留？怎样追责？怎样在多个用户和多个 Agent 之间管理权限？

Claude Code 的权限模式、hook 和 transcript 提供了基础，但组织级治理需要更多：集中策略管理、合规审计、密钥管理、数据分类、访问控制、风险分级、审批队列、异常检测和回滚机制。

未来 Agent 系统可能会像数据库、云平台和 CI/CD 系统一样拥有治理平面。这个平面不仅控制工具，还控制模型、上下文、记忆、扩展、数据访问和部署目标。

## 12.6 重新审视评估透镜：长期人类能力

本文把长期人类能力保存作为评估透镜。Claude Code 显著放大短期能力，但也可能带来理解衰退、监督能力下降和代码库认知断层。研究发现，AI 辅助条件下开发者对代码理解测试得分可能更低，这提示“完成任务”不等于“提升人类能力”。

未来 Agent 系统需要显式支持人类学习和理解。例如：

- 在完成任务后解释关键决策和代码变更原因。
- 生成可审查的证据链，而不仅是最终补丁。
- 提醒用户哪些部分值得亲自阅读。
- 在高风险修改前要求用户确认设计理解，而非简单点击批准。
- 维护代码库长期一致性，避免 Agent 只优化局部任务。

这不是要降低自动化能力，而是要让能力放大与人类成长兼容。未来 Agent 的成功指标不应只包括任务通过率和速度，还应包括开发者理解、团队知识保留、代码库可维护性和长期信任。

# 13 相关工作

## 13.1 编码 Agent 分类

编码 Agent 研究从自动补全、聊天式助手发展到能够执行工具的自主系统。GitHub Copilot 代表补全式辅助；Cursor 等 IDE 助手把对话和编辑整合到开发环境；Claude Code、Devin、SWE-Agent、OpenHands、Aider 等系统进一步把模型连接到 shell、文件系统、测试和外部服务。

这些系统可以按几个维度分类：是否显式规划、是否使用容器隔离、是否依赖版本控制回滚、是否支持多 Agent、是否有持久记忆、是否提供扩展协议、是否把人类审批作为核心安全机制。Claude Code 的独特之处在于：核心 loop 很薄，但周边 operational harness 很厚；它结合权限、hook、沙箱、压缩、MCP、技能、插件和子 Agent，而不是只依赖单一机制。

SWE-Agent 和 OpenHands 常以容器环境作为执行边界，强调 benchmark 中任务解决能力。Aider 深度依赖 Git 工作流，强调对代码修改的可逆性。LangGraph 强调显式状态图和可控 orchestration。Claude Code 更强调模型自由推理与 harness 执行约束之间的分离。

## 13.2 Agent 架构模式

Agent 架构模式包括 ReAct 式循环、计划-执行、状态图、树搜索、编排器-工作者、评估器-优化器、工具调用框架和多 Agent 协作。Claude Code 核心采用 ReAct 式反应循环，但在子 Agent 上使用编排器-工作者模式，在工具执行上使用并发读/串行写，在压缩上使用分层管线，在安全上使用多层策略。

相关研究讨论了工具使用、长上下文管理、RAG、Agent 记忆、沙箱执行、权限模型、Prompt injection 防御、多 Agent 协调和 AI 辅助开发的用户行为。本文的贡献不是提出新算法，而是通过源码分析把这些模式组织为一个生产系统的设计空间。

论文还把 Claude Code 与 OpenClaw 对比，说明 Agent 架构不能脱离部署场景。CLI 编码 Agent、IDE 助手、网关型个人助理、企业自动化平台和研究型 benchmark Agent 会对同样问题给出不同答案。

# 14 结论

本文对 Claude Code 的公开 TypeScript 源码进行了系统性架构分析，并将其与 OpenClaw 进行对比，以刻画当今与未来 AI Agent 系统的设计空间。分析显示，Claude Code 的核心并不是复杂规划器，而是一个简单的 agentic while-loop：调用模型、执行工具、把结果送回循环并重复。系统的大部分复杂性位于循环周围：权限系统、上下文压缩、扩展机制、子 Agent 委派、持久化、恢复和执行环境。

论文识别了五个驱动架构的价值和哲学：人类决策权、安全与隐私、可靠执行、能力放大、上下文适应性。它进一步把这些价值映射到十三个设计原则，并追踪到具体实现选择。Claude Code 的架构体现了一个重要趋势：现代 Agent 系统的核心能力不是模型调用本身，而是围绕模型构建的操作性 harness。

与 OpenClaw 的比较表明，同样的设计问题在不同部署上下文下会产生不同答案。Claude Code 面向本地编码工作流，因此强调逐动作权限、上下文窗口管理、本地文件化记忆和子 Agent 隔离。OpenClaw 作为多通道个人助理网关，则更强调网关级访问控制、能力注册和跨服务路由。这种对比说明，未来 Agent 系统不会只有一种标准架构，而会根据部署环境、用户关系、安全边界和任务 horizon 形成不同组合。

本文最后提出六个开放方向：可观察性与评估鸿沟、跨会话持久记忆、harness 边界演化、从会话到长期项目的 horizon 扩展、大规模治理与监督，以及长期人类能力保存。总体而言，Claude Code 代表了一类正在形成的 Agent-native 系统：它们把模型放在一个可扩展、可治理、可恢复、可审计的运行时中。未来更强大的 Agent 系统需要在能力放大、安全、可靠性、适应性和人类长期能力之间取得更成熟的平衡。

# 附录 C：术语说明

**Agent loop**：模型、工具和结果之间的迭代循环。模型生成下一步动作，harness 执行动作，结果进入下一轮。

**Harness**：围绕模型的运行时基础设施，包括权限、工具、上下文、扩展、执行、持久化和恢复。

**Tool use**：模型通过结构化协议请求调用工具，harness 负责校验和执行。

**MCP**：Model Context Protocol，用于把外部工具和资源接入 Agent。

**Skill**：由 `SKILL.md` 定义的领域能力包，通常包含说明、允许工具、参数提示和执行配置。

**Hook**：在生命周期事件或工具执行前后运行的外部化拦截机制。

**Subagent**：通过 `AgentTool` 生成的隔离 Agent，执行子任务并向父 Agent 返回摘要。

**Compaction**：在上下文压力下压缩、折叠或裁剪历史内容的机制。

**Transcript**：会话持久化日志，通常以 JSONL 形式追加写入。
