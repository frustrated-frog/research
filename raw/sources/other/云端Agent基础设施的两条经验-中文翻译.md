# 云端 Agent 基础设施的两条经验

> 原文来源：用户粘贴文本，来自 X 链接 `https://x.com/intuitiveml/status/2062699747224568212`  
> 翻译日期：2026-06-07  
> 类型：中文完整翻译

今天大多数 Agent 框架默认假设的是桌面环境：一个用户，一台机器，一个进程。Agent 在笔记本打开时运行，写入本地文件系统，把 API key 放在环境变量里，终端关闭时它也随之死亡。出了问题，用户就重试。Agent 需要某个包时，`pip install` 会把它装进用户自己的 Python 环境里。状态、密钥和生命周期，全都位于同一个可信边界之内。

云端 Agent 基础设施没有这些奢侈条件。

Agent 运行在一个全新启动的沙箱里，底层硬件和陌生人共享，触发它运行的调用方甚至可能是用户从未见过的东西：一个定时任务、一个 HTTP 请求、另一个 Agent。运行发生时，用户通常正在睡觉。沙箱里的代码可能是恶意的。文件系统必须能跨部署存活。凭证不能和 Agent 住在同一个地方。桌面环境免费给你的每一项保证：持久化、身份、网络信任、重试，在云端都必须被重建成显式系统。

过去几个月，我们在 CREAO 一直在加固这一层。从中得出了两条经验。如果你曾经发布过桌面 Agent，并好奇它迁移到云端后会发生什么变化，那么变化就在这里。

## 经验一：把变化慢的东西和变化快的东西分开

在桌面上，用户的环境和 Agent 的运行时是同一件事：由同一个人、以同一个节奏更新。在云端，它们不是。

一个 Agent 应用会在平台侧积累状态。比如一个股票分析 Agent 安装了 `matplotlib`，下载了市场数据，写了绘图脚本。这个环境就是 Agent 的肌肉记忆。当用户对它满意的那一刻，我们会把它冻结成一个沙箱快照，并一直保持这个快照冻结，直到用户再次编辑环境。每次运行都从同一份镜像启动。同样的包、同样的文件、同样的版本。周一的运行会表现得像周五的运行一样，因为底下没有任何东西移动过。

这是桌面框架无法免费给你的属性。六个月前的一次 `pip install`，今天可能解析出不同版本。云端快照解析到的则永远是同一批字节。可复现性是平台欠用户的一项能力，而冻结快照是提供这项能力最便宜的方式。

然后，耦合问题出现了。

同一份冻结用户环境的镜像里，也包含 runner 代码，也就是我们开发的一小段 harness 库，用来在每次运行中管理 Agent。用户希望他们的环境保持不变。我们希望自己的 runner 一天发布很多次。一个 artifact，两个完全相反的需求。

我们最开始的修复很粗暴。启动时，检查快照里的 runner 是否和我们刚部署的版本一致。如果不一致，就丢弃这个快照，从一个干净模板启动。这个方案能工作，也没人抱怨。损害只发生在部署后的第一次运行。

无人值守运行打破了这个遮掩。周一早上 9 点的 cron job，不应该因为我们 8 点 55 分部署过一次，就丢失自己的环境。我们其实一直在悄悄违反一个契约：“你的环境会保持冻结，直到你自己修改它。”

真正的修复，我们花了比本应更多的时间才看清。用户环境和 runner 代码的变化节奏完全不同。用户在他们选择的时候编辑自己的 Agent。我们一天部署平台很多次。把它们当成同一个 artifact，意味着每次部署都被迫做一个选择：要么保留过期的 runner 代码，要么摧毁用户明确要求我们保留的冻结环境。

我们最终采用的模型，借鉴了操作系统处理更新的方式。内核会变化，你的 home 目录不会。你不会为了安装一个安全补丁而擦掉整块磁盘。

我们画出了同样的边界。沙箱从用户冻结的快照启动，保持不动。然后，我们只热替换 runner。流程如下：

1. 在沙箱内的临时目录中放置新的 runner。
2. 用 `node --check` 验证它，确保任何语法错误都会在触碰线上代码前被捕获。
3. 原子地替换进去：先解除旧 runner 上的 immutable 标记，把新的复制过去，再用 `chattr +i` 重新加锁，最后隐藏 `chattr` 二进制本身，防止沙箱里的代码反向解除锁定。
4. 清除 V8 编译缓存，也就是 `/home/user/.cache/v8-compile-cache/*`，确保新文件真的会加载，而不是运行陈旧字节码。
5. 如果任何一步失败，就杀掉这个沙箱，并用新的沙箱重试。绝不让半升级状态运行 Agent。

整个替换大约需要 300 毫秒。只有当 runner 代码确实发生过替换，并且运行成功后，我们才会重新生成快照，把更新后的代码烘进用户镜像里，这样下一次运行就完全跳过热替换。平台部署永远不会丢弃用户状态；它们只会把新的 runner 折叠进用户状态里。用户的包、文件和自定义内容都会不变地向前延续。

如果你只从这条经验里带走一件事，那就是这个诊断问题：对于云平台中任何你要持久化的 artifact，都要问：谁控制它的变化节奏？如果用户和平台共同拥有它，你最终一定会为这种耦合付出代价。沿着所有权边界拆开 artifact，让双方按自己的时钟更新。

## 经验二：让密钥远离执行边界

这是把云端 Agent 基础设施和其他所有东西区分开的经验。

桌面 Agent 以用户身份运行。它使用用户的 key，在用户的机器上，访问用户的网络。云端 Agent 不以任何具体人身份运行，它运行在共享硬件上，面向开放互联网，并执行由 LLM 根据提示词写出的代码，而提示词可能是恶意的。安全模型必须假设沙箱里的代码已经被攻破，而不是祈祷它没被攻破。

我们坚持的规则很简单：任何长期凭证都不能存在于沙箱内部。

当 Agent 需要调用某个需要鉴权的服务，比如 Slack、GitHub，或者用户自己的 API，它不持有 token。它会向沙箱外部的 API bridge 发送一个本地 HTTP 请求。bridge 在宿主侧附加 OAuth token，然后转发调用。响应再返回，而 token 从未进入沙箱的内存或环境变量。

有意思的部分是：bridge 怎么知道这个沙箱有权发起请求？这里有两个检查，故意分层。

第一层是 IP allowlist。bridge 只接受来自我们沙箱宿主所在内网网段的连接。来自其他任何地方的调用，不管是开发者笔记本、泄露的 URL，还是公网，都会在网络层被丢弃，甚至不会进入应用代码。这把 bridge 绑定在一组具体物理基础设施上，让它对外部任何人都毫无用处。

第二层是每次运行签发一个短生命周期 JWT。沙箱启动时，平台会签发一个 token，作用域限定到这一次具体运行：哪个用户、哪个 app、哪个 session，过期时间只覆盖这次运行窗口，不多给一分。沙箱每次调用 bridge 时都出示这个 token。bridge 验证签名、检查过期时间，然后才解析用户存储的凭证，并在服务端附加它们。如果沙箱被劫持，攻击者继承到的也只是一个会随本次运行一起死亡的 token，并且只授权这一个 session 范围内的调用。没有任何 master credential 可以被偷走。

同一个 bridge 也负责把计费扣减、日志和指标带出去，所以它是唯一一个双向跨越沙箱边界的接口。沙箱内部的其他一切，默认都被视为已经被攻破。

如果明天某个 prompt injection 说服 Agent 把 `process.env` dump 到某个 webhook，攻击者拿到的也只是一个短生命周期 JWT，而且这个 JWT 只能从我们的内网里使用，并且会随本次运行过期。正是这个性质，让我们能够在共享基础设施上运行不可信用户代码，同时还能睡得着。

## 底层模式

可靠、安全的云端 Agent 基础设施并不是一个新奇系统。它只是少数几个性质被无例外地坚持住：

- 状态存在于沙箱里，冻结到用户修改为止。
- 代码可以热替换，并且独立于状态。
- 凭证存在于宿主侧，永远不在 Agent 内部。
- 所有调用方都走同一条执行流水线，不管触发者是人、调度器，还是另一段软件。

最后一个性质是整个设计的关键。一个 `executeAgent` 函数处理 UI 点击、定时运行和 API 调用。计费系统、扣除 credit 的日志、可观测信号，无论是人点击了 Run、cron 触发了任务，还是脚本调用了 API，全都完全一致。增加一个新的触发入口，只是路由变化，不是架构变化。Agent 本身不知道，也不关心是谁拉动了触发器。

这是桌面框架无法给你的，也是云端版本值得构建的原因。笔记本上的 Agent 受限于那台笔记本。云端的 Agent 是你的技术栈其余部分可以调用的一个函数。用户只写一次。平台负责让它跨部署存活，在共享硬件上安全运行，并接受用户从未预料过的调用方。

Agent 是一个带自然语言接口的函数。它的实现属于用户。它的触发面、运行时和安全边界属于平台。纪律就在于：把各层构建成可以按自己的时钟独立演进，并花时间在别人发现之前，先找到系统之间的裂缝。

这就是让下一个入口既便宜发布、又安全发布的原因。
