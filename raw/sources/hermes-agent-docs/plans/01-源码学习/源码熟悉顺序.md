# Hermes 源码熟悉顺序

## 目标

- 用最短路径建立对 Hermes 主体架构的整体认识
- 先搞清楚“主循环、扩展点、状态流”，再进入 JD 改造
- 为后续 memory / plugin / A2UI / design-context 改造提供统一阅读顺序

## 建议阅读顺序

### 1. 先看总览文档

- `AGENTS.md`

重点理解：

- Hermes 的核心目录分布
- Agent、CLI、Gateway、TUI、Tools、Plugins 各自职责
- 哪些文件是真正的主入口

### 2. 再看 Agent 主循环

- `run_agent.py`

重点理解：

- `AIAgent` 初始化时做了哪些能力装配
- `run_conversation()` 如何驱动一轮完整对话
- 模型回复、工具调用、工具结果回填、循环退出条件
- memory provider、context compressor、plugin hook 在主循环的接入点

这是后续所有改造的第一核心文件。

### 3. 再看工具注册与执行链

- `model_tools.py`
- `tools/registry.py`
- `toolsets.py`

重点理解：

- 工具是如何被发现、注册、过滤、分组的
- tool schema 最终如何暴露给模型
- 工具调用时是如何被 dispatch 的
- toolset 开关和平台能力控制怎么做

如果以后要把 A2UI 能力做成 tool / CLI / hook，这一层必须先吃透。

### 4. 再看插件系统

- `hermes_cli/plugins.py`
- `plugins/`
- `website/docs/guides/build-a-hermes-plugin.md`

重点理解：

- Hermes 的通用 plugin 是怎么发现和加载的
- `register_tool`、`register_hook`、`register_command`、`register_skill` 的行为
- plugin hook 生命周期有哪些
- 哪些东西适合做成插件，哪些不适合

JD 扩展层大概率会以这个机制为主要入口。

### 5. 再看记忆体系

- `agent/memory_provider.py`
- `agent/memory_manager.py`
- `plugins/memory/__init__.py`
- `plugins/memory/*`

重点理解：

- 内建记忆和外部记忆 provider 如何共存
- provider 的生命周期、tool schema、prefetch、sync、shutdown
- 当前 memory provider 是怎么配置和切换的
- Redis / Postgres 接入未来应该落在哪一层

### 6. 再看上下文压缩

- `agent/context_engine.py`
- `agent/context_compressor.py`
- `plugins/context_engine/__init__.py`

重点理解：

- Hermes 默认 compaction 怎么做
- 压缩触发条件、摘要生成、压缩后上下文如何回填
- 自定义 context engine 能替换哪部分能力
- 如果要做“结构化 goal card 防漂移”，最适合落哪一层

### 7. 再看 skills 体系

- `hermes_cli/skills_hub.py`
- `tools/skills_hub.py`
- `tools/skills_tool.py`
- `skills/`

重点理解：

- skill 的搜索、安装、查看、触发链路
- skill 和 tool / plugin / prompt 注入的边界
- 哪些 A2UI 能力应该做 skill，哪些不该做

### 8. 再看 MCP 能力

- `tools/mcp_tool.py`
- `mcp_serve.py`
- `tests/tools/test_mcp_tool.py`

重点理解：

- Hermes 当前如何接 MCP server
- 工具发现、调用、稳定性处理怎么做
- 后续 `jd-design-context` MCP 应该如何接入

### 9. 再看 delegation / subagent

- `tools/delegate_tool.py`
- `tests/tools/test_delegate.py`

重点理解：

- 子代理任务如何被创建和回收
- 上下文、工具集、主会话边界如何隔离
- 哪些 JD 任务适合 delegation，哪些必须主链完成

### 10. 再看 API Server

- `gateway/platforms/api_server.py`
- `tests/gateway/test_api_server.py`
- `tests/gateway/test_api_server_jobs.py`

重点理解：

- `/v1/runs`、事件流、SSE 的实现方式
- Hermes 原生 API 层已经提供了哪些能力
- 如果以后适配 `/api/chat`，应该复用哪一层，而不是另起炉灶

### 11. 最后看 CLI / Gateway / TUI 外围

- `cli.py`
- `hermes_cli/main.py`
- `gateway/run.py`
- `tui_gateway/server.py`

重点理解：

- 平台层如何把用户输入送进主循环
- 会话持久化、命令路由、平台特定行为的组织方式
- 哪些改造应该停留在平台层，哪些应该下沉到 agent 内核

## 第一轮阅读产出建议

第一轮不要急着改代码，先产出下面 4 份认知清单：

1. Hermes 主循环时序图

3. JD 改造应该新增的最小扩展层目录
