# Harness 六大组件全解析

## 一、核心公式：Agent = Model + Harness

### 1.1 什么是 Agent

"Agent" 被用滥了——每个能调用 API 的聊天机器人都自称 Agent。但回到最朴素的定义：

> **Agent 是一个能够自主感知环境、做出决策、执行行动并从结果中学习的智能体。**

四个关键动词：**感知、决策、执行、学习**。

裸模型严格来说只能做"决策"这一步。它不能主动感知外部世界，不能真正执行行动，更不能持久化学习。

真正的 Agent 必须是这样的结构：

```
Agent = Model + Harness
```

- **Model** 是大脑，负责"想"
- **Harness** 是大脑之外的一切——感官系统、运动系统、记忆系统、能量系统——负责让"想"变成"做"

### 1.2 Harness 到底是什么

Harness 的英文原意是"挽具"，就是套在马身上、让马的力量转化为拉车动力的那套装备。

类比精准：**模型是马，Harness 是挽具，Agent 是马+挽具+车的整体系统。**

技术化地说，Harness 是**模型之外的一切工程基础设施**：
- 模型如何接收输入（上下文构建）
- 模型的输出如何被解析和执行（工具调用、代码执行）
- 模型如何获取外部信息（搜索、API）
- 模型如何记住之前发生的事（记忆机制）
- 模型如何与其他模型或子系统协作（编排）
- 贯穿所有环节的安全、格式、质量约束（Hooks）

```
┌──────────────────────────────────────┐
│         Model（大脑）                  │
│   ┌────────────────────────────────┐ │
│   │ System Prompt（神经系统）        │ │
│   └────────────────────────────────┘ │
│  ┌─────┐ ┌──────┐ ┌──────┐ ┌──────┐ │
│  │文件 │ │ Bash │ │记忆  │ │搜索  │ │
│  │系统 │ │+沙箱│ │AGENTS│ │+MCP  │ │
│  └─────┘ └──────┘ └──────┘ └──────┘ │
│  ┌──────────────────────────────────┐ │
│  │ 上下文工程（注意力管理）           │ │
│  └──────────────────────────────────┘ │
│  ┌──────────────────────────────────┐ │
│  │ 编排 + Hooks（多Agent协同）       │ │
│  └──────────────────────────────────┘ │
└──────────────────────────────────────┘
```

## 二、裸模型的四个硬伤

### 2.1 硬伤一：无法维持跨会话状态

最容易被感知的痛点：聊了两小时，讨论了复杂架构，关掉窗口，第二天回来——什么都不记得。

这不是"记忆力差"，是根本没有记忆机制。裸模型的每一次对话都是一个全新的开始，前一轮的所有上下文在会话结束的瞬间灰飞烟灭。

对于需要持续推进的工作，这是致命的——每次都从头解释背景，每次都重新建立共识。

### 2.2 硬伤二：无法执行代码

裸模型可以"写"代码，但不能"跑"代码。它无法验证代码是否正确运行，无法在真实数据集上证明自己的分析。

更深层的问题：没有代码执行能力，模型就失去了 **"写→跑→看→修→再来"** 的自我验证循环。

> 一个不能运行自己代码的 AI 编程助手，就像一个只能在纸上画图纸但从来不去工地的建筑师——理论上无懈可击，实践中漏洞百出。

**实测数据**：具备自我验证循环的 Agent 任务完成率比"一次性生成"高出 **40%–60%**。这个差距完全来自 Harness 层的 Bash 能力，不来自更好的模型。

### 2.3 硬伤三：无法获取实时知识

大语言模型的知识有"截止日期"。截止日期之后的一切——新发布的 API 文档、最新的安全漏洞、上周刚更新的框架版本——它统统不知道。

在前端框架半年一个大版本、开源库 Breaking Change 防不胜防的环境下，裸模型可能用过时信息给出自信但错误的答案。

这就是"幻觉"（Hallucination）的重要来源之一：不是模型"故意"胡说，而是知识库里根本没有正确答案，于是"推理"出了一个看起来合理但实际错误的答案。

### 2.4 硬伤四：无法搭建工作环境

裸模型没有文件系统，没有工作空间，没有项目目录。它不能创建文件，不能组织代码结构，不能管理依赖，不能运行构建工具。

**工程不是写代码，工程是在正确的位置写正确的代码，并确保它与其他代码正确协作。** 没有工作环境，"工程"无从谈起。

### 2.5 四个硬伤的对应关系

| 硬伤 | 缺失的能力 | Harness 对应组件 |
|------|-----------|----------------|
| 无法维持跨会话状态 | 长期记忆 | 文件系统 + 记忆（AGENTS.md） |
| 无法执行代码 | 行动能力 | Bash + 沙箱 |
| 无法获取实时知识 | 感知能力 | Web Search + MCP |
| 无法搭建工作环境 | 环境操控 | 文件系统 + 上下文工程 + 编排 |

## 三、组件一：文件系统——最基础的原语

### 3.1 为什么是"最基础原语"

文件系统排在第一位，不是因为最炫酷，恰恰相反——它最朴素、最基础，基础到很多人压根没意识到它是一个"组件"。

但正是这个最朴素的组件，决定了 Agent 能力的上限。

人类程序员第一件事是打开 IDE、加载项目目录。文件系统是一切工程活动的地基。

对于 AI Agent 来说，文件系统的意义甚至比对人类更大——因为 Agent 的上下文窗口是有限的（即使是 200K token），文件系统是 Agent 突破上下文窗口限制的**唯一途径**。

### 3.2 文件系统的三大核心能力

**第一：工作空间与中间结果存储**

Agent 执行复杂任务时会产生大量中间产物——分析报告草稿、代码半成品、数据处理结果、决策记录。这些需要一个地方存放，以便后续步骤引用。

没有文件系统：Agent 必须把所有中间产物都塞进上下文窗口，浪费 token 且容易超限。
有了文件系统：Agent 可以把中间产物写入文件，需要时再读取，实现"按需加载"。

**第二：Agent 协作的基础**

当任务需要多个 Agent 协同时，文件系统成了它们之间的"共享白板"：
- Agent A 把分析结果写入文件
- Agent B 读取文件并在此基础上继续工作
- 这种基于文件的异步协作模式：简单、可靠、可追溯

**第三：版本追踪与错误回滚**

当文件系统与 Git 集成后，Agent 的每一步操作都可以被记录、追溯、回滚。

> 这给了 Agent"试错"的能力。没有这个能力，Agent 只能小心翼翼一步步走；有了这个能力，Agent 可以大胆尝试——反正随时可以回滚。这极大地释放了模型的创造力。

### 3.3 文件系统的设计原则

**目录结构要清晰且约定俗成**：使用标准化的目录结构（src/components、src/utils 约定），显著降低 Agent 的认知负担。

**文件粒度要适中**：太大的文件会超出 Agent 处理能力；太小的文件会增加管理复杂度。**一个文件对应一个"模块"或"职责单元"**是比较好的粒度。

**元数据要丰富**：文件名要有意义，目录要有 README，关键决策要有 ADR（Architecture Decision Records）。这些元数据是 Agent 理解"为什么这样组织"的线索。

## 四、组件二：Bash + 沙箱——从"说"到"做"

### 4.1 从"生成代码"到"执行代码"的质变

一个终端（Bash）环境意味着 Agent 可以：
- 运行它自己写的代码
- 安装依赖包
- 执行构建命令
- 运行测试套件
- 查看运行时错误并调试

**没有 Bash，Agent 是一个"提建议"的顾问；有了 Bash，Agent 是一个"动手做"的工程师。**

### 4.2 自我验证循环

这是 Bash 赋予 Agent 的最核心能力——**"写→跑→看→修→再来"** 循环。

没有这个循环：Agent 的输出质量完全依赖模型的"一次性生成"能力——推理正确就对了，推理错误就全错。

有这个循环：Agent 拥有了自我纠错能力，它可以从自己的错误中学习。

### 4.3 为什么必须是"沙箱"

有了 Bash 还需要沙箱，因为 Agent 执行的代码不一定是安全的：
- 可能无意中执行 `rm -rf /`
- 可能下载了恶意包
- 可能发起了未授权的网络请求

沙箱提供隔离的执行环境：

| 隔离类型 | 作用 |
|---------|------|
| 资源限制 | CPU、内存、磁盘上限，防止死循环拖垮系统 |
| 网络隔离 | 默认禁止外部网络访问，防止数据泄露 |
| 文件系统隔离 | Agent 只能访问工作目录，不能接触宿主机敏感文件 |
| 超时机制 | 执行时间超阈值自动终止 |

> **沙箱不是一个可选的"安全加固措施"，它是 Bash 能力的必要前提。**

### 4.4 沙箱技术选型

| 方案 | 特点 | 适用场景 |
|------|------|---------|
| **Docker 容器** | 隔离性好，生态成熟，镜像管理方便 | 大多数 Agent 框架（Devin、OpenHands） |
| **gVisor / Firecracker** | 轻量虚拟化，启动速度毫秒级 | 需要频繁创建/销毁沙箱的场景 |
| **WebAssembly (WASM)** | 浏览器端/边缘计算有潜力 | 系统调用支持还不够完善 |
| **Nix / 纯函数式环境** | 声明式环境定义，完全可重现 | 杜绝"在我机器上能跑"问题 |

## 五、组件三：记忆（AGENTS.md）——不改权重也能加知识

### 5.1 AGENTS.md 的工作机制

AGENTS.md 的设计理念：**工作中写入知识，存文件，下次自动注入。**

```
写入阶段 → Agent 在工作过程中产生有价值的知识 → 写入 AGENTS.md
存储阶段 → 文件存放在项目文件系统中（根目录或子目录）
注入阶段 → 下一次 Agent 启动时，Harness 自动读取并注入上下文
```

### 5.2 核心洞察：上下文注入 = 不改权重给模型加知识

传统上，给模型"加知识"需要微调——修改模型权重参数。成本高、周期长、存在灾难性遗忘风险。

AGENTS.md 提供了一条捷径：**不碰模型权重，只通过上下文注入来添加知识。**

```
模型 = 原来的模型
但它"看到"的信息变了 → 它的行为也变了
```

这就像一种"即插即用"的知识扩展机制：
- 今天发现新的最佳实践
- 写进 AGENTS.md
- 明天 Agent 自动具备了这个知识
- 不需要重新训练，不需要等模型供应商更新

### 5.3 AGENTS.md 的最佳实践

**层次化存放**：
- 根目录 AGENTS.md：全局知识（项目概述、核心架构决策、团队规范）
- 子目录 AGENTS.md：局部知识（该模块的特殊约定、已知问题、接口规范）
- Agent 进入某目录工作时，同时加载全局和局部的知识

**结构化书写**：
- 项目架构
- 技术约束
- 编码规范
- 已知陷阱（Gotchas）
- 决策记录（ADR）

**定期清理**：过时的知识比没有知识更危险。定期审查和清理 AGENTS.md 是保持有效性的关键。

**双向可编辑**：AGENTS.md 不仅是 Agent 写给自己的备忘录，也是人类与 Agent 之间的"知识契约"。

### 5.4 AGENTS.md 的本质

它让 Agent 拥有了跨会话的长期记忆，而且这种记忆是：
- **透明的**：人类可以直接阅读和编辑
- **可控的**：可以随时增删改
- **可审计的**：配合 Git 可以追溯每一次知识变更

## 六、组件四：Web Search + MCP——突破知识的"时间牢笼"

### 6.1 知识的截止日期

每个大语言模型都有一个知识截止日期。这个日期之后的世界，对模型来说是一片空白。

在专业工作场景中，这是严重限制：

- Bug 修复方案在模型训练之后才被社区发布
- API 在上个月做了 Breaking Change
- 竞品昨天刚发布了新产品

在这些场景中，裸模型不仅帮不了你，还可能用过时的信息**自信地给出错误的答案**——这比"不知道"更危险。

### 6.2 Web Search：打开信息的大门

Web Search 不仅仅是"接个搜索 API"。一个好的 Web Search 组件需要解决：

**查询构建**：模型的自然语言表述不一定是好的搜索查询。Harness 需要帮助模型把模糊的意图转化为精准的搜索关键词。

**结果筛选**：搜索引擎返回结果质量参差不齐。Harness 需要帮助模型过滤低质量来源，优先使用权威文档。

**内容提取**：网页内容通常包含大量无关信息（广告、导航栏、侧边栏）。Harness 需要提取核心内容并以模型友好的格式呈现。

**信息整合**：当 Agent 需要综合多个来源的信息时，Harness 需要帮助处理信息冲突、去重、排序。

### 6.3 MCP：从"搜索"到"触"

如果说 Web Search 让 Agent 能"看"互联网，那么 **MCP（Model Context Protocol）** 让 Agent 能"触"互联网。

MCP 是 Anthropic 2024 年底推出的开放协议，定义了 AI 模型与外部工具、数据源之间的标准化交互方式。可以理解为"AI 世界的 USB 接口"——只要工具遵循 MCP 规范，就可以即插即用地接入任何支持 MCP 的 Agent。

MCP 把 Agent 的"感知范围"从公开互联网扩展到了任何可编程的数据源和服务：
- 数据库
- 内部 Wiki
- 项目管理工具（Jira、Linear）
- 代码仓库（GitHub）
- 监控系统（Datadog、Grafana）

### 6.4 Web Search + MCP 的协同效应

```
Agent 需要修复一个生产环境 Bug：

MCP 连接监控系统 → 获取错误日志和堆栈信息
MCP 连接代码仓库 → 查看相关代码和最近的变更历史
Web Search 搜索错误信息 → 查找社区中类似问题的解决方案
MCP 连接项目管理工具 → 检查是否有相关的已知问题
Agent 综合所有信息 → 生成修复方案并提交 PR
```

## 七、组件五：上下文工程——对抗 AI 系统的"熵增"

### 7.1 Context Rot：上下文的"腐烂"

随着对话进行，上下文窗口中积累越来越多的信息——早期指令、中间讨论、工具调用记录、错误修复过程——这些信息像沉积物一样不断堆积，导致：

| 问题 | 影响 |
|------|------|
| 信噪比下降 | 重要信息被冗余内容淹没，注意力分散 |
| 矛盾信息累积 | 早期决定可能已被推翻，但旧信息仍在上下文中 |
| Token 浪费 | 无用历史信息占据宝贵上下文空间 |
| 推理质量退化 | 即使相关信息就在上下文中，模型提取能力也显著下降 |

> 这就是所谓的"大海捞针"（Needle in a Haystack）问题的实践版。

### 7.2 上下文工程的核心策略

**压缩（Compression）**：定期对历史上下文进行摘要压缩。把冗长的工具调用记录替换为简洁的结果摘要，把详细讨论过程替换为最终结论。像是给上下文做"垃圾回收"。

**工具输出卸载（Tool Output Offloading）**：工具调用输出是上下文膨胀的主要来源。上下文工程把这些输出存储到文件系统，在上下文中只保留摘要和文件引用。需要详细信息时，Agent 可以随时重新读取。

**Skills 渐进加载**：不同任务阶段需要不同的知识和能力。根据当前任务阶段，动态加载和卸载相关的 Skill 定义，避免一次性把所有信息都塞进上下文。

**分层上下文结构**：
- **核心层**：System Prompt、关键约束，始终保留
- **工作层**：当前任务相关信息，按需更新
- **历史层**：已完成任务的摘要，逐渐压缩

### 7.3 上下文工程是 Harness 的"元能力"

上下文工程有一个特殊的地位——**它不是 Harness 的一个独立功能模块，而是影响所有其他组件的"元能力"**：

- 文件系统的读写操作需要上下文工程来决定"读什么"和"什么时候读"
- 记忆的注入需要上下文工程来决定"注入多少"和"注入哪些"
- Web Search 的结果需要上下文工程来决定"保留什么"和"丢弃什么"
- 编排中的子 Agent 通信也依赖上下文工程来构建高效的信息传递格式

> **Harness 本质上就是好的上下文工程的交付机制。**

这也解释了为什么"上下文工程"在 2025 年底开始取代"Prompt 工程"成为 AI 工程领域的核心话题——后者关注"怎么写指令"，前者关注"怎么构建模型看到的全部信息"。

## 八、组件六：编排 + Hooks——从单兵作战到集团军

### 8.1 为什么需要编排

当任务复杂度超过单个 Agent 的处理能力时，需要把任务分解为多个子任务，分配给不同的子 Agent 处理，然后把结果汇总。这就是编排。

编排解决的核心问题：

| 问题 | 说明 |
|------|------|
| 子 Agent 调度 | 哪个子任务分配给哪个 Agent？依赖关系是什么？哪些可以并行？ |
| 任务分发 | 如何把模糊的大任务拆解为明确的小任务？ |
| 模型路由 | 简单格式转换用小模型，复杂架构设计用大模型 |
| 结果聚合 | 多个子 Agent 返回结果后，如何检查一致性、解决冲突？ |

### 8.2 Hooks：注入确定性

编排解决了"谁做什么"的问题，Hooks 则解决了"做得对不对"的问题。

在 Agent Harness 中，Hooks 在 Agent 行为的关键节点插入确定性检查，确保输出符合预期：

| Hook 类型 | 作用 |
|----------|------|
| **Lint 检查** | Agent 生成代码后自动运行 linter，不符合规范则要求修复 |
| **截断续接** | 检测到输出被截断，自动触发续接请求 |
| **格式约束** | JSON Schema 验证、Markdown 结构检查、API 响应格式校验 |
| **安全过滤** | 敏感操作前进行权限检查和安全审计 |
| **成本控制** | 监控 token 消耗，接近预算上限时发出警告 |

> **Hooks 的核心价值：用确定性的规则约束了概率性的模型输出。**

模型输出本质上是概率性的——可能正确，可能犯错。Hooks 在模型输出的"出口"设置了一道关卡，用确定性的规则把不合格的输出拦截下来。

这种**"概率性生成 + 确定性校验"**的组合模式，是当前 Agent 工程中最有效的质量保障策略之一。

### 8. 3 编排模式的演进

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **线性管道** | Agent A 输出作为 Agent B 输入，依次传递 | 步骤明确、依赖清晰的任务 |
| **DAG 编排** | 有向无环图定义依赖关系，支持并行 | 比线性管道更灵活高效 |
| **动态编排** | 编排器 Agent 根据上一步结果动态决定下一步 | 最灵活，但也最难控制质量和成本 |
| **层级编排** | 编排器本身层级嵌套，适合超大规模复杂任务 | 高层编排器 → 中层编排器 → 执行 Agent |

### 8.4 Hooks 与编排的关系

无论选择哪种编排模式，**Hooks 都是不可或缺的质量保障机制**。两者共同构成了多 Agent 协同的质量和效率基础。

## 九、System Prompt——贯穿所有组件的"神经系统"

System Prompt 不是 Harness 的"第七个组件"，但它是贯穿所有六个组件的"神经系统"。

### 9.1 四个关键角色

**定义角色边界**：告诉模型"你是谁"和"你不是谁"。不是简单的角色扮演，而是在定义 Agent 的能力边界和行为约束。

**注入领域知识**：项目背景、技术栈选型、核心业务逻辑——直接写在 System Prompt 中，确保 Agent 从第一轮对话开始就具备必要的领域知识。

**约束安全规则**：哪些操作允许，哪些禁止；哪些数据可以读取，哪些是敏感的；遇到不确定情况怎么处理。这些安全规则通过 System Prompt 直接"刻"进 Agent 的行为模式。

**贯穿所有组件**：
- 影响文件系统：定义文件的组织规范和命名约定
- 影响 Bash 执行：限制可执行的命令范围
- 影响记忆写入：规定知识记录的格式和标准
- 影响搜索行为：设置搜索的优先来源和可信度标准
- 影响上下文管理：定义信息的优先级和压缩策略
- 影响编排逻辑：规定任务分解的粒度和协作规范

### 9.2 System Prompt 与 AGENTS.md 的关系

两者是互补关系：
- **System Prompt**：装"必须知道的"（容量有限）
- **AGENTS.md**：装"最好知道的"（容量无限制）

> 写 System Prompt 就是在设计 Harness 的行为规范。一个好的 System Prompt 就像一部好的公司章程——它不直接做任何事，但它决定了所有事怎么做。

## 十、核心洞察总结

### 10.1 文章核心公式

> **Agent = Model + Harness**
> 模型提供智能，Harness 让智能变得有用。

### 10.2 裸模型四大硬伤与 Harness 组件对应

```
硬伤1：无法维持跨会话状态     → 文件系统 + AGENTS.md
硬伤2：无法执行代码            → Bash + 沙箱
硬伤3：无法获取实时知识        → Web Search + MCP
硬伤4：无法搭建工作环境        → 文件系统 + 上下文工程 + 编排
```

### 10.3 六大组件总览

```
Harness 六大组件
├── 组件1：文件系统
│   ├── 工作空间与中间结果存储
│   ├── Agent协作基础（共享文件）
│   └── 版本追踪与错误回滚（Git）
│
├── 组件2：Bash + 沙箱
│   ├── 自我验证循环（写→跑→看→修→再来）
│   ├── 沙箱隔离（资源/网络/文件系统/超时）
│   └── 沙箱技术选型（Docker/gVisor/WASM/Nix）
│
├── 组件3：记忆（AGENTS.md）
│   ├── 工作中写入知识 → 存文件 → 下次自动注入
│   ├── 上下文注入 = 不改权重给模型加知识
│   └── 层次化 + 结构化 + 定期清理 + 双向可编辑
│
├── 组件4：Web Search + MCP
│   ├── 查询构建 + 结果筛选 + 内容提取 + 信息整合
│   ├── MCP = AI世界的USB接口（数据库/Wiki/Jira/GitHub）
│   └── 协同效应：多信息源穿梭，快速定位和解决问题
│
├── 组件5：上下文工程
│   ├── Context Rot：信息腐烂导致推理质量退化
│   ├── 压缩 + 工具输出卸载 + Skills渐进加载 + 分层结构
│   └── 元能力：影响所有其他组件
│
└── 组件6：编排 + Hooks
    ├── 子Agent调度 + 任务分发 + 模型路由 + 结果聚合
    ├── Hooks：Lint + 续接 + 格式约束 + 安全过滤 + 成本控制
    └── 概率性生成 + 确定性校验 = Agent工程质量保障
```

### 10.4 关键洞察

1. **Harness 不是锦上添花，是对裸模型致命缺陷的系统性补救。** 没有 Harness 的 Model，就像没有身体的大脑——可以思考，但无法存在于这个世界。

2. **模型决定了 Agent 能力的下限，Harness 决定了 Agent 能力的上限。**

3. **真正在生产环境中创造价值的，往往不是那个最强的模型，而是那个最好的 Harness。**

4. **如果你不是模型本身，那你就是 Harness 的一部分。** 你写的 System Prompt 是 Harness 的神经系统，搭建的工具链是 Harness 的四肢，设计的记忆机制是 Harness 的长期记忆，优化的上下文策略是 Harness 的注意力管理，编写的 Hook 规则是 Harness 的质量底线。

5. **Harness 的工程空间还几乎没有被充分探索。** 文件系统怎么设计才能最大化 Agent 效率？上下文工程有没有最优压缩算法？编排模式怎样才能在成本和质量之间取得完美平衡？记忆机制能否实现真正的"终身学习"？这些问题的答案，不在模型的论文里，而在 Harness 的工程实践中。
