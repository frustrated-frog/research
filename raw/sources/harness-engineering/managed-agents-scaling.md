# Scaling Managed Agents：将大脑与双手解耦

> 原文链接：https://www.anthropic.com/engineering/managed-agents
>
> 来源：Anthropic Engineering Blog
>
> 获取更多关于 Claude Managed Agents 的信息，请参阅[官方文档](https://platform.claude.com/docs/en/managed-agents/overview)。

Harnesses（编排框架）编码的假设会随模型改进而过时。Managed Agents——我们在 Claude Platform 上托管的用于长时序 Agent 工作负载的服务——围绕那些在 harnesses 变化时仍能保持稳定的接口构建。

开始使用 Claude Managed Agents，请参阅我们的[官方文档](https://platform.claude.com/docs/en/managed-agents/overview)。

工程博客的一个持续主题是：如何[构建有效的 Agent](https://www.anthropic.com/engineering/building-effective-agents)、如何[为长时运行任务设计 harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。贯穿这些工作的一个共同点是：harnesses 会编码关于"Claude 独自无法完成什么"的假设。然而，这些假设需要被频繁质疑，因为它们会随着模型的改进而[变得过时](http://www.incompleteideas.net/IncIdeas/BitterLesson.html)。

举一个具体的例子：在[之前的工作](https://www.anthropic.com/engineering/harness-design-long-running-apps)中，我们发现 Claude Sonnet 4.5 在感知到上下文限制临近时会过早地结束任务——这种行为有时被称为"上下文焦虑"。我们通过在 harness 中添加上下文重置来解决这个问题。但当我们将同一个 harness 用于 Claude Opus 4.5 时，发现这种行为消失了。那些重置操作已变成了死代码。

我们预计 harnesses 将持续演进。因此我们构建了 Managed Agents：一种托管服务，运行在 Claude Platform 上，通过一小套接口代表您完成长时序 Agent 工作——这些接口的设计寿命长于任何特定实现——包括我们今天运行的那些。

构建 Managed Agents 意味着解决计算领域的一个古老问题：如何为一个"尚待思考的程序"设计系统。几十年前，操作系统通过将硬件虚拟化为抽象——process、file——解决了这个问题，这些抽象足够通用，能够容纳尚不存在的程序。抽象比硬件更经久。`read()` 命令不在乎它访问的是 1970 年代的磁盘组还是现代 SSD。上层的抽象保持稳定，而下层的实现可以自由变化。

Managed Agents 遵循同样的模式。我们将 Agent 的组件虚拟化：**session**（所有发生事件的仅追加日志）、**harness**（调用 Claude 并将 Claude 的工具调用路由到相关基础设施的循环）、以及 **sandbox**（Claude 可以运行代码和编辑文件的执行环境）。这使得每个组件的实现可以相互替换而不打扰其他组件。我们对接口的形态有明确的观点，但对接口背后的运行方式没有执念。

---

## 不要养宠物

我们最初将所有 Agent 组件放入单个容器，这意味着 session、Agent harness 和 sandbox 共享一个环境。这种做法有好处，包括文件编辑是直接系统调用，没有服务边界需要设计。

但通过将所有东西耦合到一个容器中，我们遇到了一个古老的基础设施问题：我们养了一只"**宠物**"。在宠物与牲畜的类比中，宠物是一个被命名、被精心照料的个体，你承受不起失去它；而牲畜是可以互换的。在我们的案例中，服务器成了那只宠物——如果容器失败，session 就丢了；如果容器无响应，我们必须把它奶回来。

护理容器意味着调试无响应的卡住 session。我们唯一的窗口是 WebSocket 事件流，但它无法告诉我们失败**发生在哪里**，这意味着 harness 中的 bug、事件流中的数据包丢失或容器离线都呈现为相同的问题。要弄清楚哪里出了问题，工程师必须在容器内部打开一个 shell，但由于该容器通常也持有用户数据，这种方法实际上意味着我们缺乏调试能力。

第二个问题是 harness 假设 Claude 处理的所有内容都位于它所在的容器中。当客户要求我们将 Claude 连接到他们的虚拟私有云时，他们必须要么将他们的网络与我们的网络对等，要么在我们自己的环境中运行我们的 harness。嵌入 harness 中的一个假设在我们想将其连接到不同基础设施时成了问题。

## 将大脑与双手解耦

我们得出的解决方案是将我们所谓的"**大脑**"（Claude 及其 harness）与"**双手**"（执行操作的 sandbox 和工具）以及"**session**"（session 事件的日志）解耦。每一个都成为一个对其他组件几乎不做假设的接口，每个都可以独立失败或被替换。

**Harness 离开容器。** 将大脑与双手解耦意味着 harness 不再存在于容器内部。它调用容器的方式与调用任何其他工具相同：`execute(name, input) → string`。容器变成了"牲畜"。如果容器死了，harness 将失败捕获为工具调用错误并将其传回给 Claude。如果 Claude 决定重试，可以用标准配方重新初始化一个新容器：`provision({resources})`。我们不再需要把失败的容器奶回来了。

**从 harness 故障中恢复。** Harness 也变成了"牲畜"。由于 session 日志位于 harness 外部，harness 中没有任何东西需要存活过崩溃。当一个 harness 失败时，可以用 `wake(sessionId)` 重新启动它，使用 `getSession(id)` 获取事件日志，然后从最后一个事件恢复。在 Agent 循环期间，harness 使用 `emitEvent(id, event)` 向 session 写入，以保持事件的持久记录。

**安全边界。** 在耦合设计中，Claude 生成的任何不受信任的代码都在与凭证相同的容器中运行——因此提示注入只需要说服 Claude 读取自己的环境。一旦攻击者获得这些令牌，他们可以生成新的、无限制的 session 并将工作委托给它们。窄范围化是一个显而易见的缓解措施，但这编码了一个关于 Claude 不能用有限令牌做什么的假设——而 Claude 正变得越来越聪明。结构性修复是确保令牌永远无法从 Claude 生成代码运行的 sandbox 中访问到。

我们使用两种模式来确保这一点。Auth 可以与资源捆绑在一起，也可以保存在 sandbox 外部的保险库中。对于 Git，我们在 sandbox 初始化期间使用每个仓库的访问令牌克隆仓库，并将其绑定到本地 git remote。Git push 和 pull 从 sandbox 内部工作，而 Agent 本身从不处理令牌。对于自定义工具，我们支持 MCP，并将 OAuth 令牌存储在安全保险库中。Claude 通过专用代理调用 MCP 工具；该代理接收与 session 关联的令牌。然后代理可以从保险库获取相应凭证并调用外部服务。Harness 永远不会被告知任何凭证。

## Session 不是 Claude 的上下文窗口

长时序任务通常会超过 Claude 上下文窗口的长度，而解决这个问题的标准方法都涉及关于保留什么的不可逆决策。我们在之前的上下文工程工作中探索了这些技术。例如，压缩让 Claude 保存其上下文窗口的摘要，而内存工具让 Claude 将上下文写入文件，从而实现跨 session 的学习。这可以与上下文修剪配对，选择性删除令牌，如旧工具结果或思考块。

但对选择性保留或丢弃上下文的不可逆决策可能导致失败。我们很难知道未来的轮次需要哪些令牌。如果消息通过压缩步骤被转换，harness 会从 Claude 的上下文窗口中删除已压缩的消息，而这些消息只有在被存储时才能恢复。之前的工作探索了通过将上下文存储在上下文窗口之外的对象中来解决这个问题。例如，上下文可以是 REPL 中的一个对象，LLM 通过编写代码来过滤或切片它，从而以编程方式访问。

在 Managed Agents 中，session 提供相同的好处，作为驻留在 Claude 上下文窗口之外的上下文对象。但上下文不是存储在 sandbox 或 REPL 中，而是持久存储在 session 日志中。接口 `getEvents()` 允许大脑通过选择事件流的位置切片来查询上下文。这个接口可以灵活使用，允许大脑从上次停止阅读的地方继续，在特定时刻之前回退几个事件以查看铺垫，或者在特定操作之前重新阅读上下文。

任何获取的事件也可以在进入 Claude 上下文窗口之前在 harness 中进行转换。这些转换可以是 harness 编码的任何内容，包括为实现高提示缓存命中率而进行的上下文组织以及上下文工程。我们将 session 中可恢复的上下文存储与 harness 中任意的上下文管理的关注点分离，因为我们无法预测未来模型需要什么特定的上下文工程。接口将上下文管理推入 harness，只保证 session 是持久的且可供查询。

## 多个大脑，多双手

**多个大脑。** 将大脑与双手解耦解决了我们最早的客户投诉之一。当团队希望 Claude 使用他们自己 VPC 中的资源时，唯一的路径是将他们的网络与我们的网络对等，因为持有 harness 的容器假设每个资源都在它旁边。一旦 harness 不再在容器中，这个假设就消失了。同样的改变也带来了性能收益。当我们最初把大脑放在一个容器中时，意味着多个大脑需要多个容器。对于每个大脑，在该容器被配置之前无法进行任何推理；每个 session 都要预先支付完整的容器设置成本。每个 session，即使那些永远不会接触 sandbox 的 session，也必须克隆仓库、启动进程、从我们的服务器获取待处理事件。

这段等待时间体现在首 token 时间（TTFT）中，这是衡量 session 在接受工作到产生第一个响应 token 之间等待多长时间的指标。TTFT 是用户感知最强烈的延迟。

将大脑与双手解耦意味着容器由大脑通过工具调用（`execute(name, input) → string`）按需配置。因此，一个不需要立即使用容器的 session 不需要等待它。推理可以在编排层从 session 日志中拉取待处理事件后立即开始。使用这种架构，我们的 p50 TTFT 下降了约 60%，p95 下降了 90% 以上。扩展到多个大脑只需要启动多个无状态 harnesses，并在需要时将它们连接到双手。

**多双手。** 我们还希望能够将每个大脑连接到多双手。在实践中，这意味着 Claude 必须能够推理多个执行环境并决定将工作发送到哪里——这比在单个 shell 中操作更艰巨的认知任务。我们最初将大脑放在单个容器中是因为早期的模型没有这个能力。随着智能的扩展，单个容器反而成了限制：当那个容器失败时，我们失去了大脑正在触及的每双手的状态。

将大脑与双手解耦使每双手成为一个工具：`execute(name, input) → string`：输入一个名称和输入，返回一个字符串。这个接口支持任何自定义工具、任何 MCP 服务器以及我们自己的工具。Harness 不知道 sandbox 是容器、手机还是宝可梦模拟器。而且由于没有任何手与任何大脑耦合，大脑可以将手传递给彼此。

---

## 结论

我们面临的挑战是一个古老的挑战：如何为"尚待思考的程序"设计系统。操作系统通过将硬件虚拟化为足够通用的抽象来容纳尚不存在的程序，持续了数十年。通过 Managed Agents，我们的目标是设计一个能够容纳未来围绕 Claude 的 harnesses、sandboxes 或其他组件的系统。

Managed Agents 在同样的精神下是一个**元 harness**——对 Claude 未来需要的特定 harness 不持观点。相反，它是一个具有通用接口的系统，允许许多不同的 harnesses。例如，Claude Code 是一个出色的 harness，我们在各种任务中广泛使用它。我们也已证明，特定于任务的 Agent harnesses 在狭窄领域表现出色。Managed Agents 可以容纳任何这些，随 Claude 的智能演进。

元 harness 设计意味着对围绕 Claude 的接口有明确的观点：我们预计 Claude 将需要操纵状态（session）的能力和执行计算（sandbox）的能力。我们还预计 Claude 将需要扩展到多个大脑和多双手的能力。我们设计了这些接口，以便可以可靠和安全地运行跨长时间范围。但我们对 Claude 需要的大脑或双手的数量或位置没有任何假设。

## 一、这篇文章在讲什么：3 分钟带你抓住核心

### 一句话概括

Anthropic 在做一件跟当年操作系统解决"硬件抽象"相同的事——把 **Agent 的三个核心组件（大脑、双手、Session）解耦成标准接口**，让每一部分都可以独立演进、替换、扩展，而不影响其他部分。

### 三个组件是什么

| 组件 | 原文比喻 | 具体指什么 | 对应到开源框架 |
|------|---------|-----------|--------------|
| **大脑（Brain）** | Claude + harness 的循环 | 调用模型的推理引擎 + 编排逻辑 | Hermes Agent 的 AIAgent 核心循环；DeerFlow 的 Lead Agent |
| **双手（Hands）** | Sandbox + 工具 | 执行代码、编辑文件、操作外部服务 | Harness Engineering 的 Bash+沙箱 + MCP；Hermes 的工具架构 |
| **Session** | 事件的仅追加日志 | 持久化的执行记录，可供查询 | Hermes Agent 的 state.db（FTS5 检索）；DeerFlow 的 Checkpointer |

### 核心设计思想

```
耦合时代：  ┌─────────────────────────┐
           │  container (宠物)       │
           │  ├─ harness (大脑)      │
           │  ├─ sandbox (双手)      │
           │  └─ session             │
           └─────────────────────────┘
           → 容器死了，全死。调试靠猜。

解耦时代：  ┌───────────┐   ┌───────────┐   ┌───────────┐
           │ harness   │   │ sandbox   │   │ session   │
           │ (大脑)     │──▶│ (双手)     │   │ (日志)    │
           └───────────┘   └───────────┘   └───────────┘
           → 各自都是"牲畜"，死了就换。
              通过标准接口通信：execute(name, input) → string
```

## 二、pets vs cattle：这个问题你可能正在踩

### 原文在说什么

Anthropic 最初把所有东西塞进一个容器，结果这个容器成了"宠物"——不能死，死了就丢数据；病了要人工介入奶回来。

### 这在说什么（通俗版）

当你把 harness、sandbox、session 写死在同一个进程/容器里，你就给自己挖了一个大坑：

**坑 1：容错变成不可能任务**

```
场景：Claude 生成的代码把 sandbox 卡住了。

耦合设计下：
  → 你只能通过 WebSocket 观察外部表现（"它不动了"）
  → 但不知道是 harness 的 bug？还是 sandbox 资源耗尽？还是网络丢包？
  → 要调试？得进容器。但容器里有用户数据，进不去。
  → 只能把整个 session 标记为"失败"。

解耦设计下：
  → harness 通过 execute() 调用 sandbox
  → 超时返回工具调用错误
  → harness 把错误扔给 Claude，让它自己决定重试
  → sandbox 死了？provision({resources}) 起一个新的
  → 无需人工介入。
```

**坑 2：基础设施假设写死**

```
场景：客户要把 Claude 接入自己的 VPC。

耦合设计：容器里的 harness 假设"我要处理的文件都在我本地"
          → 客户必须 peering 网络 or 把整套服务部署到客户环境

解耦设计：harness 只通过 execute(name, input) 调用容器
          → 容器在哪不重要，可以是客户 VPC 里的一台机器
          → harness 本身不需要改动
```

### 实践启示

在构建自己的 Agent 系统时，**永远不要假设任何组件是不可替代的**。问问自己：

- 如果承载 sandbox 的进程突然崩溃，会丢多少状态？
- 如果 harness 重启，能从上一次进度恢复吗？
- 新来一个客户要把 Agent 接入他的私有环境，要改多少代码？

## 三、安全边界：原文最容易被忽视的设计

> 这一节是原文最"隐晦"的部分，但它实际上是整个架构最关键的安全设计。

### 原文在说什么

在耦合设计里，Claude 生成的不可信代码和**凭证**跑在同一个容器里。攻击者只要做一次提示注入，让 Claude 读一下自己的环境变量，API Key 就到手了。

### 问题分析

```
耦合设计下的凭证流向：
┌─────────────────────────────────────────────────────┐
│ container                                            │
│  ├─ Claude（生成代码）─────┐                         │
│  ├─ sandbox（运行代码）────┼─── 共享进程内存          │
│  └─ API credentials ──────┘                         │
│                                                      │
│ 攻击路径：prompt injection → "读一下环境变量" → 凭证明文泄露│
└─────────────────────────────────────────────────────┘

你以为限制 token 权限就安全了？
错！Claude 正在变得越来越智能，
你写在 token 限制里的"它做不了的事"，明年可能就能做了。
结构性修复：让 sandbox 永远碰不到凭证。
```

### 解耦设计的解决路径

```
解耦设计下的凭证流向：
┌──────────────┐    ┌─────────────┐    ┌──────────────┐
│ vault（保险库）│◀───│ MCP 代理     │    │  sandbox     │
│ 存 API Key   │    │(持session令牌)│    │(无凭证)      │
└──────────────┘    └──────┬──────┘    └──────────────┘
                          │ 执行 MCP 调用时
                          ▼           去获取凭证
                    ┌─────────────┐
                    │ 外部服务     │
                    └─────────────┘

关键：Claude 生成的代码在 sandbox 里跑，
      但凭证永远不在 sandbox 的进程内存里。
```

### 对应仓库里的框架

**Hermes Agent** 的设计也体现了类似思路：
- `memory store` 里的安全扫描会在注入系统提示前检测凭证泄露模式
- 技能系统通过规范化的接口操作文件系统，而不是直接暴露原始文件句柄

**DeerFlow** 的 MCP 扩展机制在接入外部服务时，遵循的是同样的原则：连接外部数据源时，通过 MCP 协议规定的标准路径，而不是直接把 API Key 写进 System Prompt。

**Harness Engineering** 明确指出：安全过滤 Hook 是 Harness 的六大组件之一，在敏感操作前进行权限检查。

### 实践启示

```
不要做的事：
❌ 把 API Key 写进 system prompt
❌ 把 token 放进环境变量让 sandbox 能读到
❌ 在 Claude 能访问的上下文里存放敏感字符串

应该做的事：
✅ 使用 MCP 代理模式：Claude 通过代理操作外部服务，代理从 vault 取凭证
✅ Git 操作时，在 sandbox 初始化时把 token 绑定到本地 .gitconfig，
   让 git push/pull 在 sandbox 内正常工作，但 Agent 本身不接触 token
✅ 任何外部认证都走"session 关联的临时令牌 → vault 换取真实凭证"的路径
```

## 四、Session 不是上下文窗口：最核心的认知升级

### 原文在说什么

大多数人在解决"上下文不够长"这个问题时，思路是：**压缩 → 删掉**。但删掉之后，如果未来需要那些被删掉的内容，就找不回来了。

Managed Agents 的解决思路是：**Session 是外部存储，上下文窗口是从外部存储按需查询的结果**。

```
传统思路（不可逆）：
  ┌──────────────────────────────────┐
  │ 上下文窗口（容量有限）               │
  │  [消息1][消息2][压缩摘要][消息N]     │
  │           ↓ 压缩时                │
  │  [压缩摘要]  ← 旧消息被删掉了！      │
  └──────────────────────────────────┘
  问题：未来需要消息2的具体内容？没了。

Managed Agents 思路（可逆）：
  ┌──────────────────────────────────┐
  │ session（日志，容量无限）          │
  │ [事件1][事件2][事件3]...[事件N]  │
  │                                    │
  │           ┌──────────────────────┐ │
  │           │ 上下文窗口（按需查询）  │ │
  │           │ [事件5][事件6] ← 需要  │ │
  │           │        从 session 取  │ │
  │           └──────────────────────┘ │
  └──────────────────────────────────┘
  问题：未来需要事件3的具体内容？
  getEvents() 可以回溯任意切片，随时取回。
```

### 这在仓库里的对应实践

**Hermes Agent 的记忆三层架构** 完美呼应了这个思路：

```
Hermes 的外部存储 vs 按需加载：

外部存储（无限）：state.db（所有历史会话原文）
                 ↓ FTS5 检索
温热（按需加载）：MEMORY.md / USER.md（2,200/1,375 字符）
                 ↓ 会话开始时注入
热（始终可用）：系统提示中冻结的快照
               ↓ 这个才是真正的"上下文窗口"
```

关键洞察：**Hermes 的 memory freeze（冻结快照）** 和 **Managed Agents 的 getEvents()** 解决的是同一个问题——"如何让模型在有限的上下文窗口里工作，同时不丢失历史数据的可追溯性"。

**DeerFlow 的 Checkpointer** 也是类似思路：异步将完整执行状态持久化到磁盘，进程重启可恢复。但 DeerFlow 更偏向"恢复点"，而 Managed Agents 更强调"可查询的历史"。

### 实践启示

```
不要做的事：
❌ 上下文快满了就开始删历史消息
❌ 认为压缩后的摘要能还原所有细节
❌ 把 session 当作纯日志而不支持查询

应该做的事：
✅ session 的设计目标是"可查询的外部存储"，而非"不可逆的日志带"
✅ 提供 getEvents() 这样的接口，允许大脑：
   - 从上次停止的地方继续（线性前进）
   - 回退 N 个事件查看铺垫（rewind）
   - 在关键决策点前重新阅读上下文（reread）
✅ harness 负责在事件进入上下文窗口前做转换（压缩、切片、组织），
   但原始事件永远保存在 session 里，可回溯。
```

## 五、Many Brains, Many Hands：扩展性的设计

### 原文在说什么

解耦之后，"多个大脑"和"多双手"变成了自然的能力，而不是架构负担。

```
Many Brains = 多个 harness 实例，各自独立，都连接到同一个 session store。
              新 session 来了？起一个新的无状态 harness 就行。
              不需要预先给每个 session 分配独占容器。

Many Hands = 每个 sandbox/tool 都是一个 execute(name, input) → string 接口。
             容器是 hand，手机是 hand，Pokémon 模拟器也是 hand。
             Claude 自己决定把任务发给哪个 hand。
             没有 hand 被绑定到任何大脑，大脑之间可以互相交接 hand。
```

### TTFT 优化：60% / 90% 是怎么来的

```
传统耦合架构下，session 启动的流程：
  1. 启动容器（几十秒）
  2. 克隆仓库
  3. 启动进程
  4. 拉取 session 事件
  → 全程阻塞，直到第一步完成才能开始推理
  → TTFT = 容器启动时间 + 其他固定开销

解耦架构下的懒加载：
  1. harness 从 session 拉取待处理事件（不需要容器）
  2. 立即开始推理
  3. 推理过程中需要执行代码时 → execute() 调用容器
  → 如果 session 根本不需要代码执行（纯推理任务），
    TTFT = 几乎为 0
```

### 对应仓库里的框架

**DeerFlow 的 SubAgent 并行分解** 与 "Many Hands" 理念相通：
- Lead Agent 可以将子任务委派给 Sub-agent 并行执行
- 各自有独立的执行环境，隔离了上下文膨胀

**Hermes Agent 的无状态设计** 与 "Many Brains" 理念相通：
- AIAgent 本身不持有状态，所有状态在外部存储（MEMORY.md / state.db）
- 多个 harness 实例可以连接同一个存储，实现水平扩展

### 实践启示

```
在设计自己的 Agent 系统时：
✅ 先问：这个组件死了，要不要整个系统停摆？
   如果是，就违反了 cattle 原则。

✅ "需要时才初始化"比"预先初始化好"性能好得多：
   session 建好后不立即分配容器，
   等 Claude 真正需要执行代码时再 provision({resources})。

✅ 每个外部能力（工具、数据源、执行环境）
   都用统一的 execute(name, input) → string 接口包装。
   这样将来加新的"手"（比如连上一台打印机、一个树莓派）
   不需要改 harness 本身。
```

## 六、接口规范：原文定义的 6 个核心接口解读

原文虽然没有给出完整的接口规范，但明确提到了几个关键接口。以下是结合原文理解的具体含义：

| 接口                              | 原文描述                 | 本质含义                                                                      |
| ------------------------------- | -------------------- | ------------------------------------------------------------------------- |
| `execute(name, input) → string` | Harness 调用容器的标准方式    | **通用工具调用**：任何外部能力（容器、MCP 服务、API）都可以通过这个接口被调用。Name 是工具名，Input 是参数，返回是执行结果。 |
| `provision({resources})`        | 创建新容器的标准配方           | **资源工厂**：给定资源规格，返回一个可被 execute() 调用的执行环境。失败时返回错误，harness 决定是否重试。          |
| `wake(sessionId)`               | Harness 崩溃后重新启动      | **进程恢复入口**：新 harness 实例用 sessionId 恢复到上一次进度，不需要知道任何 session 内部细节。         |
| `getSession(id) → eventLog`     | 获取 session 的完整事件历史   | **只读查询**：返回所有 emitEvent() 写入的历史，供恢复或回溯使用。                                 |
| `emitEvent(id, event)`          | 在 agent 循环中记录事件      | **仅追加写入**：每次关键操作（工具调用、Claude 响应、系统事件）都写入 session。不可变，只能追加。                |
| `getEvents()`                   | 大脑从 session 中查询上下文切片 | **按需读取**：不传递完整历史，而是由大脑决定需要哪些事件片段。支持位置切片、过滤、转换。                            |

### 接口设计的哲学

```
关键洞察：每个接口都遵守"谁需要知道"原则：
- execute()：harness 知道怎么调用，不需要知道容器内部
- provision()：harness 知道要什么资源，不需要知道怎么造出来
- emitEvent()：harness 知道发生了什么，不需要知道怎么存储
- getEvents()：harness 知道需要什么，不需要知道存在哪
- wake() / getSession()：新 harness 知道 sessionId，不需要知道旧 harness 的状态

对比 Hermes Agent 的接口设计：
  - memory/skill_manage 操作（patch/edit/delete 等）
  → 也是谁需要知道谁就调用，不需要知道底层存储实现
  - MemoryManager 编排 Honcho/Mem0
  → 类似 provision() 的工厂模式

对比 DeerFlow 的接口设计：
  - MCP 协议规定的标准工具调用
  → 就是 execute() 的具体实现
  - Checkpointer 的 save/restore
  → 就是 emitEvent() + wake() 的具体实现
```

## 七、核心设计哲学总结

原文总结的 5 条设计哲学，结合仓库里的框架解读：

### 1. 抽象接口比具体实现更持久

```
操作系统用 read()/write() 抽象了 50 年的硬件变化。
Managed Agents 用 execute()/provision() 抽象了 harness 的演进。
你的代码今天用 Docker 作为 sandbox，
明天换成 WASM 或 Firecracker，harness 不需要改一行。

实践：在构建 Harness 时，投入时间定义清晰的接口，
     收益会在未来每次切换实现时兑现。
```

### 2. 不要养宠物，养牲畜

```
Pet = 有名字的、不能死的、坏了要人工奶回来的。
Cattle = 编号的、死了换新的、自动化的。

当你发现自己在一个组件上花费大量运维精力时，
问自己：是不是把它当宠物养了？

实践：所有组件都应该能自动故障恢复，
     而不是需要人工介入。
```

### 3. 凭证是安全边界，不是有利条件

```
Claude 能用凭证 ≠ Claude 应该碰到凭证。
Claude 能访问资源 ≠ Claude 的生成代码应该能读取凭证。

实践：即使模型现在"还不够聪明"绕过你的限制，
     也不要依赖这一点做安全设计。
     结构性方案（vault + 代理）永远优于限制性提示。
```

### 4. Session 是外部记忆，不是上下文窗口

```
上下文窗口是稀缺资源，决定了模型"现在能想什么"。
Session 是充裕资源，决定了系统"历史上发生了什么"。

让稀缺资源做推理（需要模型实时处理），
让充裕资源做存储（只需要按需查询）。

实践：不要往上下文窗口里塞最终会被删除的历史记录，
     把历史放在外部存储，需要时通过 getEvents() 查询。
     类似 Hermes Agent 的 memory freeze 机制。
```

### 5. Meta-harness：你的系统应该是框架的框架

```
Managed Agents 本身不实现具体 harness，
它提供接口让任何 harness 跑在它上面。
Claude Code 是一个 harness，跑在 Managed Agents 上。
任务特定的 narrow agent 也是一个 harness，跑在 Managed Agents 上。

实践：构建自己的 Agent 系统时，
     先问"我要做一个 harness，还是一个 meta-harness？"。
     Meta-harness 的接口更少、更稳定、更通用；
     Harness 的接口更细、更贴近具体任务。
     大多数时候，你应该做一个 meta-harness，
     然后把具体的任务逻辑留给具体的 harness 去处理。
```

## 九、如果你要实践这篇文章的思想，从哪里开始

### 起步清单（按优先级）

**P0 - 必须做（不改架构，但防止踩坑）**

```
1. 把 API 凭证从代码/环境变量移到专门的 vault 或 secrets manager
2. 如果用容器跑 Agent 代码，不要让容器进程能读到主系统的凭证
3. 任何状态（session、memory）都做持久化，不要只放内存里
4. 给所有外部调用加超时，不要让 Agent 调用无限等待
```

**P1 - 重要（改进架构走向解耦）**

```
5. 把 sandbox / tool 的调用抽象成 execute(name, input) → string 接口
6. 支持 harness 崩溃后用 sessionId 恢复，不需要从头开始
7. 把"凭经验做的假设"写成配置，而不是写死代码
   （比如：假设 Claude 上下文剩 20% 时要压缩）
8. 用原子写入（临时文件 + rename）代替直接覆写文件
```

**P2 - 进阶（完整实现解耦思想）**

```
9. 实现 getEvents() 接口，支持从 session 历史中按切片查询
10. 分离"context 存储"和"context 管理"：
    session 保证持久化，harness 负责在进入窗口前做转换
11. 让容器变成按需创建的资源，harness 不预先持有
12. 考虑 Many hands：不同任务路由到不同执行环境（重计算 vs 轻量）
```
