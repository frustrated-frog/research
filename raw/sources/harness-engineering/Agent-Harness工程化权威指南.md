2026年初，Claude Code 的源码被泄露到 GitHub（非官方镜像 `nirholas/claude-code`），引发了技术圈的广泛关注。这次泄露让我们第一次比较完整地看到，一个生产级 AI 编码助手内部是怎么实现的。

3. **架构学派的转变**：Claude Code 的设计反映了从"框架做编排"到"模型做决策"的根本转变。TAOR 循环的核心逻辑大约只有 50 行，但给了模型无限的操作空间。

### F. Prompt Cache 机制的 14 个 Break 向量详解

Claude Code 的 `promptCacheBreakDetection.ts` 追踪了 14 个 cache-break 向量，理解这些向量对于优化 Token 成本至关重要：

| 编号 | Break 向量 | 说明 | 影响 |
|---|---|---|---|
| 1 | System Prompt 变更 | 修改系统提示词 | 完全失效 |
| 2 | 项目 CLAUDE.md 变更 | 修改项目配置 | 局部失效 |
| 3 | 用户偏好变更 | 修改用户设置 | 局部失效 |
| 4 | 工作目录变更 | cd 命令切换目录 | 路径相关失效 |
| 5 | 工具列表变更 | 添加/删除工具 | 接口级失效 |
| 6 | 工具参数变更 | 修改工具定义 | 接口级失效 |
| 7 | Hook 脚本变更 | 修改钩子逻辑 | 行为级失效 |
| 8 | Skills 配置变更 | 修改技能设置 | 功能级失效 |
| 9 | Subagent 定义变更 | 修改子代理配置 | 结构级失效 |
| 10 | 权限设置变更 | 修改信任级别 | 安全级失效 |
| 11 | 环境变量变更 | 修改运行时环境 | 环境级失效 |
| 12 | API 版本变更 | 升级 API 版本 | 协议级失效 |
| 13 | 模型版本变更 | 切换模型 | 完全失效 |
| 14 | 会话 ID 变更 | 创建新会话 | 完全失效 |

**DANGEROUS_uncachedSystemPromptSection() 函数**：

这个函数名本身就是一种文档机制，提醒开发者：任何添加到这里的内容都会破坏 prompt 缓存。命名规范在这里起到了安全警示的作用。

   - 成功的工作流程
3. **加载阶段**：下次调用同一子 Agent 时，自动加载前 200 行到上下文
4. **遗忘阶段**：定期清理不再适用的记忆，保持 MEMORY.md 的精简

### H. bashSecurity.ts 的 23 项安全检查详解

Claude Code 的 `bashSecurity.ts` 实现了 23 项编号的安全检查，分为以下类别：

**命令拦截类（18 个被阻止的 Zsh 内置命令）**：
- 危险系统命令：`rm -rf /`, `mkfs`, `dd` 等
- 网络配置命令：`ifconfig`, `route`, `iptables` 等
- 用户管理命令：`useradd`, `userdel`, `passwd` 等
- 服务管理命令：`systemctl`, `service` 等

**注入防御类**：
- Zsh equals expansion 防御：`=curl` 可以绕过对 curl 的权限检查
- Unicode 零宽字符注入：防止隐藏在命令中的恶意字符
- IFS null-byte 注入：防止通过特殊字符绕过检查
- 恶意 token 绕过：防止通过特殊编码绕过安全检查

**实现示例**：

```typescript
// 简化的风险判断逻辑
function classifyCommand风险等级(cmd: string): RiskLevel {
  const dangerousPatterns = [
    /rm\s+-rf\s+\//,           // 递归删除根目录
    /curl.*\|.*sh/,            // 下载并执行
    /wget.*\|.*sh/,            // 下载并执行
    /:\(\).*;.*/,              // 伪装的危险命令
    /\x00/,                    // Null-byte 注入
  ];
  
  for (const pattern of dangerousPatterns) {
    if (pattern.test(cmd)) {
      return 'BLOCK';  // 直接阻止
    }
  }
  
  // 白名单检查
  const whitelist = ['git', 'npm', 'yarn', 'pnpm', 'make', 'docker'];
  if (whitelist.some(cmd => cmd.startsWith(cmd))) {
    return 'ALLOW';  // 自动放行
  }
  
  return 'ASK';  // 需要确认
}
```

### I. 上下文压缩的四级机制详解

Claude Code 实现了四级上下文压缩机制，每一级都有不同的触发条件和压缩效果：

| 层级 | 名称 | 触发条件 | 压缩效果 | 可逆 | Token 节省 |
|---|---|---|---|---|---|
| 1 | **Snip** | 历史消息超过 50 轮 | 移除早期消息对 | ✗ | ~30% |
| 2 | **Microcompact** | 相同文件被读多次 | 折叠重复读取 | ✓ | ~20% |
| 3 | **Context Collapse** | 检测到可折叠模式 | 保留原始+投影视图 | ✓ | ~40% |
| 4 | **Autocompact** | Token 超限 90% | 生成摘要替换 | ✗ | ~50% |

**压缩算法的关键特性**：

1. **语义保留**：压缩不是简单截断，而是理解语义后生成摘要
2. **引用保真**：压缩后的内容仍然保留原始引用的锚点
3. **增量压缩**：每次只压缩到目标阈值的 120%，避免过度压缩
4. **可追溯**：压缩历史被记录，支持回溯和审计

### N. Hook 系统的实现原理

Hook 系统是 Harness 的"免疫系统"，它通过拦截关键节点来确保操作符合预期：

```typescript
// Hook 执行时机
enum HookPhase {
  PRE_TOOL_CALL,     // 工具调用前
  POST_TOOL_CALL,    // 工具调用后
  PRE_SESSION_START, // 会话开始前
  POST_SESSION_END,  // 会话结束后
  ON_DIRECTORY_CHANGE, // 目录切换时
  ON_ERROR,          // 错误发生时
}

// 内置 Hook 类型
const builtInHooks = {
  // 格式化检查
  lint_hook: {
    trigger: 'POST_TOOL_CALL',
    filter: (ctx) => ctx.tool === 'Edit' || ctx.tool === 'Write',
    action: async (ctx) => {
      const result = await runLinter(ctx.file);
      if (result.errors.length > 0) {
        return {阻止: true, reason: 'Linter检查失败', details: result };
      }
      return {允许: true };
    }
  },
  
  // SQL 风险检查
  sql_risk_hook: {
    trigger: 'POST_TOOL_CALL',
    filter: (ctx) => ctx.file?.endsWith('Mapper.xml'),
    action: async (ctx) => {
      const risks = await analyzeSqlRisks(ctx.content);
      if (risks.high.length > 0) {
        return {阻止: true, reason: '高风险SQL操作', details: risks };
      }
      return {允许: true, warnings: risks.medium };
    }
  },
  
  // 敏感文件保护
  guard_write_hook: {
    trigger: 'PRE_TOOL_CALL',
    filter: (ctx) => ctx.tool === 'Write' && isSensitive(ctx.file),
    action: async (ctx) => {
      return {阻止: true, reason: '敏感文件禁止直接写入' };
    }
  }
};
```

### O. 脚手架薄化定律（The Harness Thinning Law）

> 随着模型能力提升，硬编码的脚手架应该被主动删除，而不是不断增加。

这一原则在 Claude Code 的架构中得到了充分体现：

1. **2019-2023**：框架做编排（LangChain 时代），大量逻辑写在代码里
2. **2024-2025**：模型做决策（Claude Code 时代），脚手架变薄
3. **2026+**：模型主导（Agent 原生架构），脚手架最小化

**判断脚手架是否过度的标准**：

- 如果模型升级后你需要增加更多规则，说明你在对抗模型
- 如果新功能需要修改框架代码而不是配置，说明脚手架过度
- 如果 Agent 能自己搞定的事还需要手动干预，说明脚手架不足

## 一、Harness 的本质定义

### 1.1 一句话定义

**Agent = Model + Harness**

- **Model（模型）**：大模型本身，负责理解、推理、生成，是 AI 的"大脑"
- **Harness（挽具/马具）**：包裹在模型外围的运行时控制系统，负责调度、约束、恢复、审计，是让大脑稳定干活的"工作台 + 指挥中心"

"Harness"原意是马具——人类需要的不是一匹无法控制的野马（原始大模型），而是一套完整的缰绳、鞍具、车轮与导航系统，将其转变为能安全、准确抵达目的地的"智能马车"。

### 1.2 Harness 与 Framework 的本质区别

| | Framework（如 LangChain） | Harness（如 DeerFlow） |
|---|---|---|
| 定位 | 地基和工具箱，给你材料让你自己盖房 | 带装修的房子 / 操作系统 |
| 特性 | 非 Opinionated，给你原料自己决策 | Opinionated，内置最佳实践 |
| 上手 | 需要大量配置和决策 | 开箱即用（Batteries Included） |
| 灵活性 | 高，但代价是每次都要做大量决策 | 低，但工程可靠性高 |

### 1.3 为什么 AI 落地必须靠 Harness

没有 Harness 的 AI 落地会遇到典型问题：
- 修 bug，改完一处忘三处
- 长任务跑着跑着忘了核心目标
- 一个接口报错导致整个任务崩盘

**核心症结**：模型太"自由"——没有边界、没有流程、没有出错兜底机制。

> **Harness 的核心价值**：Prompt Engineering 解决"让模型听懂话"，Harness 解决"让模型把事做完"。

## 二、Agent 架构的三代演进

理解 Claude Code 这样的成熟产品，需要了解 Agent 架构的演进历程：

| 代际 | 类型 | 特征 | 代表 |
|---|---|---|---|
| 第一代 | Chatbot | 无状态问答，模型没有工具调用能力 | 早期对话机器人 |
| 第二代 | Workflow | 用 n8n、LangChain 把 LLM 嵌进代码驱动的 DAG 流，**代码决定**模型下一步做什么 | LangChain Agents |
| 第三代 | Autonomous Agent | **模型控制循环**，运行时只是执行器 | Claude Code、DeerFlow 2.0 |

Claude Code 属于第三代商业化产品。其核心洞察是：**真正难的是 Harness**，给任何支持工具调用的 LLM 提供文件系统访问、shell、分层记忆和声明式扩展能力，全部在一个由可组合权限约束的有界自主循环里运行。

## 三、TAOR 循环：Orchestrator 越笨，架构越稳定

### 3.1 循环设计

Claude Code 的执行引擎是一个叫 **TAOR** 的循环：**Think → Act → Observe → Repeat**。

这背后的设计哲学极其关键：

> **运行时越笨，架构越稳定。把智能下沉到模型，把确定性留给框架。**

运行时本身只负责驱动循环、执行工具调用、感知结果。**所有的推理、决策、何时停止，全部都交给模型**。运行时不知道代码是什么、不知道文件在哪，它只是跑循环，让模型决定下一步。

这和早期 LangChain 试图在框架层做各种"聪明编排"的路线形成了鲜明对比。TAOR 循环的核心逻辑大约只有 50 行，但给了模型无限的操作空间。

### 3.2 四种能力原语

Claude Code 没有给模型配备大量专项工具，而是只提供**四种能力原语**：

- **Read**（读取）
- **Write**（写入）
- **Execute**（执行）
- **Connect**（连接）

其中 **Bash 是通用适配器**，允许模型使用任何人类开发者会用的工具——git、npm、docker，全部通过 shell 组合完成。

> **核心原则**：不要构建 100 个工具，给模型一个 shell，让它自己组合。

### 3.3 脚手架的演化规律

随着模型变得更强，**脚手架应该变薄，而不是变厚**。

硬编码的脚手架应该随着模型能力提升而被主动删除，架构随时间推移越来越薄。如果你每次模型升级都要往框架里加更多脚手架，说明你在对抗模型，而不是利用模型。

## 四、六大核心模块详解

根据 DeerFlow 2.0 等代表性项目的架构，一个完整的 Harness Agent 由六大核心组件构成：

### 4.1 规划与编排引擎（Planning & Orchestration）

**角色**：Harness 的"小脑"，负责任务的拆解和流程控制。

**核心功能**：
- **任务拆解**：自动将大任务分解为有序的子步骤
- **状态机管理**：基于 LangGraph 等技术，管理任务的状态流转（如：规划 → 执行 → 检查 → 修正）
- **断点续传**：通过 Checkpoint 机制，确保任务中断后能从断点恢复，而不是重头再来

### 4.2 沙箱执行环境（Sandbox / Execution Environment）

**角色**：Harness 的"双手"，让 AI 真正拥有操作计算机的能力，而不仅仅是聊天。

**核心功能**：
- **文件读写**：AI 可以创建、修改、保存文件（如 `/mnt/workspace/`）
- **代码执行**：在 Docker 或本地容器中运行 Python/Bash 命令
- **安全隔离**：限制网络访问、CPU/内存配额，防止 AI 误操作破坏宿主机系统

### 4.3 技能与工具系统（Skills & Tools）

**角色**：Harness 的"武器库"，定义了 AI 能做什么。

**核心功能**：
- **渐进式加载**：只有在任务需要时才加载相关技能（如"视频生成"技能），避免塞爆上下文窗口
- **标准化工具调用**：统一封装搜索、代码解释器、API 调用等接口，处理参数校验和异常

### 4.4 记忆与上下文工程（Memory & Context Engineering）

**角色**：Harness 的"海马体"，解决模型"记性差"和"上下文溢出"的问题。

**核心功能**：
- **上下文压缩**：自动对过长的对话历史进行摘要，保留核心信息
- **跨会话记忆**：持久化存储用户偏好、项目背景，让 AI 在下次启动时仍能"记得"之前的设定

> 详细内容见本文第五章"十二种可复用的 Harness 设计模式"中的"记忆与上下文"部分。

### 4.5 系统提示词与角色准则（System Prompts & Guardrails）

**角色**：Harness 的"宪法"，定义 AI 的行为边界。

**核心功能**：
- **角色定义**：明确 AI 是"资深程序员"还是"严谨的分析师"
- **硬约束**：例如"禁止使用 `rm -rf` 命令"、"必须先用搜索工具验证事实再回答"。这些规则通常通过 Hook 机制强制执行，不依赖模型的自觉性

### 4.6 可观测性与反馈闭环（Observability & Feedback Loop）

**角色**：Harness 的"监控塔"，让黑盒的 AI 执行过程变得透明。

**核心功能**：
- **全链路日志**：记录每一步的输入输出
- **自动纠错**：当工具调用失败或代码报错时，Harness 会捕获错误信息并自动反馈给 AI，要求其修正（代码运行报错 → 把错误日志喂回给 AI → AI 重写代码）

## 五、十二种可复用的 Harness 设计模式

以下 12 个模式是从 Claude Code 源码中提炼出来的，分成四类：

### 5.1 记忆与上下文（5 个模式）

这五个模式其实是一条逐步演进的路径：一开始只是给 Agent 一份固定的规则文件，然后按目录去限制这些规则的作用范围，再把记忆做成分层结构，接着在后台做清理，最后在上下文快满的时候对对话本身做压缩。

#### 模式 1：持久化指令文件模式（Persistent Instruction File Pattern）

**问题**：没有持久化指令文件时，每个 Agent 会话都像从零开始。同样的约定、命令和边界，需要一遍遍重复。

**做法**：放一个项目级的配置文件（如 `CLAUDE.md`），每次会话自动加载。里面写清楚构建命令、测试方式、架构规则、命名约定这些内容。文件跟着代码仓库走，而不是靠人每次复制粘贴。

**适用场景**：需要在多个会话里反复处理同一个代码库。

**权衡点**：有维护成本。这个文件需要跟着项目一起更新，一旦过时，反而会误导 Agent。

#### 模式 2：作用域上下文组装模式（Scoped Context Assembly Pattern）

**问题**：一个指令文件在小项目里够用，但项目一大就容易出问题：要么越写越长没人看，要么写得太泛对具体目录没什么用。

**做法**：把指令拆到不同作用域里——组织级、用户级、项目根目录、父目录、子目录。Agent 会根据当前所在的位置，动态加载对应的规则。通过导入的方式，可以把大的指令集拆开管理。

**适用场景**：Monorepo、多语言项目，或者不同目录有不同规范的代码库。

**权衡点**：可读性会变差。规则分散在多个文件里后，很难一眼看清 Agent 实际加载了哪些内容，不同作用域之间也可能出现冲突。

#### 模式 3：分层记忆模式（Tiered Memory Pattern）

**问题**：把所有记忆都塞进上下文，每次会话都会浪费 token，还容易撞上窗口限制，重要信息反而被淹没。

**做法**：把记忆分层——一个精简的索引始终放在上下文里（控制在几百行以内），和当前任务相关的内容按需加载，完整的历史记录留在磁盘上需要时再去查。

**适用场景**：需要跨多次会话保留偏好、决策或状态的 Agent。

**权衡点**：实现会更复杂。需要想清楚信息该放哪一层，什么时候上升或下沉，以及怎么保证索引和实际数据同步。

#### 模式 4：记忆整合模式（Dream Consolidation Pattern）

**问题**：即使做了分层，记忆用久了还是会"变乱"——重复内容越来越多，旧信息和新信息打架，索引也会慢慢膨胀。

**做法**：加一个后台整理机制，在空闲时定期做清理：去重、删旧、重组结构，让记忆保持干净、可用。可以理解为给 Agent 做一次"垃圾回收"。Claude Code 源码里提到的 `autoDream`，就是在做类似的事情。

**适用场景**：Agent 会长期运行、持续积累记忆，而且不方便靠人工去维护。

**权衡点**：整理本身也要消耗 token，而且不一定完全准确。如果清理太激进，可能会把有用的信息一起删掉。

#### 模式 5：渐进式上下文压缩模式（Progressive Context Compaction Pattern）

**问题**：对话一长，很快就会碰到上下文窗口的上限。要么早期内容被挤掉，要么任务直接做不下去。

**做法**："分层压缩"——新的对话尽量保留细节，稍旧的内容做轻量总结，再往前的就逐步压缩，甚至折叠成很短的摘要。越久远的信息，保留得越粗。

**适用场景**：对话轮次比较多（比如 20～30 轮以上）的任务。

**权衡点**：压缩一定是有损的。信息在一轮轮总结中会丢失，如果后面又需要这些细节，Agent 可能会"编"而不是承认不知道。

### 5.2 工作流与编排（3 个模式）

这一组模式的核心就是一个词：**分离**。把读取和写入拆开，把"查资料"和"改代码"的上下文拆开，把顺序执行和并行执行也拆开。

#### 模式 6：探索-规划-行动循环模式（Explore-Plan-Act Loop Pattern）

**问题**：如果一上来就让 Agent 改代码，很容易出问题——理解不完整，改错文件，漏掉依赖，或者直接忽略现有的实现方式。

**做法**：把流程拆成三步，而且**权限逐步放开**：
1. **探索**（只读）：只读代码、查信息、摸清结构
2. **规划**（对齐）：和用户对齐思路
3. **行动**（写入）：最后再动手改代码

本质上是先搞清楚，再决定怎么做，最后再执行。

**适用场景**：不熟悉的代码库，或者涉及多个文件的复杂修改。

**权衡点**：会慢一点。多了探索和规划这两步，小任务会显得有点"流程过重"。

#### 模式 7：上下文隔离子智能体模式（Context-Isolated Subagents Pattern）

**问题**：会话一长，所有东西都会堆在同一个上下文里——调研内容、规划讨论、代码修改、日志输出，全混在一起。等真正开始改代码时，很多无关信息已经在干扰判断了。

**做法**：把任务拆给不同的子 Agent，每个都有自己的上下文和权限：
- 做调研的只负责看和分析，不能改代码
- 做规划的只负责设计方案
- 真正执行的才有完整工具权限

每个子 Agent 只接触自己需要的信息，避免被"流噪声"影响。

**适用场景**：长会话、多阶段流程，或者不同阶段对上下文要求差异很大的任务。

**权衡点**：需要额外协调。主 Agent 要决定每一步传什么信息，传少了会丢细节，传多了又回到上下文污染的问题。

#### 模式 8：分支-合并并行模式（Fork-Join Parallelism Pattern）

**问题**：有些任务其实可以拆开做，但如果 Agent 一次只能处理一件事，最后还是会变成一条一条顺序执行。

**做法**：把任务拆成多个分支并行处理——每个子 Agent 在独立的代码副本里工作（比如用 `git worktree`），互不干扰。等都完成后，再把结果合并回来。

**适用场景**：可以拆成多个互不依赖子任务的场景。

**权衡点**：合并会更复杂。如果不同分支改到了同一部分代码，冲突可能比顺序处理更难解决。

### 5.3 工具与权限（3 个模式）

如果说前面的记忆模式是在解决"Agent 知道什么"，工作流是在解决"它怎么做事"，那这一部分关注的就是**"它能做什么"**。

#### 模式 9：渐进式工具扩展模式（Progressive Tool Expansion Pattern）

**问题**：如果一开始就把所有工具都开放给 Agent，反而会变得更难用——工具一多，选择成本变高，也更容易选错。

**做法**：先给一小部分常用工具，够用就行；其他工具按需再打开。比如读写文件、搜索这些作为默认能力，复杂一点的工具等用到再加载。

**适用场景**：工具很多，但大多数任务其实只用到一小部分。

**权衡点**：需要额外判断什么时候该开新工具。如果开得太晚，Agent 可能已经走了弯路，浪费了一些轮次。

#### 模式 10：命令风险分类模式（Command Risk Classification Pattern）

**问题**：如果让 Agent 随便执行 shell 命令，风险很高；但如果每一步都让用户确认，很快就会点到麻木。

**做法**：在执行前做一层"风险判断"——低风险的命令自动放行，高风险的才需要人工确认或直接拦截。实现上通常是对命令做解析（看做什么操作、带了哪些参数、影响范围多大），再结合规则去判断风险等级。

Claude Code 的 `bashSecurity.ts` 里有 **23 项编号的安全检查**，包括：
- 18 个被阻止的 Zsh 内置命令
- 防御 Zsh equals expansion（`=curl` 这种写法可以绕过对 curl 的权限检查）
- unicode 零宽字符注入
- IFS null-byte 注入
- 一个在 HackerOne 审查期间发现的恶意 token 绕过

**适用场景**：Agent 能执行 shell 命令，或者会操作外部系统。

**权衡点**：规则不可能覆盖所有情况，需要不断调整；有时候会误判，要么放过风险操作，要么拦住本来安全的命令。

#### 模式 11：单用途工具设计模式（Single-Purpose Tool Design Pattern）

**问题**：如果所有操作都走通用 shell（`cat`、`sed`、`grep`），问题会慢慢出现——命令不直观、不好审查，也更难做权限控制。对模型来说，也更容易用错。

**做法**：把常见操作拆成专门的工具——读文件、改文件、搜索、匹配路径，各自都有明确的输入和边界。这样不仅更好理解，也更容易限制权限。

**适用场景**：需要频繁做文件操作或搜索的 Agent。

**权衡点**：灵活性会受限。专用工具不可能覆盖所有情况，所以还是需要保留通用 shell 作为兜底。

### 5.4 自动化（1 个模式）

这类模式其实贯穿前面的所有部分。本质问题是：有些步骤是每次都必须执行的，但不能指望模型每次都记得。

#### 模式 12：确定性生命周期钩子模式（Deterministic Lifecycle Hooks Pattern）

**问题**：有些事情是必须每次都做的——改完代码跑一遍格式化、执行前做校验、切换目录时重新加载配置。但如果只是写在提示词里，基本不可靠。模型会忘、会跳过，甚至在复杂上下文里"理解偏了"。

**做法**：把这些动作挂到 Agent 生命周期的关键节点上自动执行，完全不依赖提示词。比如工具调用前后、会话开始、工作目录变化时，系统都会触发对应的钩子。

> **核心原则**：凡是"不能出错、不能漏"的事情，都不该交给模型记，而应该交给系统兜底。

**适用场景**：存在必须严格执行、不能遗漏的步骤。

**权衡点**：出了问题不太好排查，因为这些逻辑是在对话之外跑的。

## 六、上下文窗口：稀缺资源，不是越大越好

### 6.1 Context Collapse：Agent 系统最普遍的失败模式

随着对话进行，上下文窗口被填满，记忆退化，幻觉出现，Agent 开始在自己积累的噪音里迷失方向。

Claude Code 把 Context Window 看成一种**需要主动管理的稀缺资源**，围绕 Context 构建了三层防御体系：

### 6.2 第一层：Auto-Compaction（自动压缩）

当 Context 使用量达到约 **50%** 时自动触发，用 LLM 摘要替换原始对话轮次，释放空间的同时保留关键决策。这不是简单地截断历史，而是用摘要压缩，确保重要信息不丢失。

**故障模式**：Context Collapse
**解决方案**：Auto-compaction at ~50% + sub-agents with isolated context windows

### 6.3 第二层：Sub-Agent 隔离

把重型的探索、研究任务卸载给独立的子 Agent。子 Agent 运行自己独立的 TAOR 循环，有自己的 Context 预算，任务完成后只把摘要返回给主 Agent。

从代码结构上看，子 Agent 运行时：
- 有自己的 `maxTurns` 上限
- 有自己的 compaction 机制（独立压缩，不影响主对话）
- 有自己的 `MEMORY.md`

主 Agent 派出子 Agent 之后，只等一个 summary 回来，整个子任务的 token 消耗对主 Context 完全透明隔离。

### 6.4 第三层：Prompt Cache 经济学

Claude Code 的 `promptCacheBreakDetection.ts` 里追踪了 **14 个 cache-break 向量**，也就是 14 种会让 prompt 缓存失效的情况。

代码里还有一个函数叫 `DANGEROUS_uncachedSystemPromptSection()`，光是这个命名本身就是一种文档——这里加东西要小心，会破坏缓存。

> 当你为每个 token 付费的时候，缓存失效不再是一个计算机科学笑话，更多的是一个**财务问题**。

### 6.5 Session Continuity（会话连续性）

Claude Code 里，会话不是一次性的。它们像 **git branch** 一样运作，可以 checkpoint、rollback，或者把某个探索方向 fork 成一条新路径。这意味着 Context 的管理不只是在单次会话内，而是**跨会话**的。

## 七、记忆系统：核心是索引，不是存储

### 7.1 核心设计原则

> **记忆是索引，不是存储。能从代码库中重新推导出的信息，绝不应该被存储。**

Claude Code 的记忆系统，更像是一个带有严格图书管理员的档案系统，而不是一个越来越大的背包。

### 7.2 六层记忆架构

Claude Code 的记忆系统在每次会话启动时按层加载：

| 层次 | 名称 | 描述 |
|---|---|---|
| 1 | Managed Policy | 组织级策略：企业或团队层面的统一规范 |
| 2 | Project CLAUDE.md | 项目配置：当前项目的特定指令和上下文 |
| 3 | User Preferences | 用户偏好：个人层面的习惯和偏好设置 |
| 4 | Auto-Memory | 自动学习：Agent 从历史交互中学到的用户模式 |
| 5 | Session | 会话上下文：当前会话的临时信息 |
| 6 | Sub-Agent Memory | 子 Agent 记忆：各子 Agent 独立维护的专项记忆 |

### 7.3 Auto-Memory 机制

Claude Code 的 Auto-Memory 循环甚至允许 Agent 学习用户的工作模式，并把这些模式写入 `MEMORY.md` 供未来会话使用。用户不需要反复解释相同的事情，Agent 会从之前的交互里学习并记住重要信息。

### 7.4 子 Agent 记忆机制

在自定义子 Agent 的配置里，可以设置 `memory: user`，Agent 会把学到的模式写入 `~/.claude/agent-memory/<name>/MEMORY.md`，下次调用时自动加载前 200 行。每个子 Agent 都可以有自己独立的、持续积累的专项记忆。

### 7.5 主动自我编辑能力

记忆系统不仅会记录，还会主动重写、去重、甚至剪除互相矛盾的信息。过期且无效的记忆在这里被视为**"负债"而非资产**。

> **产品层面的启示**：记忆不只是一个 Feature，它是决定用户是否继续使用的核心留存机制——用户真正期待的是一个"会学习"的 Agent。

## 八、权限系统：五档信任光谱，信任是可组合的

### 8.1 五档信任级别

Claude Code 的权限系统被设计为一个**五档的信任光谱**：

| 级别 | 名称 | 权限描述 |
|---|---|---|
| 1 | plan | 只读，完全不能写入，信任级别最低 |
| 2 | default | 编辑和 shell 操作前都需要询问，标准模式 |
| 3 | acceptEdits | 自动批准文件编辑，shell 操作仍需询问，中等信任 |
| 4 | dontAsk | 自动批准白名单内的所有操作，高信任 |
| 5 | bypassPermissions | 跳过所有检查，仅限托管组织使用，最高信任 |

### 8.2 底层 API 身份验证机制

Claude Code 还有一个更底层、巧妙的机制：API 请求在 JS 层之下做了身份验证。

在 `system.ts` 文件里，每个 API 请求都包含一个 `cch=00000` 占位符。在请求真正离开进程之前，Bun 的原生 HTTP 栈（用 Zig 编写，运行在 JavaScript 运行时之下）会把这五个零替换成一个计算出的哈希值。服务端会验证这个哈希，确认请求来自真实的 Claude Code 二进制文件，而不是第三方伪造的客户端。

之所以用等长的占位符，是为了让替换不改变 Content-Length 头部，也不需要缓冲区重新分配。**整个计算过程发生在 JS 层之下，对运行在 JS 里的任何代码都完全不可见。** 本质上是在 HTTP 传输层实现的 API 调用 DRM。

这正是 **Anthropic 此前向 OpenCode 发律师函背后的技术基础**——二进制文件本身通过加密证明了自己的身份。

### 8.3 权限设计即 UX

这种可组合的信任光谱，让 Claude Code 能够适应完全不同的使用场景：从什么都要确认的高度受限企业环境，到全速运行的个人开发环境。

> **权限设计更像是 UX 设计。对于 Agent 产品来说，这是从 Demo 进入企业生产环境的"门槛"。**

## 九、多 Agent 编排：从子 Agent 到 Agent Teams

### 9.1 两层横向扩展架构

Claude Code 的多 Agent 编排采用横向扩展的方式，分为两层：

**第一层：Sub-Agent（子 Agent）**
- 以独立进程方式运行
- 有自己的 TAOR 循环、Context 预算、`maxTurns` 上限、记忆
- 任务完成后，只把摘要返回给主 Agent
- 主 Agent 的 Context 完全不受影响

**第二层：Agent Teams（代理团队）**
- 多个专业 Agent 协同工作
- 类似于 OpenAI 内部的实践：一个智能体写代码，一个智能体评审，互相独立，避免自我评估的盲区

### 9.2 Anthropic 的角色分离实践

Anthropic 内部团队用"角色分离"做校验——一个智能体写代码，一个智能体评审，互相独立。这是 Harness Engineering 的核心思路：**不靠单个模型搞定所有事，而是设计一套系统，让多个智能体协作、互相校验，最终产出可靠结果。**

## 十、Harness 工程化最佳实践（Java Spring Boot 场景）

### 10.1 核心原则

1. **OpenSpec 管变更生命周期**：用 `/opsx:propose → /opsx:apply → /opsx:verify → /opsx:archive` 管住"需求从提出到归档"的全过程
2. **AGENTS.md 只当地图，不当百科全书**：`AGENTS.md` 负责告诉 AI"先看什么、按什么流程做"；真正的项目知识应该放在 `docs/` 里
3. **Claude 的硬约束靠 permissions + hooks**：规则写在文档里只是"软约束"；真正能拦住危险动作的，是权限和 hook
4. **团队专用动作放到 skills 和 subagents**：比如 review 摘要、Spring 分层审查、SQL 风险审查，这些都应该变成可重复调用的能力

> **一句话总结**：需求先工件化，知识先显性化，执行先加护栏，评审与验证必须分离。

### 10.2 推荐仓库组织方式

```
repo/
├─ AGENTS.md              # 通用 OpenSpec 规则
├─ CLAUDE.md              # Claude 系统提示词
├─ REVIEW.md              # 只读评审代理提示词
├─ docs/                  # 项目知识库目录
│   ├─ architecture/       # 整体知识
│   │   ├─ index.md       # 项目架构总览
│   │   └─ implicit-contracts.md  # 隐性业务约定/项目坑点
│   ├─ product/            # 产品知识
│   │   └─ index.md
│   └─ standards/         # 相关规范
│       ├─ testing.md
│       └─ database.md
├─ openspec/              # OpenSpec 执行目录
│   ├─ changes/            # 变更目录
│   │   └─ <change名>/
│   │       ├─ specs/      # 该 change 的工作原理
│   │       ├─ proposal.md # 当前拆解的需求实现提案
│   │       ├─ design.md   # 执行的具体方案
│   │       └─ task.md     # 拆解的执行步骤节点
│   │   └─ archive/        # 归档文件
│   └─ specs/              # 当前系统如何工作
├─ .claude/
│   ├─ settings.local.json.example  # 项目级权限设置
│   ├─ skills/            # 项目级 Skills
│   │   ├─ prepare-review/  # review 前变更审计
│   │   ├─ spring-architecture-review/  # Springboot 分层架构检查
│   │   └─ sql-risk-review/ # SQL、Mapper、批量更新等检查
│   ├─ agents/
│   │   └─ reviewer.md     # 只读评审代理
│   └─ hooks/              # Hook
│       ├─ guard_write.py   # 文件写入保护
│       ├─ ensure_change_context.py  # 上下文变更保护
│       └─ run_checks.sh    # 编译检查
├─ src/
└─ pom.xml
```

**职责分层**：
- `openspec/`：OpenSpec 的执行目录，管理"这次改什么"
- `docs/`：项目知识库，管理"这个项目本来是怎么工作的"
- `AGENTS.md / CLAUDE.md / REVIEW.md`：通用项目级配置，管理"AI 进入仓库后应该怎么做"
- `.claude/settings.json + hooks`：约束和限制配置，管理"哪些事不能做、哪些检查必须跑"
- `skills / agents`：自动化流程，管理"团队专用的审查动作"

### 10.3 AGENTS.md 只做导航，不做知识库

很多人会本能地把所有规则都塞进 `AGENTS.md`，但这会很快失控。更好的方式是：

> **AGENTS.md 只负责告诉 AI 去哪里看，真正的知识、规则、隐性约定放进 `docs/`**

`AGENTS.md` 应该像一个"入口地图"，而不是一本"项目百科全书"。它至少应该说明：
- 仓库采用什么工作流
- AI 进来后必须先读哪些文件
- 没有 change 是否允许开始开发
- 哪些目录是受保护的
- 主要命令入口是什么

如果 `AGENTS.md` 变得越来越长，通常不是因为规则更多了，而是因为**知识没有被正确拆分到 docs**。

### 10.4 把"隐性约定"单独文档化

对真实业务项目来说，最危险的通常不是显式规则，而是那些"大家都知道，但没人写下来"的东西。

最佳实践是：把所有容易导致"改完能跑、联调出错"的口头约定，单独沉淀到 `docs/architecture/implicit-contracts.md`。

并且要做到两件事：
- OpenSpec 在 `design.md` 阶段就显式检查这些约定
- reviewer / verify 阶段也把这些约定作为对齐依据

### 10.5 OpenSpec 变更生命周期管理

OpenSpec 的定位要非常清楚：**它负责把需求变成 change 工件，并驱动 change 生命周期。**

**标准流程**：

| 步骤 | 命令 | 职责 | 产出物 |
|---|---|---|---|
| 提案 | `/opsx:propose` | 把需求拆成一个 change | `proposal.md`、`design.md`、`tasks.md` |
| 执行 | `/opsx:apply` | 根据确认的 design.md 和 tasks.md 实施代码改动 | 代码改动 |
| 验证 | `/opsx:verify` | 核对"实现有没有和 OpenSpec 工件对上" | 验证报告 |
| 归档 | `/opsx:archive` | 把当前 change 归档，保持进行中上下文干净 | 归档文件 |

**实战经验**：
- 第一版 proposal 往往不靠谱，**不要急着执行**。如果 proposal 拆错了，宁可废弃当前 change，重新生成新的，也不要硬着头皮继续做。
- `/opsx:verify` **不是代码评审，也不是架构评审**，它只负责检查实现与 change 工件是否一致。

### 10.6 把"实现、评审、验证"彻底拆开

在真实项目里，下面几件事**不能混在一起**：
- 需求拆解
- 代码实现
- OpenSpec 对齐校验
- 架构审查
- SQL 风险审查
- 面向 PR 的人工阅读摘要

最佳实践是把它们拆成不同职责：

| 动作 | 职责 |
|---|---|
| `/opsx:verify` | 检查"实现有没有和 OpenSpec 对上" |
| `/prepare-review` | 整理"这次到底改了什么，方便人 review" |
| `/spring-architecture-review` | 检查 Spring 分层有没有乱 |
| `/sql-risk-review` | 检查 SQL、Mapper、批量更新、索引和扫描范围风险 |
| `reviewer` 子代理 | 做一轮独立、只读、偏代码审查视角的检查 |

**拆分的好处**：
1. 每种审查都有明确目标，不会互相覆盖又互相遗漏
2. 出问题时更容易定位，到底是 proposal 有问题、实现有问题，还是架构/SQL 有风险

### 10.7 真正的硬护栏必须落在 permissions + hooks

很多团队喜欢把规则写进提示词，然后默认 AI 会听。但在工程实践里，这种做法并不可靠。

> **最佳实践**：能通过权限系统和 hook 强制拦住的，就不要只靠提示词约束。

**高风险目录**（应该默认视为高风险区域）：
- `src/main/resources/application*.yml`
- `src/main/resources/bootstrap*.yml`
- `src/main/resources/application-secrets.yml`

## 十一、标杆案例

### 11.1 Claude Code：把 Harness 刻进执行框架

Claude Code 是 Harness Agent 的典型实现。收到复杂任务后，它不会直接动手，而是按固定框架执行：

1. **探索代码库**：理清项目结构、依赖关系，像工程师接需求前的"读代码"
2. **制定执行计划**：拆任务、标步骤、明依赖，相当于写技术方案
3. **逐步执行并检查**：完成一步验证一步，发现问题即时调整，对应代码评审和自测
4. **全局检查**：全步骤完成后做回归测试，排查遗漏和边界问题

这套流程不是写在提示词里，而是 Harness 内置的。就连高风险操作的人工确认，也是框架的"钩子"拦截实现，而非模型的"自觉"。

> **核心**：把"信任模型"变成"信任框架"，模型可以犯错，框架能兜住。

### 11.2 字节 DeerFlow 2.0：开源 Harness 的标杆

字节开源的 DeerFlow 2.0，上线不到一个月斩获 **54.7K Star**，核心亮点有三个：

1. **子代理沙箱隔离**：每个子智能体在独立沙箱运行，文件、网络、资源全隔离，一个出错不影响其他
2. **结构化任务状态**：用清晰数据结构替代对话历史，模型只读关键信息，告别上下文过载
3. **可插拔工具链**：工具调用封装成标准接口，新增工具不用改框架，按规范实现即可

它把做智能体从"调模型、写代码"，升级成了"配置 Harness"，让开发者不用再操心调度、恢复、隔离等底层问题。

## 十二、工程师角色的根本转变

Harness Agent 的出现，不仅解决了 AI 落地的痛点，更带来了工程师工作重心的根本转变：

| 过去 | 现在（AI 智能体时代） |
|---|---|
| 直接告诉计算机每一步该怎么做 | 设计一套环境，让模型在环境里自己完成任务 |
| 写具体业务逻辑 | 设计执行框架和约束条件 |
| 处理边界异常 | 配置工具接口和权限边界 |
| 手动调试修复问题 | 定义状态流转和恢复机制 |
| - | 搭建可观测和审计系统 |

**OpenAI 内部实践**：已有团队用智能体写了百万行代码，人类工程师从"写代码的人"变成了"设计系统的人"。
