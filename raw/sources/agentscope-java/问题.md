## 一. Hook在这个项目里会在各种事件之后触发，代码如何做的？原理是什么？

Hook 在这个项目里本质上不是“框架外部的监听器”，而是 **Agent 主执行链路里的一个可组合中间件队列**。

最核心的代码模式是这个：

```java
private <T extends HookEvent> Mono<T> notifyHooks(T event) {
    Mono<T> result = Mono.just(event);
    for (Hook hook : getSortedHooks()) {
        result = result.flatMap(hook::onEvent);
    }
    return result;
}
```

也就是说：每到一个生命周期点，框架创建一个事件对象，比如 `PreReasoningEvent`、`PostActingEvent`，然后把这个 event 按 Hook priority 顺序传给每个 Hook。每个 Hook 返回一个 `Mono<T>`，下一个 Hook 接收的是上一个 Hook 返回后的 event。

所以它不是广播式“通知一下就完了”，而是：

```text
event0
  -> hook1.onEvent(event0) -> event1
  -> hook2.onEvent(event1) -> event2
  -> hook3.onEvent(event2) -> event3
  -> 主流程继续使用 event3
```

这就是它的原理。

比如 reasoning 前：

```java
return checkInterruptedAsync()
    .then(notifyPreReasoningEvent(memory.getMessages()))
    .flatMapMany(event -> {
        GenerateOptions options =
            event.getEffectiveGenerateOptions() != null
                ? event.getEffectiveGenerateOptions()
                : buildGenerateOptions();

        List<Msg> modelInput =
            prependSystemMsg(event.getInputMessages(), event.getSystemMessage());

        return model.stream(modelInput, toolkit.getToolSchemas(), options);
    })
```

这里 `PreReasoningEvent` 被 Hook 处理完之后，主流程真的会读取 Hook 修改后的：

- `event.getInputMessages()`
- `event.getSystemMessage()`
- `event.getEffectiveGenerateOptions()`

所以 Hook 可以真实改变模型输入，而不是只能旁观。

再比如 acting 前：

```java
return Flux.fromIterable(toolCalls)
    .concatMap(tool -> notifyHooks(new PreActingEvent(this, toolkit, tool)))
    .map(PreActingEvent::getToolUse)
    .collectList();
```

每个工具调用都会经过 `PreActingEvent`。Hook 如果改了 `ToolUseBlock`，后面真正执行的就是改过后的工具参数。

它的几个关键设计点：

1. **事件对象承载上下文**

   每个 HookEvent 都带着 agent、timestamp、类型，有些还带 memory、toolkit、modelName、inputMessages、toolUse、toolResult、finalMessage 等。

2. **有些事件可修改，有些只读**

   比如：

   - `PreReasoningEvent` 可以 `setInputMessages`
   - `PostReasoningEvent` 可以 `stopAgent()` 或 `gotoReasoning(...)`
   - `PreActingEvent` 可以 `setToolUse`
   - `PostActingEvent` 可以 `setToolResult` 或 `stopAgent()`
   - `ReasoningChunkEvent`、`ActingChunkEvent` 更偏通知，只用于 streaming、trace、日志

3. **Hook 按 priority 顺序串行执行**

   `AgentBase` 里会按 `Hook::priority` 排序。priority 越小越早执行。这样安全、恢复、压缩、RAG、日志等能力可以有确定顺序。

4. **Hook 是 Reactor 链的一部分**

   因为 Hook 返回 `Mono<T>`，它可以做异步操作，比如查知识库、读工作区、写日志、请求远端服务。主流程会等 Hook 完成后继续。

5. **主流程在关键点主动触发 Hook**

   不是 JVM 魔法，也不是 AOP。就是代码在每个阶段显式调用：

   - `notifyPreCall`
   - `notifyPreReasoningEvent`
   - `notifyReasoningChunk`
   - `notifyPostReasoning`
   - `notifyPreActingHooks`
   - `notifyActingChunk`
   - `notifyPostActingHook`
   - `notifyPreSummaryHook`
   - `notifyPostSummaryHook`
   - `notifyPostCall`
   - `notifyError`

最深的一点是：Hook 在这里是 **控制流扩展机制**，不是普通 observer。

普通 observer 只能看；这里的 Hook 能影响下一步：

- 改 prompt
- 改工具参数
- 改工具结果
- 让 agent 停下来
- 让 agent 跳回 reasoning
- 注入 RAG、Plan、Skill、Workspace 上下文
- 把 stream chunk 转成外部事件

所以这个项目里的 Hook 更像“ReAct 主循环的中间件管线”。主循环保持稳定，复杂企业能力都挂在事件点上。

## 二. 什么是 pending tool？

`pending tool` 就是：**模型已经发起了工具调用，但 Memory 里还没有对应工具结果的 tool call。**

在 ReActAgent 里，一次标准工具调用闭环应该是：

```text
assistant: ToolUseBlock(id="call_1", name="search", input={...})
tool:      ToolResultBlock(id="call_1", name="search", output=[...])
assistant: 基于工具结果继续回答
```

如果 Memory 里出现了：

```text
assistant: ToolUseBlock(id="call_1", name="search", input={...})
```

但后面还没有：

```text
tool: ToolResultBlock(id="call_1", ...)
```

那么 `call_1` 就是一个 `pending tool`。

它表示 agent 上一次执行停在了“模型要求执行工具”之后，但工具结果还没有补回来。可能原因包括：

- 工具执行被中断了
- 工具超时了
- 工具需要人工确认
- 工具是外部工具，需要调用方自己执行
- agent 被暂停后等待恢复

所以 ReActAgent 下次 `call()` 时会先检查 pending tool：

- 如果没有 pending tool：正常把用户输入加入 Memory，然后问模型。
- 如果有 pending tool 且这次输入为空：尝试继续执行这些工具。
- 如果有 pending tool 且用户传入 `ToolResultBlock`：把外部工具结果补回来。
- 如果有 pending tool 但用户又发普通文本：通常报错，因为工具调用链还没闭合。

一句话：**pending tool 是“未完成的工具调用债务”。模型已经开了口要工具结果，框架必须先把这个债还上，才能继续正常对话。**

## 三. ReasoningContext 的设计思想？

这个思想可以概括成一句话：

**把模型的一轮输出看成“一个完整的 assistant turn”，而不是看成“文本回答”或“工具调用”二选一。**

也就是说，在一次 reasoning 里，模型可能同时产生三类东西：

```text
assistant message
├── ThinkingBlock   思考过程或模型内部推理片段
├── TextBlock       对用户可见的说明、阶段性表达
└── ToolUseBlock    下一步要执行的工具调用
```

`ReActAgent` 选择把它们聚合进同一个 assistant message，背后的思想是：**这一轮模型的“认知结果”是一个整体**。文本、思考、工具调用不是三段互不相干的输出，而是同一次模型决策的不同侧面。

为什么要这样做？

第一，**保持因果完整性**。

比如模型这一轮输出：

```text
我需要先查询数据库确认订单状态。
tool_call: query_order(orderId=123)
```

这里的文本和工具调用其实是一体的。文本解释了为什么要调用工具，工具调用表达了下一步行动。如果框架强行只保留工具调用，用户或 trace 系统就看不到模型为什么这么做；如果只保留文本，就丢了行动意图。

聚合成一个 assistant message 后，Memory 里保存的是完整决策：

```text
assistant:
  text: 我需要先查询数据库确认订单状态。
  tool_use: query_order(...)
```

这比拆散成多个孤立消息更忠实。

第二，**适配现代模型的真实输出协议**。

现在很多模型并不是只返回纯文本。它们可能流式返回：

```text
thinking delta
text delta
tool call name
tool call args delta
usage
```

尤其是 Anthropic、Gemini、OpenAI 新一些的接口，都越来越像“content blocks”协议，而不是一个字符串协议。`ReActAgent` 用 `ReasoningContext` 把这些 block 累积起来，本质上是在顺应模型原生输出形态。

**第三，方便恢复和 pending tool 判断。**

工具调用要恢复，最关键的是这条 assistant message 里有没有 `ToolUseBlock`，以及对应的 `id` 是什么。

如果一轮 reasoning 产生多个 tool calls，放在同一个 assistant message 里，框架就能明确知道：

```text
这一轮 assistant 同时请求了 call_1、call_2、call_3
```

后面 Memory 里只要检查有没有对应的 `ToolResultBlock(id=...)`，就能判断哪些工具完成了，哪些还是 pending。

这对暂停恢复、外部工具执行、HITL 很重要。

**第四，避免人为把模型行为切成不自然的阶段。**

传统 ReAct 论文里常写成：

```text
Thought: ...
Action: ...
Observation: ...
Thought: ...
Action: ...
```

这是一种文本格式化的表达。但现代 tool calling 里，模型的一轮 assistant 输出本来就可以既包含思考/说明，也包含工具调用。如果框架强制规定“有工具调用时不能有文本”，就会损失表达能力。

比如模型可能需要告诉用户：

```text
我会先查库存，然后再给你最终答复。
tool_call: check_inventory(...)
```

这不是最终答案，但它是合理的阶段性沟通。

**第五，让 UI、日志、trace 更自然。**

如果文本、thinking、tool call 都在一个 assistant message 里，前端可以展示为：

```text
Assistant 正在分析...
Assistant: 我需要先查一下库存。
Tool call: check_inventory(...)
```

这比框架内部把它们拆成几条不相关的消息更容易解释，也更适合做调试和审计。

至于“主流 agent 都是这样吗”，答案是：**方向上越来越主流，但实现细节不完全一样。**

很多现代框架已经采用类似思想：

- LangChain 的 `AIMessage` 可以同时带 `content` 和 `tool_calls`。
- OpenAI/Anthropic/Gemini 的模型协议都在往 content blocks / tool calls / reasoning blocks 的方向发展。
- 很多 agent runtime 都会把“一轮 assistant 输出”作为一个完整 turn 保存。

但也有不少简单 agent 框架仍然采用更老的模式：

```text
如果模型调用工具，则 assistant content 为空，只保存 tool_call。
工具执行后，再让模型生成最终文本。
```

这种模式简单，但表达力弱一些。

所以更准确地说：

**把 text、thinking、tool_use 聚合成一个 assistant message，是现代 tool-calling agent runtime 的主流趋势，但不是所有框架都做得这么完整。**

`ReActAgent` 这里做得比较深，因为它不是只服务“聊天”，而是服务可恢复、可流式、可审计、可 Hook 扩展的 agent runtime。它保存的不是一句回答，而是模型这一轮完整的“决策记录”。

## 四. 什么是 suspended？外部执行指的是什么？

`suspended` 可以理解成：**工具调用被“挂起”了，框架没有真正完成这个工具，只是把工具请求交还给外部系统或人来处理。**

标准工具执行是这样：

```text
模型：我要调用 search(query="...")
框架：找到 search 工具并执行
工具：返回结果
框架：把 ToolResultBlock 写回 Memory
模型：基于结果继续回答
```

`suspended` 是这样：

```text
模型：我要调用 some_external_tool(...)
框架：发现这个工具不能/不该在框架内部执行
框架：返回 TOOL_SUSPENDED
外部系统或人：去执行这个工具
外部系统或人：把 ToolResultBlock 传回 agent
agent：恢复继续推理
```

这里的“外部执行”指的是：**工具的真实执行不在 ReActAgent 当前进程里完成**。

常见场景有几类。

**第一类：只注册了工具 schema，没有注册真实实现。**

比如框架只知道有个工具：

```text
transfer_money(amount, toAccount)
```

但 Java 里没有真正的 `AgentTool.callAsync()` 实现，或者这个工具被注册成 `SchemaOnlyTool`。模型可以生成调用参数，但框架不会真的转账。它会把这个调用返回给业务系统，让业务系统决定是否执行。

**第二类：高风险工具，需要人工确认。**

比如：

```text
delete_database(...)
send_email(...)
place_order(...)
transfer_money(...)
deploy_to_production(...)
```

框架不应该模型一说就执行。工具可以主动抛出 `ToolSuspendException`，意思是：

```text
这个工具需要外部确认，我先挂起。
```

然后前端展示给人：

```text
Agent 想执行：send_email(to=..., body=...)
是否确认？
```

人确认后，业务系统执行邮件发送，再把结果补回 agent。

**第三类：工具在远端系统执行。**

比如工具需要由：

- 浏览器端执行
- 移动端执行
- 企业内部审批流执行
- 另一个微服务执行
- 云函数执行
- 队列 worker 执行
- 人工工单系统执行

当前 Java agent 进程只负责生成结构化的工具请求，不直接接触真实执行环境。

**第四类：需要异步长任务。**

比如：

```text
generate_video(...)
run_big_data_job(...)
train_model(...)
crawl_website(...)
```

这些任务可能要跑几分钟甚至几小时。ReActAgent 当前这次 `call()` 不适合一直等。工具可以 suspended，把任务提交给外部任务系统。等任务完成后，再用对应 `ToolResultBlock(id=...)` 恢复 agent。

为什么“框架不能伪造成功结果”？

因为 tool result 是模型下一轮推理的事实依据。如果工具没执行，框架却写：

```text
ToolResultBlock: success
```

模型就会基于假的观察继续回答。这会非常危险。

所以 suspended 的本质是诚实地说：

```text
模型已经提出了行动请求；
但这个行动还没有完成；
当前 agent 必须暂停；
等外部给我真实结果，我再继续。
```

恢复时靠 tool call id 对齐：

```text
assistant: ToolUseBlock(id="call_1", name="send_email", input={...})

外部执行后补回：

tool: ToolResultBlock(id="call_1", name="send_email", output="Email sent successfully")
```

只要 `id` 对上，ReActAgent 就知道这个 pending tool 已经闭合，可以继续 reasoning。

## 五. 你说不适合一直等，那么是怎么做到类似异步的结果的？外部执行完成又是怎么通知到agent的插入进去？

它不是 agent 自己“后台等结果”，而是把一次工具调用变成了一个**可恢复的暂停点**。

核心机制是：

```text
1. 模型产生 ToolUseBlock(id="call_1")
2. 工具返回 suspended ToolResultBlock
3. ReActAgent 返回 TOOL_SUSPENDED 给调用方
4. 当前这次 call 结束
5. 外部系统异步执行真实任务
6. 外部系统完成后，再次调用 agent.call(toolResultMsg)
7. ReActAgent 校验 id，把 ToolResultBlock 写入 Memory
8. agent 继续 reasoning
```

所以“异步”不是在 `ReActAgent` 内部开线程等，而是通过 **返回 suspended 状态 + 之后补 ToolResultBlock** 实现。

举个例子。

模型说：

```text
ToolUseBlock(
  id="call_1",
  name="generate_video",
  input={ "prompt": "做一个产品介绍视频" }
)
```

框架里的工具发现这是长任务，于是挂起：

```java
throw new ToolSuspendException("Video generation submitted externally");
```

`ToolExecutor` 会把它转成 suspended result。然后 `ReActAgent` 返回：

```text
Msg(
  generateReason = TOOL_SUSPENDED,
  content = [
    ToolUseBlock(id="call_1", name="generate_video", input={...}),
    ToolResultBlock(id="call_1", metadata={suspended=true})
  ]
)
```

这时调用方拿到的不是最终答案，而是一个结构化的“待执行任务”。

外部系统可以做这些事：

```text
1. 读取返回消息里的 ToolUseBlock
2. 把 generate_video 任务投递到队列 / worker / 云函数
3. 立刻把当前 HTTP 请求结束，告诉用户任务已提交
4. worker 慢慢执行
5. 执行完成后拿到结果
```

完成后，外部系统要“通知 agent”，本质上就是**再次调用 agent，并把工具结果传回去**：

```java
Msg toolResultMsg = Msg.builder()
    .role(MsgRole.TOOL)
    .name("generate_video")
    .content(
        ToolResultBlock.builder()
            .id("call_1")
            .name("generate_video")
            .output(List.of(
                TextBlock.builder()
                    .text("视频已生成：https://example.com/video.mp4")
                    .build()
            ))
            .build()
    )
    .build();

agent.call(List.of(toolResultMsg));
```

`ReActAgent.doCall` 开头会检查 Memory：

```text
Memory 里最后一条 assistant message 有 ToolUseBlock(id="call_1")
但还没有 ToolResultBlock(id="call_1")
```

所以它知道现在有 pending tool。

然后它看到这次输入里有：

```text
ToolResultBlock(id="call_1")
```

就会：

```text
1. 校验这个 id 确实属于 pending tool
2. 把 toolResultMsg 写入 Memory
3. 如果还有别的 pending tool，继续 acting
4. 如果 pending 都补齐了，进入 reasoning(0)
```

于是下一轮模型看到的上下文就是：

```text
assistant: 我要生成视频
tool_use: generate_video(id="call_1", prompt="...")

tool: 视频已生成：https://example.com/video.mp4
```

模型就可以继续回答：

```text
视频已经生成，这是链接...
```

这就是“插入进去”的方式：**不是修改模型内部状态，而是把外部执行结果作为一条 `TOOL` 角色消息补进 Memory。**

如果是分布式环境，关键是 Memory/Session 要能持久化。流程会变成：

```text
节点 A:
  agent.call(userMsg)
  -> 返回 TOOL_SUSPENDED
  -> Session 保存 Memory，其中有 ToolUseBlock(id="call_1")

外部 worker:
  执行真实任务
  -> 生成 ToolResultBlock(id="call_1")

节点 B:
  加载同一个 session 的 agent state
  agent.call(toolResultMsg)
  -> 补入 Memory
  -> 继续 reasoning
```

所以它依赖三个东西：

1. **tool call id**
   用来精确匹配哪个工具调用完成了。

2. **Memory/Session**
   用来保存“之前模型发起过 call_1”这个事实。

3. **调用方再次调用 agent**
   用来把外部结果补回来。

一句话：  

**ReActAgent 的异步不是内部 await，而是协议级暂停恢复。它把未完成工具调用暴露成 `TOOL_SUSPENDED`，外部执行完成后用同一个 tool call id 补 `ToolResultBlock`，agent 再从 Memory 继续推理。**

## 六. 累积 streaming tool call chunks 这一步是什么意思？在流程当中的作用是什么？

“累积 streaming tool call chunks”指的是：**模型在流式输出工具调用时，工具调用本身也可能不是一次性完整返回的，而是像文本一样分片返回；框架需要把这些碎片拼成一个完整的 `ToolUseBlock`。**

举个抽象例子，模型最终想调用：

```json
{
  "id": "call_1",
  "name": "search",
  "input": {
    "query": "AgentScope Java ReActAgent"
  }
}
```

但在 stream 模式下，它可能分几次吐出来：

```text
chunk1: id=call_1, name=search, input={"que
chunk2: ry":"AgentScope Java
chunk3:  ReActAgent"}
```

如果框架每收到一个 chunk 就直接当成完整工具调用执行，那会出大问题：参数不完整、JSON 不完整、工具名可能还没齐，甚至同一个工具会被误执行多次。

所以 `ReasoningContext` 的作用之一就是：

```text
每收到一个 ChatResponse chunk
    如果是文本：累积文本
    如果是 thinking：累积思考
    如果是 tool call：按 tool call id 累积工具调用片段
最后 stream 结束
    buildFinalMessage()
    生成完整 assistant message
```

它在流程里的作用是三层：

1. **保证工具调用完整性**  
   `acting()` 只能执行完整的 `ToolUseBlock`，不能执行半截参数。

2. **支持流式观察**  
   前端或 `StreamingHook` 可以边收到边展示“模型正在准备调用某个工具”，但真正执行要等最终 assistant message 构建完成。

3. **保证 Memory 里只写入完整协议状态**  
   Memory 不能存半截 tool call。最终写进去的是完整 assistant message，后续 pending tool 判断才可靠。

所以这一步的本质是：

> 把模型流式吐出的“工具调用碎片”暂存在 `ReasoningContext`，等模型这一轮 reasoning 结束后，拼成完整的 `ToolUseBlock`，再交给 ReAct 状态机判断是否进入 acting。
