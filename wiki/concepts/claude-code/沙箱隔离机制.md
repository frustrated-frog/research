# 沙箱隔离机制

> Claude Code 的沙箱机制是执行层安全边界：权限系统决定动作是否允许，沙箱限制动作实际能影响的资源范围。

## 核心思想

Claude Code 中，安全不是一个开关，而是多层治理：

```text
权限系统：这个动作该不该做？
沙箱系统：即使做了，它最多能影响什么？
```

权限系统属于应用层，处理 Allow / Ask / Deny、规则优先级、用户确认和工具检查。沙箱属于执行层，通过操作系统隔离限制 Bash / Shell 操作的文件系统、网络和环境访问。

## 分层架构

```text
应用层：BashTool / PowerShellTool / Shell
  ↓
适配层：sandbox-adapter
  ↓
运行时层：sandbox-runtime
  ↓
系统层：macOS sandbox-exec / Linux bubblewrap
```

适配层负责把 Claude Code 的权限规则、设置系统和平台差异转换成底层 sandbox runtime 能理解的配置。

## 平台实现

| 平台 | 底层技术 | 说明 |
|------|----------|------|
| macOS | `sandbox-exec` | 系统内置 |
| Linux | `bubblewrap` | 需要 bwrap / socat |
| WSL2 | `bubblewrap` | 支持 |
| WSL1 / Windows | 不支持或受限 | 技术限制 |

## 文件系统隔离

沙箱通过 allow/deny 规则限制文件访问：

- `allowWrite`：允许写入路径
- `denyWrite`：禁止写入路径
- `allowRead`：允许读取路径
- `denyRead`：禁止读取路径

同时还有自动安全策略：

- 阻止写入配置文件，避免修改安全策略
- 阻止写入 `.claude/skills`，避免注入恶意 skill
- 防护 Git bare repository 攻击
- Worktree 场景下允许必要的 `.git` 操作

## 网络隔离

沙箱可以限制允许访问的域名、禁止访问的域名、本地绑定、Unix socket、HTTP/SOCKS 代理等。

这让 WebFetch、Bash 等工具在联网时也能受到治理，而不是只靠 prompt 告诉模型“不要访问危险网站”。

## 命令排除与回退

并非所有命令都必须进入沙箱。Claude Code 支持 excludedCommands，例如：

```text
npm run test:*
git status
bazel *
```

这用于排除已知安全、需要特殊环境或长期运行的命令。

同时，沙箱不可用时可以根据配置决定：

- 直接失败
- 回退到非沙箱执行，但仍经过权限系统
- 严格模式下禁止回退

## 关联页面

- [[concepts/claude-code/工具架构与注册机制|工具架构与注册机制]]

原因是：

- 权限系统让用户理解 Agent 的意图
- 沙箱系统限制意图造成的后果
- 两者叠加才构成纵深防御

典型执行路径：

```text
模型生成 Bash 命令
  -> 权限系统判断 Allow / Ask / Deny
  -> 如果允许，Shell 用沙箱包装命令
  -> OS 在隔离环境中执行
  -> 输出返回工具结果
```

## 设计启发

如果设计自己的 Agent，安全至少拆成三层：

| 层级 | 问题 |
|------|------|
| 意图层 | 模型想做什么？ |
| 审批层 | 这个动作是否允许？ |
| 执行层 | 即使允许，它能影响哪些资源？ |

不要把安全简化成一个确认弹窗。真正的工程安全，是让误判也有边界。
