# 上下文压缩策略

> Claude Code 的上下文压缩不是简单“删旧消息”或“做摘要”，而是按信息生命周期进行分层处理。

## 核心思想

长会话中，历史消息、工具结果、文件内容、图片、搜索结果都会不断挤占上下文窗口。Claude Code 的策略不是等满了再粗暴摘要，而是用多层压缩机制逐步释放空间。

设计原则可以概括为：

> 上下文压缩不是删除历史，而是把不同生命周期的信息放到不同层。

## 三层压缩

| 层级 | 触发/用途 | 是否调用模型 | 核心动作 |
|------|-----------|--------------|----------|
| MicroCompact | 局部清理旧工具结果 | 否 | 清理 Read/Bash/Grep/Glob/WebSearch 等可重取内容 |
| Session Memory Compact | 使用已有 session memory | 否 | 用已提取的 session memory 替代大段历史 |
| API 摘要压缩 | 手动 compact 或自动回退 | 是 | 调用模型生成摘要 |

## MicroCompact：先清理可再获取的信息

MicroCompact 的价值在于低成本。它不改变对话结构，也不依赖模型，而是清理旧工具结果。

典型可清理内容：

- 文件读取结果：可以重新 Read
- 搜索结果：可以重新 Grep/Glob/WebSearch
- 命令输出：通常只对当时有意义
- 图片和文档：可替换为占位符
- 写入/编辑结果：动作已经完成，详细输出不一定继续需要

这说明 Claude Code 对信息做了一个重要分类：

> 可重新获得的信息，不应该长期占据模型上下文。

## 协议完整性保护

上下文压缩最危险的地方，是破坏模型 API 的消息不变量。例如保留了 `tool_result`，却删掉对应的 `tool_use`，就会导致下一次 API 调用失败。

因此 Claude Code 会在压缩时保护工具调用对：

```text
assistant: tool_use(id=call_1)
user/tool: tool_result(tool_use_id=call_1)
```

这对内容必须保持协议闭环。压缩策略不是只看 token 数，而要维护消息协议的合法性。

## 保留最近窗口

Session Memory Compact 会保留最近一段上下文窗口，避免摘要后丢失当前任务的局部语境。它考虑：

- 至少保留一定 token 数
- 至少保留若干文本消息
- 控制最大 token 上限
- 必要时向前扩展，保护 tool pair 和 thinking block

这体现了一个成熟判断：

> 摘要负责长期连续性，最近窗口负责当前操作连续性。

## 与 DeerFlow 的对照

DeerFlow 也采用分层思路：

- [[../deerflow-book/记忆三层架构]]：长期信息分层保存
- [[../../entities/deerflow-book/中间件管道]]：SummarizationMiddleware 负责摘要
- TodoMiddleware 在摘要后重新注入任务列表，防止 Agent 忘记当前任务
- MemoryMiddleware 把值得沉淀的信息异步写入长期记忆

两个项目共同说明：上下文工程不是“prompt 越长越好”，而是设计信息在不同层之间的流动。

## 设计启发

如果设计自己的 Agent，可以把上下文分为：

| 信息 | 处理方式 |
|------|----------|
| 最近对话 | 保留在工作上下文 |
| 当前任务列表 | 显式状态保存并可重注入 |
| 大工具结果 | 落盘或替换为引用 |
| 稳定用户偏好 | 写入长期记忆 |
| 可重查资料 | 保留查询条件或路径 |
| 工具调用协议 | 压缩时保护闭环 |

真正的上下文压缩，不是问“删什么”，而是问“这条信息未来如何再次被使用”。
