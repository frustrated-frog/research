# 会话交接

**会话交接** 指每次 agent 会话结束前必须完成的状态整理工作，确保下一个会话能直接开始工作而不需要"先收拾烂摊子"。

## 问题背景

没有清洁交接时，12 周后的典型数据：
- 构建通过率：从 100% 跌到 68%
- 测试通过率：从 100% 跌到 61%
- 新会话启动时间：从 5 分钟涨到 60+ 分钟

"以后再清理"等于永远不清理——熵增是默认状态，只有主动清洁操作才能对抗。

## 清洁状态五条件

会话结束时必须满足：
1. **构建通过**：`npm run build` 成功
2. **测试通过**：`npm test` 全绿
3. **进度已记录**：功能清单和 PROGRESS.md 更新
4. **无过时工件**：调试代码、临时文件、TODO 标记清理干净
5. **启动路径可用**：`npm run dev` 能正常运行

## 双模式清理策略

### 即时清理（每个会话结束时）
- 清理本次会话创建的临时工件
- 更新功能清单状态
- 确保构建和测试通过

类比："引用计数式"清理——用完就清，不留到第二天。

### 定期清理（每周一次）
- 全系统扫描，处理累积的结构性问题
- 更新质量文档
- 运行基准测试检测漂移

类比："追踪式"清理——定期大扫除。

## 质量文档

对每个模块持续评分的活跃工件：
```markdown
## 用户认证模块 (质量: A)
- 验证通过: 是
- agent 可理解: 是
- 测试稳定性: 稳定

## 支付模块 (质量: C)
- 验证通过: 部分（支付回调未测试）
- agent 可理解: 困难（逻辑分散在 3 个文件）
```

## 定期简化 Harness

随着模型能力提升，移除不再必要的 harness 组件。Anthropic 实验：Sonnet 4.5 需要 sprint 拆分机制，Opus 4.6 原生能力已可自主处理工作分解，sprint 构造变成不必要开销。

推荐做法：每月挑一个 harness 组件暂时禁用，跑基准任务。如果结果没退化，永久移除。

## 跨运行时交接的额外约束

[原文事实] [[summaries/运行时独立持久智能体|Runtime-Independent Persistent Agents]] 的迁移协议将普通“清洁交接”扩展为六步：quiesce/fence、checkpoint、validate、bind、rehydrate、verify/resume。源执行在目标验证成功前仍保有权威；目标取得新 authority epoch 后，源执行必须被 fence（PDF 第 4 页）。

对会话内的交接，更新进度与验证结果通常已经足够；对 host、harness、模型或交互面发生替换的交接，还应额外核验：身份与谱系、memory/workflow 的祖先关系、body revision、唯一协作 authority、显式 capability delta，以及运行时标签没有覆盖安装身份。该论文将这些列为系统连续性不变量；它并未证明新模型会产生相同的行为或人格表现（PDF 第 5–7 页）。
