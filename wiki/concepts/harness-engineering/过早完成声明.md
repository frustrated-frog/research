# 过早完成声明

**过早完成声明（Premature Completion）** 是 agent 的主要失败模式之一：agent 断言任务完成，但实际上存在未满足的正确性规范。核心问题：agent 依据代码层面的局部信心做判断，系统级正确性需要全局验证。

## 问题背景

Guo 等人 2017 年证明：现代神经网络系统性地过度自信——模型自报的置信度显著高于实际准确率。

Agent 过早完成的标准套路：
1. 代码看着还行（语法正确、逻辑合理）
2. Harness 没有强制要求全面执行验证
3. 跳过了实际运行或只跑了部分测试
4. "代码看起来没问题"被当作"功能已完成"的证据

## 置信度校准偏差

agent 自报的完成信心与实际完成质量之间的系统性差距。对复杂多文件任务，这个偏差显著为正——agent 总是比实际做得更自信。

就像学生考完试估分总是偏高。

## 单元测试通过 ≠ 任务完成

单元测试的设计哲学（隔离被测单元、模拟依赖）恰好使其无法检测跨组件问题：
- **接口不匹配**：渲染进程和预加载脚本期望不同的路径格式，各自单元测试都 mock 了对方，通过了但集成时出问题
- **状态传播错误**：数据库迁移改了表结构，ORM 缓存层还持有旧结构，单元测试每次全新 mock 环境不会暴露
- **环境依赖性**：测试环境一切 mock 正确，真实环境因配置差异失败

## 三层终止校验

**第一层：语法与静态分析**（成本最低，信息量最小）
- lint / typecheck
- 必须通过，这是最低限度检查

**第二层：运行时行为验证**（核心完成证据）
- 测试执行
- 应用启动检查
- 关键路径验证

**第三层：系统级确认**（最后防线）
- 端到端测试
- 集成验证
- 用户场景模拟

## 解决之道：干活的人和检查的人分开

Anthropic 实验数据：

| 架构 | 时长 | 成本 | 核心功能是否可用 |
|------|------|------|---------------|
| 单 agent 裸跑 | 20 分钟 | $9 | 否 |
| 三 agent（planner + generator + evaluator） | 6 小时 | $200 | 是 |

同一模型（Opus 4.5），同一任务。区别只在 harness——planner 扩展需求，generator 逐功能实现，evaluator 用 Playwright 实际点击测试。

## 面向 agent 的错误消息

好的错误消息要像老师的红笔批注——包含"怎么修"的具体步骤：

```
ERROR: POST /api/reset-password returned 500
WHY: email service config missing in environment variables
FIX: Add EMAIL_SERVICE_API_KEY to .env and restart server
```
