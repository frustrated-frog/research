# Harness驾驭层

**Harness（驾驭层）** 是模型权重之外的一切工程基础设施——指令、工具、环境、状态管理、验证反馈。类比：模型是千里马，harness 是马鞍。同一匹马，配不配马鞍，产出有本质差异。

## 定义

Harness = AI agent 执行任务所需的全部工程基础设施，不包括模型权重本身。具体包含五个子系统：

| 子系统 | 类比 | 核心产出 |
|--------|------|---------|
| 指令子系统 | 菜谱架 | AGENTS.md / CLAUDE.md |
| 工具子系统 | 刀具架 | shell / 文件 / 测试 |
| 环境子系统 | 灶台 | 依赖 / 服务 / 版本 |
| 状态子系统 | 备菜台 | PROGRESS.md / git |
| 反馈子系统 | 出菜检查口 | test / lint / build |

## 问题背景

即使最强模型（Claude Max、GPT-4o），裸跑做真实任务仍然不可靠：
- 需求说不清楚 → agent 自己猜
- 项目隐含规则 agent 不知道 → 违反架构约定
- 没有验证手段 → "代码写完了" ≠ "功能跑通了"
- 跨会话状态丢失 → 每个新会话从零开始

## 核心机制

### 五元组审计框架

对每个项目按五元组做完整审计，每个子系统打 1-5 分。最低分的子系统是瓶颈，集中精力改进。

### 等模型对照实验

保持模型不变，逐个移除五个子系统，看哪个移除后性能下降最多。那个就是瓶颈。

### 诊断循环

```
执行 → 观察失败 → 定位到 harness 的哪一层 → 修补那一层 → 重新执行
```

每次失败都归因到具体层，不要笼统说"模型不行"。

## 五层防御模型

Harness 本质上是五层防御体系：

1. **任务规范层** — 需求说清楚了吗？完成定义明确了吗？
2. **上下文供给层** — agent 能看到所有必要信息吗？
3. **执行环境层** — 环境配置完整吗？依赖版本对吗？
4. **验证反馈层** — 有没有验证手段？验证命令告诉 agent 了吗？
5. **状态管理层** — 跨会话状态能恢复吗？

## 关键结论

- **遇到失败先修 harness**：同一个模型在结构良好的任务中能成功，就优先假设是 harness 问题
- **换模型是成本最高的选择**：大多数"模型不行"的结论，经分析都是 harness 问题
- **Harness 会腐化**：需要像还技术债一样还 harness 债
