# 可观测性

**可观测性（Observability）** 是 harness 的架构属性，不是事后添加的功能。核心作用：让 agent 在不确定状态中做决策时，有客观信号指导方向。

## 问题背景

没有可观测性时，四类问题系统性出现：
1. **无法区分"正确"和"看似正确"**：代码审查看起来对，运行时边界条件处理错误
2. **评估变成玄学**：没有评分标准，质量评估不可复现
3. **重试变成盲猜**：不知道为什么失败，重试方向随机
4. **会话交接信息断崖**：新会话必须从零诊断，重复诊断占 30-50% 会话时间

## 双层可观测性

### 运行时可观测性
系统层的信号——日志、追踪、进程事件、健康检查。回答"系统做了什么"。相当于仪表盘：速度、油量、发动机温度。

### 过程可观测性
harness 决策工件的可见性——计划、评分标准、验收条件。回答"为什么这个变更应该被接受"。相当于导航系统：知道现在在哪，还知道为什么走这条路。

## 核心工具

### 冲刺合同（Sprint Contract）
编码开始前协商的短期协议：
```markdown
# 冲刺合同: 暗色模式支持

## 范围
- 修改主题切换组件
- 更新全局 CSS 变量

## 验证标准
- 每个组件的视觉回归测试通过
- 主流程端到端测试通过

## 排除项
- 不处理打印样式
```

### 评估评分标准
把"好不好"变成可量化的评分：

| 维度 | A | B | C | D |
|------|---|---|---|---|
| 代码正确性 | 所有测试通过 | 主流程通过 | 部分通过 | 编译失败 |
| 架构合规 | 完全合规 | 轻微偏离 | 明显偏离 | 严重违反 |

### 任务轨迹（Task Trace）
一个任务从开始到完成的完整决策路径记录。agent 的每一步操作及其上下文都被记录，类似分布式系统中的请求追踪。

HarnessDev 为这一定义提供了一个可操作的评测实例：每次运行保留冻结 harness 源码、`trajectory.jsonl`、结果、日志与领域权威产物，官方评分不信任 harness 自报状态。其 Evolution 结果还显示，只有轨迹存在并不保证诊断发生——专门轨迹接口很少被调用，且小 probe 可能与完整评测矛盾。详见 [[summaries/HarnessDev：LLM能否创建并演化自己的Agent Harness]]。

## Anthropic 三 agent 架构

- **Planner（规划者）**：接收 1-4 句话需求，扩展成完整产品规格。约束交付物，让 agent 在执行中自己找到路径。
- **Generator（生成者）**：按 sprint 逐功能实现。按 sprint 合同施工，不按感觉施工。
- **Evaluator（评估者）**：用 Playwright MCP 实际点击测试，按四个维度评分。
