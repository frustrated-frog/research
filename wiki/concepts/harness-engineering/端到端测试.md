# 端到端测试

**端到端测试（E2E Test）** 是验证系统级正确性的关键手段，只有端到端测试能证明组件边界缺陷不存在。

## 问题背景

单元测试通过 ≠ 任务完成。Google 测试金字塔告诉我们：大量单元测试是基础，但止步于此会系统性地漏掉组件交互问题。

Agent 倾向于只跑最快测试然后宣告完成——这个行为模式加剧了问题。

## 单元测试的盲区

单元测试的设计哲学是隔离，恰好制造了系统性盲区：

| 缺陷类型 | 描述 | 单元测试 | 端到端 |
|---------|------|---------|--------|
| 接口不匹配 | 路径格式不一致 | 未检测 | 检测 |
| 状态传播 | ORM 缓存层不一致 | 未检测 | 检测 |
| 资源泄漏 | 大文件句柄未释放 | 未检测 | 检测 |
| 权限问题 | 打包环境权限不同 | 未检测 | 检测 |

## 端到端测试不仅改变结果，还改变行为

当 agent 知道它的工作要过端到端测试时，编码行为会改变：
1. **考虑组件交互**：写代码时会想"这个接口和上游怎么对接"
2. **尊重架构边界**：有架构约束迫使 agent 遵守边界规则
3. **处理错误路径**：端到端测试通常包含故障场景，迫使 agent 考虑异常处理

## 架构规则必须可执行

把架构文档里的规则变成可执行的自动化检查：

```bash
# 检查渲染进程是否直接调用 Node.js API
grep -r "require('fs')" src/renderer/ && exit 1 || echo "OK"
```

错误消息要包含修复指导：

```
ERROR: Found direct import of 'fs' in src/renderer/App.tsx:12
WHY: Renderer process has no access to Node.js APIs for security
FIX: Move file operations to src/preload/file-ops.ts and call via window.api.readFile()
```

## 审查反馈提升

每次在代码审查中发现新类型的 agent 错误，就把它变成自动化检查。一个月后 harness 会比月初强得多。
