# 功能清单

**功能清单（Feature List）** 是 harness 的"脊梁骨"——整个 harness 的核心数据结构。调度器靠它选任务，验证器靠它判完成，交接器靠它生成报告。

## 定义

功能清单服务四个 harness 组件：
1. **调度器**：读状态，选下一个 `not_started` 的功能
2. **验证器**：执行验证命令，判断是否允许状态转移
3. **交接报告器**：从功能清单自动生成会话交接摘要
4. **进度追踪器**：统计各状态分布，提供项目健康度指标

## 三元组结构

每个功能项是 `(行为描述, 验证命令, 当前状态)` 的三元组：

```json
{
  "id": "F03",
  "behavior": "POST /cart/items returns 201",
  "verification": "curl -X POST http://localhost:3000/api/cart/items ... | jq .status == 201",
  "state": "passing",
  "evidence": "commit abc123"
}
```

缺了任何一项，这个功能项就不完整。

## 状态机

每个功能项有四种状态：
- `not_started` — 未开始
- `active` — 进行中
- `blocked` — 被阻塞
- `passing` — 已通过

状态转移由 harness 控制，不是 agent 想改就能改。功能从 `active` 变成 `passing` 的唯一方式是验证命令执行成功。

## 为什么是"原语"

文档是给人看的，原语是给系统用的。文档可以被忽略，原语不能被绕过。

类比数据库的触发器约束 vs 应用层检查逻辑：前者由数据库引擎强制执行，后者可能被意外绕过。功能清单作为 harness 原语，就是数据库级别的约束。

## 粒度校准

每个功能项应该是"一次会话能完成"的范围：
- 太粗了做不完
- 太细了管理开销大

好粒度例子："用户可以添加商品到购物车"
太粗："实现购物车"
太细："创建 Cart 模型的 name 字段"
