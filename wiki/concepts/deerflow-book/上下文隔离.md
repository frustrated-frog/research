# 上下文隔离

**上下文隔离（Context Isolation）** 是 DeerFlow Sub-agent 架构的核心设计原则——每个 Agent（无论是 Lead Agent 还是 Sub-agent）只能看到自己被明确传递的信息，而非全局上下文。Sub-agent 执行过程中的所有中间步骤、工具调用结果、思考过程都不会泄漏到 Lead Agent 的上下文中；它完成后只返回最终结果。

## 隔离的具体含义

当 Lead Agent 使用 `task` 工具将任务委派给 Sub-agent 时，传递的信息只有：

```python
task(
    description="AWS 分析",           # 仅用于日志展示
    prompt="详细分析 AWS 的核心服务...",  # Sub-agent 唯一的信息来源
    subagent_type="general-purpose"
)
```

Sub-agent 的 `prompt` 参数是它能看到的全部上下文。它不会自动继承 Lead Agent 之前的对话历史、已读取的文件内容、或记忆中关于用户的背景信息。

Sub-agent 自己的消息历史（包括工具调用、AI 思考、Tool 执行结果）也完全独立，不会流回到 Lead Agent 的消息列表中。Sub-agent 完成后，通过 `SubagentResult` 数据结构只返回：

- `result`：最终输出文本（几百到几千 tokens）
- `status`：执行状态
- `artifacts`：Sub-agent 产生的文件路径列表

## 为什么需要上下文隔离

这里有一个看似矛盾的设计动机：长时程 Agent 需要多步骤执行，而 Sub-agent 的中间步骤如果全部回流到 Lead Agent 上下文，会造成严重的上下文膨胀。

以"调研 10 篇论文"为例：

**无隔离方案**：Lead Agent 委派 10 个 Sub-agent，每个 Sub-agent 可能进行 5-10 轮工具调用（搜索 → 阅读 → 总结 → 再搜索 → 再总结）。假设每轮 500 tokens，总共 10 × 10 × 500 = 50,000 tokens 的中间数据涌入 Lead Agent 上下文。

**有隔离方案**：每个 Sub-agent 只在最后返回一个 500 token 的摘要，10 个 Sub-agent 共 5,000 tokens。中间过程全部隔离在各自的执行环境中。

这个差距在 10 个任务时是 10 倍，在更复杂的场景（20 个 Sub-agent 并行）差距会更大。

## 隔离的工程实现

Sub-agent 的上下文隔离在 `SubagentExecutor` 中通过以下机制实现：

**独立的 LangGraph 图实例**：每个 Sub-agent 调用 `create_react_agent()` 创建自己独立的图实例，拥有独立的消息列表和状态。这与 Lead Agent 共享同一个图实例（通过 Checkpointer 实现跨轮持久化）形成鲜明对比。

**消息过滤**：`MemoryMiddleware` 在捕获对话时，只处理当前 Agent 的消息列表，不会跨 Agent 共享数据。

**文件系统作为信息桥梁**：Sub-agent 可以将产出物写入 `/mnt/user-data/outputs/`，Lead Agent 通过 `artifacts` 列表知道有哪些文件被生成，可以调用 `present_files` 工具将文件内容注入上下文。这是一种**显式的、按需的信息传递**而非隐式的上下文污染。

## 隔离的边界：什么信息会被共享

上下文隔离是精细的，而非绝对的。以下是信息共享的合法通道：

| 信息类型 | 是否共享 | 共享方式 |
|---------|---------|---------|
| Skill 元数据（name + description） | 是 | System Prompt 启动时全量注入 |
| 用户在 prompt 中显式传递的背景 | 是 | `task` 工具的 `prompt` 参数 |
| Sub-agent 的最终输出文本 | 是 | `SubagentResult.result` |
| Sub-agent 生成的文件 | 是 | `SubagentResult.artifacts` + `present_files` |
| Sub-agent 的中间推理步骤 | 否 | 完全隔离 |
| Sub-agent 调用的工具列表 | 否 | 不共享 |
| Lead Agent 的消息历史 | 否 | Sub-agent 无权访问 |

## 隔离与协作的平衡

上下文隔离带来一个新的问题：Sub-agent 如果完全不知道 Lead Agent 之前做了什么，可能会做出与整体任务不一致的判断。

DeerFlow 的解法是**让开发者通过 prompt 参数主动传递必要的上下文**。Skill `deep-research` 的示例 prompt 中包含了明确的上下文说明：

```
分析论文 'Deep Residual Learning for Image Recognition':
1. 核心贡献和创新点
2. 技术方法概要
3. 实验结果和关键数据
4. 对后续工作的影响
使用 web_search 搜索论文信息，并提供引用链接。
```

这里"分析论文"这个任务本身是自包含的，不需要 Lead Agent 的额外上下文。但对于需要共享信息的场景（如"竞品分析"需要知道用户所在行业），开发者需要在 prompt 中明确说明，而不是假设 Sub-agent 能"看到"。

## 小结

上下文隔离是 DeerFlow 多 Agent 架构的基石设计——通过限制信息流动的方向（Sub-agent → Lead Agent 只有最终结果），换取了上下文空间的可控性。这种设计既避免了"所有信息堆积在一个上下文里"的膨胀问题，又通过 prompt 参数和 artifacts 提供了显式的信息传递通道。理解这个设计，有助于你在编写复杂的多步骤任务时，正确地通过 prompt 传递必要的背景信息，同时依赖隔离机制保持上下文的整洁。
