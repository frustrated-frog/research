# 记忆三层架构

DeerFlow 的长期记忆系统采用三层架构——`user`（用户层）、`topOfMind`（最近焦点层）和 `facts`（原子事实层）。每层有不同的语义含义、更新频率和容量限制，共同构成一个既能让 Agent"记住你是谁"、又能"了解你在关注什么"、还能"持有具体知识点"的全方位记忆结构。

## 三层结构总览

```
memory.json
├── user/           # 用户层：相对稳定的个人背景
│   ├── workContext/    # 工作背景（公司、职位、技术栈）
│   ├── communicationStyle/  # 沟通风格偏好
│   └── preferences/    # 偏好和习惯
├── topOfMind/      # 最近焦点层：当前关注的事物
│   ├── summary/       # 当前项目的核心内容摘要
│   └── projects/      # 正在进行的项目
└── facts/          # 原子事实层：可独立引用的具体信息
    ├── content/        # 事实内容
    ├── category/       # 分类（context | goal | preference | skill | project）
    ├── confidence/     # 置信度（0.0-1.0）
    └── source/         # 来源 thread_id
```

## 每一层的语义和更新逻辑

### 第一层：user — 你是谁

`user` 是最稳定的一层，存放关于用户本人相对不变的背景信息：

```json
{
  "workContext": {
    "summary": "字节跳动后端开发工程师，主要使用 Go 和 Python",
    "updatedAt": "2026-03-10T08:00:00Z"
  }
}
```

这一层的 Fact 通常置信度很高（0.9+），因为它们来自用户在多个会话中反复提及的信息。更新时不是覆盖，而是**合并**——新旧 summary 会由 LLM 综合成一个更全面的描述，而非简单替换。

### 第二层：topOfMind — 你在想什么

`topOfMind` 是最动态的一层，对应当前会话中最"新鲜"的信息：

```json
{
  "summary": "正在研究 DeerFlow 的记忆系统架构，计划下季度迁移 CI/CD 到 GitHub Actions",
  "projects": [
    {
      "name": "DeerFlow 源码解析",
      "description": "为 DeerFlow 0.3 版本编写完整的中文源码解析 wiki"
    }
  ]
}
```

这一层的更新策略是**直接替换**——每次新会话可能更新 `summary`，因为"最近在想什么"是易变的。`projects` 列表有数量限制（默认 5 个），超出时按时间顺序淘汰。

### 第三层：facts — 我知道的具体事情

`facts` 是一个扁平的事实列表，每条 Fact 都有明确的语义分类：

| category | 含义 | 示例 |
|----------|------|------|
| `context` | 上下文背景 | "用户在字节工作" |
| `goal` | 目标或计划 | "计划迁移 CI/CD 到 GitHub Actions" |
| `preference` | 偏好 | "喜欢用中文交流" |
| `skill` | 技能或经验 | "熟悉 Python 和 Go" |
| `project` | 项目参与 | "正在参与 DeerFlow wiki 项目" |

每条 Fact 有独立的置信度分数和来源记录，支持跨会话的证据累积（详见[[concepts/deerflow-book/置信度阈值]]）。

## 三层的交互关系

三层不是孤立的，而是协同工作的：

**用户说**："我最近在做一个 DeerFlow 的中文 wiki。"

**LLM 记忆更新时的处理**：

1. `workContext` 可能保持不变（新信息与此层语义不符）
2. `topOfMind.summary` 需要更新，加入"做 DeerFlow wiki"这一新焦点
3. `facts` 可能新增一条 `{category: "project", content: "正在为 DeerFlow 编写中文 wiki", confidence: 0.7}`

**下次对话开始时**，Agent 注入的记忆格式为：

```
## 关于你
- 工作背景：字节跳动后端开发，使用 Go 和 Python
- 当前焦点：正在做 DeerFlow 中文 wiki 项目，计划下季度迁移 CI/CD

## 我知道的事
- 你在字节跳动（来源：thread_abc，置信度：高）
- 你计划迁移 CI/CD 到 GitHub Actions（来源：thread_xyz，置信度：0.9）
- 你在写 DeerFlow wiki（来源：thread_123，置信度：0.7）
```

## 容量限制与淘汰策略

三层架构各有容量限制：

- `facts`：最多 100 条（`max_facts`），超出时按置信度淘汰最低的
- `projects`：最多 5 个，超出时按 `updatedAt` 淘汰最旧的
- `user.*`：无硬性数量限制，但 summary 过长时会在下次更新时被 LLM 压缩

这种分层容量设计确保了记忆文件不会无限膨胀，同时优先保留高价值（高置信度、近期相关）的信息。

## 与上下文注入的区别

记忆三层架构和上下文注入（Context Injection）是两个互补的机制：

- **上下文注入**：在单次会话开始时，将 `memory.json` 中的信息格式化后注入 System Prompt，让 Agent 在当前会话中"知道"用户背景
- **记忆三层架构**：在每次会话结束后，从对话中抽取新的信息，更新 `memory.json`

两者的关系类似于"读"和"写"——上下文注入是"读出"历史记忆服务于当前对话，记忆更新是"写入"新对话中的信息到长期记忆。

## 小结

三层记忆架构是 DeerFlow 对"AI 记忆用户"这个问题的结构化答案：稳定的用户背景放在 `user` 层缓慢更新，当前关注的焦点放在 `topOfMind` 层快速迭代，可独立引用的具体事实放在 `facts` 层累积。三层各有不同的更新策略和容量限制，共同实现了一个既能"了解你是谁"又能"跟上你变化"的记忆系统。
