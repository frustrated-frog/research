# 渐进式加载

**渐进式加载（Progressive Loading）** 是 DeerFlow Skills 系统的核心设计策略——不是为了炫技，而是解决一个真实的上下文窗口压力问题：如果 17 个内置 Skill 的完整操作手册全部塞进 System Prompt，再强大的模型也会被撑爆。

## 问题背景

DeerFlow 0.3 版本内置了 17 个 Skill，包括 deep-research、data-analysis、image-generation、video-generation 等。以 deep-research 为例，它的 SKILL.md 本身就长达数百行，加上 data-analysis 的 DuckDB 脚本说明、frontend-design 的 Vercel 指南等，所有 Skill 的总内容量轻易超过 10 万 token。

如果把这些全部注入 System Prompt，会发生两件事：上下文窗口迅速被填满，导致长任务执行到一半就"失忆"；每次工具调用的可用上下文空间被压缩，推理质量下降。

## 三层加载模型

DeerFlow 采用了严格的三层渐进式加载策略：

| 层级 | 内容 | 注入时机 | 大小 |
|------|------|---------|------|
| **第一层** | name + description | 始终在 System Prompt | ~100 词 |
| **第二层** | SKILL.md 正文 | 用户查询匹配到 Skill 时 | 建议 < 500 行 |
| **第三层** | 脚本、参考文档、模板 | 执行过程中按需读取 | 无限制 |

### 第一层：始终可见的元数据

System Prompt 中的 `<skill_system>` 部分包含所有启用 Skill 的简短列表：

```
<skills>
    <skill>
        <name>deep-research</name>
        <description>Use this skill instead of WebSearch for ANY question requiring web research...</description>
        <location>/mnt/skills/public/deep-research/SKILL.md</location>
    </skill>
    <skill>
        <name>data-analysis</name>
        <description>Analyze Excel and CSV files with DuckDB...</description>
        <location>/mnt/skills/public/data-analysis/SKILL.md</location>
    </skill>
    ...
</skills>
```

Agent 收到的信息只有：Skill 叫什么名字、做什么用、文件在哪里。它据此决定"这个任务是否需要加载某个 Skill"。

### 第二层：按需加载完整指令

当 Agent 判断需要使用某个 Skill 时，它主动调用 `read_file` 工具读取对应的 SKILL.md 文件。System Prompt 中已经注入了明确的加载指令：

```
**Progressive Loading Pattern:**
1. 当用户查询匹配某个 Skill 时，立即调用 read_file 读取 Skill 主文件
2. 阅读并理解 Skill 的工作流和指令
3. Skill 文件中引用了同目录下的外部资源
4. 仅在执行过程中需要时才加载引用的资源
```

这意味着 17 个 Skill 在未被触发前，对 Agent 来说是"透明"的。只有真正需要的 Skill 才会占据上下文空间。

### 第三层：执行时按需读取外部资源

SKILL.md 中可能引用了 `scripts/`、`references/`、`assets/` 下的文件。Agent 只在具体执行到相关步骤时才去读取这些资源，而非一次性全部加载。

## 节省了多少上下文？

做个粗略估算：

- 17 个 Skill 的元数据（name + description）：约 1,700 词 ≈ 2,500 tokens
- 假设平均每个 Skill 被触发的概率是 20%，即 3-4 个 Skill 实际被加载
- 每个被加载的 SKILL.md 平均 200 行 ≈ 3,000 tokens
- 总计：2,500 + 3 × 3,000 ≈ 11,500 tokens（vs. 全部加载可能需要 80,000+ tokens）

节省超过 85% 的上下文占用，而且这个节省是自动的——Agent 越精准地只在需要时触发 Skill，节省越多。

## 与 MCP 工具加载的对比

Skills 的渐进式加载与 MCP 工具的动态发现是两种互补的扩展机制：

- **MCP 工具**：通过 `get_cached_mcp_tools()` 每次从磁盘读取配置文件，工具列表在 Agent 启动时完整注入
- **Skill 指令**：通过 `get_skills_prompt_section()` 生成元数据列表，完整 SKILL.md 由 Agent 按需主动读取

两者的加载时机不同：MCP 工具是"启动时全量注入，按需调用"，Skill 指令是"启动时只注入元数据，触发时才加载正文"。

## 小结

渐进式加载是 DeerFlow 在上下文管理方面的创新实践。它通过三层分离（元数据 → 正文 → 外部资源），让 Agent 的上下文占用从"O(全部 Skill)"降为"O(触发的 Skill)"，同时保持了"需要时能获取完整指令"的能力。这是让 17 个内置 Skill 共存而不引发上下文战争的关键工程决策。
