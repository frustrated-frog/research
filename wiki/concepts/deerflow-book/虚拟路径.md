# 虚拟路径

**虚拟路径（Virtual Path）** 是 DeerFlow Sandbox 系统的核心抽象——一套 Agent 永远生活其中的"虚拟文件系统"路径。DeerFlow 规定所有 Agent 统一使用以 `/mnt/user-data` 为前缀的路径，无论底层是本地文件系统、Docker 容器还是 Kubernetes Pod，路径语义完全一致。

## 核心前缀：`/mnt/user-data`

```
VIRTUAL_PATH_PREFIX = "/mnt/user-data"
```

`/mnt/` 是 Linux 中挂载外部存储的标准目录，DeerFlow 选择这个前缀并非随意，而是精心利用了 LLM 训练数据中大量 Linux 运维文档形成的语义锚点——当 Agent 看到 `/mnt/` 路径时，会自然地将其理解为"外部挂载的持久存储"，而非"临时缓存"。

## 三个标准子目录

| 虚拟路径 | 用途 | 读写权限 |
|---------|------|---------|
| `/mnt/user-data/uploads/` | 用户上传的文件 | 只读（Agent 不能修改上传内容） |
| `/mnt/user-data/workspace/` | Agent 工作区 | 读写（临时文件、中间产物） |
| `/mnt/user-data/outputs/` | 最终产出物 | 读写（交付物必须在这里） |

此外还有 `/mnt/skills/` 用于 Skill 脚本的挂载。

## 虚拟路径的价值：透明适配多环境

虚拟路径的核心价值在于**对 Agent 屏蔽底层差异**。同一套工具代码在三种环境下无需任何修改：

**LocalSandbox 环境**：虚拟路径映射到宿主机目录
```
/mnt/user-data/workspace/* → ~/.deerflow/threads/{thread_id}/user-data/workspace/*
/mnt/user-data/uploads/*   → ~/.deerflow/threads/{thread_id}/user-data/uploads/*
/mnt/user-data/outputs/*   → ~/.deerflow/threads/{thread_id}/user-data/outputs/*
/mnt/skills/*              → ~/.deerflow/skills/*
```

**aio-sandbox（Docker）环境**：Docker Volume 挂载，虚拟路径即真实路径
```
/mnt/user-data/* → /mnt/user-data/* （恒等映射）
```

**K8s 环境**：PersistentVolume 挂载
```
/mnt/user-data/* → PersistentVolume 挂载到 Pod 内部
```

Agent 代码完全不知道也不需要知道自己在哪种环境里运行——它只需要使用虚拟路径，路径翻译由 DeerFlow 的沙箱层自动完成。

## 双向路径转换：LocalSandbox 的特殊处理

LocalSandbox 是唯一需要进行路径转换的环境，因为 Agent 的"虚拟世界"和宿主机的"真实世界"是完全不同的两套文件系统。转换逻辑分两阶段：

**正向转换（命令执行前）**：虚拟路径 → 物理路径
```python
# tools.py 中的 replace_virtual_paths_in_command()
def replace_virtual_paths_in_command(command: str, thread_data) -> str:
    for subdir in ["workspace", "uploads", "outputs"]:
        virtual_base = f"{VIRTUAL_PATH_PREFIX}/{subdir}"
        physical_base = thread_data.get(f"{subdir}_path")
        if command.startswith(virtual_base):
            relative = command[len(virtual_base):].lstrip("/")
            return f"{physical_base}/{relative}"
    return command
```

**反向转换（输出处理后）**：物理路径 → 虚拟路径
```python
# sandbox/local.py 中的 _reverse_resolve_paths_in_output()
# 将命令执行结果中出现的物理路径替换回虚拟路径
# 防止 Agent 在后续推理中使用物理路径导致混乱
```

这种双向转换确保 Agent 永远不会看到宿主机的真实目录结构，既是安全考量（防止路径穿越），也是工程考量（避免 Agent 记忆了只在本地有效的路径）。

## 工具层对虚拟路径的使用

所有五个沙箱内置工具（bash、ls、read_file、write_file、str_replace）的文档字符串都明确标注了虚拟路径前缀：

```
- User workspace: /mnt/user-data/workspace - Working directory for temporary files
- Output files: /mnt/user-data/outputs - Final deliverables must be saved here
```

这些路径说明通过 System Prompt 注入到 Agent 的上下文中，使 Agent 理解"工作区是临时的，输出目录是持久化的交付物"这一语义差异。

## 小结

虚拟路径是 DeerFlow 多环境适配策略的基石。`/mnt/user-data` 前缀统一了三种部署环境下的文件系统访问约定，双向路径转换机制确保 LocalSandbox 模式下 Agent 始终生活在虚拟世界中，而不需要关心宿主机的物理目录结构。这套设计将"Agent 写代码"与"系统管路径"完全解耦，让开发者可以一处编写、多处运行。
