# 沙箱（Sandbox）

**沙箱（Sandbox）** 是 DeerFlow 为 Agent 提供的一个完整的虚拟计算环境——包含文件系统、命令行工具、五个标准化工具函数，以及与宿主机隔离的独立工作空间。Sandbox 让 Agent 能够像使用一台真实计算机一样读写文件、执行命令、安装依赖、运行脚本，而不破坏宿主系统的安全边界。

## 为什么需要沙箱

Agent 执行用户任务时，可能需要：
- 运行 Python 脚本分析数据
- 执行 `git clone` 拉取代码仓库
- 安装 npm 包
- 编译程序

这些操作在宿主机上直接执行是危险的——文件覆盖、系统命令误用、依赖冲突等问题层出不穷。沙箱通过进程级或容器级隔离，确保 Agent 的所有操作都在受控范围内执行。

## Sandbox 抽象基类

所有沙箱实现继承自 `Sandbox` 抽象基类（`backend/src/sandbox/base.py`）：

```python
class Sandbox(ABC):
    _id: str

    @abstractmethod
    def execute_command(self, command: str) -> str: ...

    @abstractmethod
    def read_file(self, path: str) -> str: ...

    @abstractmethod
    def list_dir(self, path: str, max_depth=2) -> list[str]: ...

    @abstractmethod
    def write_file(self, path: str, content: str, append: bool = False) -> None: ...

    @abstractmethod
    def update_file(self, path: str, content: bytes) -> None: ...
```

五个抽象方法定义了沙箱的统一接口。上层工具函数完全不知道也不关心底层是哪种实现。

## 虚拟路径系统

Sandbox 的所有路径操作都基于虚拟路径前缀 `/mnt/user-data/`：

| 虚拟路径 | 实际含义 |
|---------|---------|
| `/mnt/user-data/uploads/` | 用户上传的文件（只读） |
| `/mnt/user-data/workspace/` | Agent 工作目录（读写） |
| `/mnt/user-data/outputs/` | 最终交付物（读写） |
| `/mnt/skills/` | Skill 脚本挂载点 |

虚拟路径对 Agent 屏蔽了底层环境的差异——同一套工具代码在 Local、Docker、K8s 三种环境下无需修改。

## 三种沙箱实现

### 1. LocalSandbox（本地开发用）

直接在宿主机上执行命令，不需要 Docker：

```python
class LocalSandbox(Sandbox):
    def __init__(self, id: str, path_mappings: dict[str, str] | None = None):
        self.path_mappings = path_mappings or {}
```

**路径映射**（最长前缀匹配）：
```
/mnt/user-data/workspace/* → ~/.deerflow/threads/{thread_id}/user-data/workspace/*
/mnt/skills/*              → ~/.deerflow/skills/*
```

**双向转换**：命令执行前将虚拟路径转为物理路径，输出中再将物理路径转回虚拟路径，确保 Agent 永远不感知物理路径。

**单例模式**：`LocalSandboxProvider.acquire()` 返回同一个实例，`release()` 是空操作。

### 2. AioSandbox（Docker 容器隔离）

字节跳动开源的 All-In-One 沙箱，通过 HTTP API 与容器交互：

```python
class AioSandbox(Sandbox):
    def __init__(self, id: str, base_url: str, home_dir: str | None = None):
        self._client = AioSandboxClient(base_url=base_url, timeout=600)
```

**恒等映射**：Docker Volume 直接挂载 `/mnt/user-data/`，虚拟路径就是容器内真实路径，无需路径转换。

**热池机制**：`AioSandboxProvider` 维护一个 `_warm_pool`，`release()` 不销毁容器，而是放入热池复用。超过 `replicas` 上限后，LRU 淘汰最久未使用的热池容器。

**空闲超时**：后台守护线程每 60 秒检查，超过 `idle_timeout`（默认 600 秒）的容器被销毁。

### 3. RemoteSandboxBackend（Kubernetes 生产用）

通过 Provisioner 在 K8s 集群中动态创建 Pod：

```yaml
sandbox:
  use: src.community.aio_sandbox:AioSandboxProvider
  provisioner_url: http://provisioner:8002
```

Provider 自动检测到 `provisioner_url` 后选择 `RemoteSandboxBackend`，通过 HTTP API 与 Provisioner 通信，由后者在 k3s 中创建 Pod 和 NodePort Service。

## 生命周期管理

```
Agent 启动（before_agent）
    ↓
首次工具调用 → ensure_sandbox_initialized()
    ↓
Provider.acquire(thread_id) → 获取/创建 Sandbox 实例
    ↓
runtime.state["sandbox"] = {sandbox_id}
    ↓
Agent 执行工具
    ↓
Agent 完成（after_agent）
    ↓
Provider.release(sandbox_id)
    ↓
LocalSandbox：空操作
AioSandbox：放入热池（不销毁）
    ↓
[后台：空闲超时 / 容量驱逐 / 应用关闭]
    ↓
Provider.destroy(sandbox_id) → 真正停止容器
```

延迟初始化（`lazy_init=True`）确保不需要沙箱的 Agent 调用零开销。

## 工具函数层

沙箱之上的五个工具函数（`bash`、`ls`、`read_file`、`write_file`、`str_replace`）是 Agent 实际调用的接口：

```python
@tool("bash", parse_docstring=True)
def bash_tool(runtime: ToolRuntime, description: str, command: str) -> str:
    sandbox = ensure_sandbox_initialized(runtime)
    ensure_thread_directories_exist(runtime)
    if is_local_sandbox(runtime):
        command = replace_virtual_paths_in_command(command, thread_data)
    return sandbox.execute_command(command)
```

所有工具都遵循同一模式：获取沙箱实例 → 确保目录存在 → 必要时做路径转换 → 委托执行。

## 安全边界

沙箱定义了清晰的安全边界：

- **LocalSandbox**：无隔离，只能用于本地开发（Agent 可访问宿主机所有资源）
- **aio-sandbox**：容器级隔离，文件系统、网络、进程与宿主机分离
- **K8s**：Pod 级隔离，可配合网络策略实现更细粒度的多租户控制

无论哪种实现，Agent 都无法访问沙箱边界之外的资源。

## 小结

Sandbox 是 DeerFlow 为 Agent 打造的"虚拟计算机"——通过统一的抽象接口和虚拟路径系统，让 Agent 能够在隔离环境中安全地执行文件系统操作和命令。三种实现（Local/aio-sandbox/K8s）覆盖了从本地开发到生产部署的全部场景，延迟初始化和热池机制确保了资源的按需使用和高效复用。理解沙箱系统，是理解 DeerFlow 如何实现"安全且高效的多 Agent 执行"的基础。
