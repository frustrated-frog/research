# 子智能体（Sub-agent）

**Sub-agent** 是 DeerFlow 多 Agent 架构的核心组成——一种由 Lead Agent 动态创建的轻量级执行单元，专门用于并行处理复杂任务中的独立子任务。与 Lead Agent 共享同一个进程的 Thread 不同，每个 Sub-agent 运行在完全独立的执行上下文中，拥有自己的消息历史、工具调用和状态管理。

## 何时使用 Sub-agent

DeerFlow 的 System Prompt 中明确列出了适用和不适用的场景：

**适合使用 Sub-agent 的情况**：
- 复杂的研究问题（需要多角度同时探索）
- 多方面的分析（竞品分析需要同时研究多个对象）
- 大型代码库（多个模块可以并行理解）
- 综合性的调查（一份报告需要多个独立的信息来源）

**不适合使用 Sub-agent 的情况**：
- 任务不可分解（下一步依赖上一步的结果）
- 极其简单的操作（一次工具调用就能完成）
- 需要立即澄清（用户意图还不明确）
- 存在顺序依赖（步骤 B 必须等待步骤 A 完成）

## Sub-agent 的类型

DeerFlow 内置两种 Sub-agent 配置：

### 1. General Purpose（通用型）

`SubagentConfig` 数据类定义在 `backend/src/subagents/builtins/general_purpose.py`：

```python
GENERAL_PURPOSE_CONFIG = SubagentConfig(
    name="general-purpose",
    description="General purpose agent for complex multi-step tasks",
    tools=["bash", "ls", "read_file", "write_file", "str_replace", "web_search", "web_fetch"],
    max_turns=20,
)
```

通用型 Sub-agent 配备完整的工具集，可以进行网络搜索、文件读写、命令执行，是最常用的 Sub-agent 类型。

### 2. Bash（命令执行型）

```python
BASH_AGENT_CONFIG = SubagentConfig(
    name="bash",
    description="Bash agent for command execution only",
    tools=["bash"],
    max_turns=5,
)
```

Bash 型 Sub-agent 只有执行命令的能力，适用于只需要运行脚本、编译代码等简单重复性任务。

## 执行引擎：SubagentExecutor

Sub-agent 的生命周期由 `SubagentExecutor` 管理（`backend/src/subagents/executor.py`），其核心是一个状态机：

```
PENDING → RUNNING → COMPLETED
              ↓
           FAILED / TIMED_OUT / CANCELLED
```

### 双线程池架构

`SubagentExecutor` 使用两个独立的线程池处理并发请求：

```
scheduler pool (2 线程)
    │
    └── 接收 execute_async() 调用，提交到 execution pool
            │
            ▼
    execution pool (3 线程)  ← MAX_CONCURRENT_SUBAGENTS=3
            │
            └── 真正执行 Sub-agent 的 ReAct 循环
```

**为什么两层池？** `scheduler pool` 负责接收请求和管理任务队列，`execution pool` 负责实际执行。两者分开确保任务提交（快）和任务执行（慢）互不阻塞。

### execute_async：异步任务提交

```python
def execute_async(self, prompt: str, task_id: str | None = None) -> str:
    task_id = task_id or str(uuid.uuid4())

    def background_target():
        # 创建 LangGraph 图
        # 运行 ReAct 循环
        # 保存结果到内存字典

    future = self._executor.submit(background_target)
    self._tasks[task_id] = {
        "future": future,
        "status": SubagentStatus.PENDING,
        "result": None,
    }
    return task_id
```

任务提交后立即返回一个 `task_id`，调用者通过轮询 `get_background_task_result(task_id)` 检查状态。

## 任务委派：task 工具

Lead Agent 使用 `task` 工具委派任务：

```python
@tool("task", parse_docstring=True)
def task_tool(
    runtime: ToolRuntime,
    description: str,          # 简短描述（3-5 词），用于日志
    prompt: str,                # 详细的子任务描述
    subagent_type: Literal["general-purpose", "bash"],
    tool_call_id: Annotated[str, InjectedToolCallId],
    max_turns: int | None = None,
) -> str:
```

执行流程：

```
task_tool 被调用
    ↓
创建 SubagentExecutor(config, tools, ...)
    ↓
executor.execute_async(prompt, task_id=tool_call_id)
    ↓
返回 "Task started"（不等待完成）
    ↓
轮询循环（每 5 秒检查一次状态）
    ↓
推送 task_started / task_running / task_completed 事件到前端
    ↓
最终返回 SubagentResult.result
```

前端可以实时显示 Sub-agent 的执行进度，给用户"多个助手在同时工作"的感觉。

## 与 Lead Agent 的关键区别

| 维度 | Lead Agent | Sub-agent |
|------|-----------|-----------|
| 创建方式 | 启动时创建，常驻 | 通过 task 工具动态创建，按需运行 |
| 生命周期 | 与会话同长 | 任务完成后即结束 |
| 上下文 | 共享主线程状态 | 完全独立的消息历史 |
| 状态持久化 | Checkpointer 持久化 | 不持久化（无状态） |
| 工具集 | 全部工具 + task 工具 | 不含 task 工具（防递归） |
| 内存管理 | 有 MemoryMiddleware | 无 |

## 并发控制

`SubagentLimitMiddleware` 确保单个响应中最多只有 3 个（默认）`task` 调用被触发：

```python
def after_model(self, state, runtime) -> dict | None:
    last_msg = messages[-1]
    task_calls = [tc for tc in last_msg.tool_calls if tc.get("name") == "task"]
    if len(task_calls) > self.max_concurrent:
        # 截断超额调用，只保留前 max_concurrent 个
        ...
```

即使 LLM 在一次响应中生成了 10 个 `task` 调用，也只有前 3 个会被执行。这既是资源保护，也是避免上下文膨胀的必要措施。

## 小结

Sub-agent 是 DeerFlow 并行执行能力的核心载体——通过 `task` 工具，Lead Agent 可以将复杂任务分解为多个独立的子任务并行执行，每个子任务在完全隔离的上下文中运行，最终结果以结构化摘要的形式返回给 Lead Agent。双线程池架构确保任务提交和执行分离，状态机管理保障了生命周期的可靠转换，而 `SubagentLimitMiddleware` 的硬限制防止了资源耗尽。
